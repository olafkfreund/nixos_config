# Intent: MCP servers do not follow a rebuild

## Problem

On a machine where Claude Code has already run, an MCP server's binary and its
tool descriptions stop tracking this repo's configuration. Changing the Nix
config does nothing; the server keeps running whatever build it was first
pointed at, silently and indefinitely.

The mechanism: `home/development/claude-code-mcp.nix` renders
`~/.claude/settings.local.json`, but that file is **seeded only when missing**
(#398, `claude-code-mcp.nix:258-263`) because Claude Code mutates it at runtime
and a read-only symlink fails with EACCES. The live registration is elsewhere —
`~/.claude.json` — and nothing reconciles the two.

**This has already caused two silent failures**, both of which passed a green
build, all seven CI checks, and review:

1. #1928 changed the `ollama-code` MCP `description` in Nix. It reached
   neither an existing install nor the model. Found by a `codex review` run
   against already-merged code.
2. #1931 then corrected the `ollama_code` docstring in
   `pkgs/ollama-mcp/server.py` — which genuinely is the model-facing text —
   and it *still* did not take effect, because the registered command points
   at `~/.local/state/nix/gcroots/ollama-mcp/bin/ollama-mcp`, a gcroot symlink
   resolving to the previous build. A full `switch` on p620 did not move it.
   No file in this repo manages that gcroot; `grep -rIln 'gcroots'
   --include='*.nix' .` returns nothing.

**It is wider than the one server.** Of the servers registered in
`~/.claude.json`, five are pinned to frozen `/nix/store` paths — `agent-bus`,
`mcp-nixos`, `mcp-server-fetch`, `mcp-server-git`, `nixos` — and one
(`ollama-code`) is gcroot-pinned. Two different `mcp-nixos` builds are
registered simultaneously (2.3.1 and 3.0.1), which is the drift showing
through.

**There is a second failure mode nobody has hit yet.** Those five frozen store
paths are not garbage-collection roots in any way this repo establishes. They
all resolve today, but a `nix-collect-garbage` that removes one leaves a
registered MCP server whose binary no longer exists. That failure would look
like a server that simply stops working, with nothing in the config to explain
it.

## Proposed outcome

- A change to an MCP server's package or its tool description takes effect
  after a normal rebuild, on a machine that already has Claude Code configured.
- If full reconciliation is not possible within the existing constraints, the
  divergence is at least **loud** rather than silent: something fails or warns
  when the registered command paths no longer match what the config builds.
- Registered MCP binaries cannot be garbage-collected out from under a working
  session.

## Affected users and systems

- `home/development/claude-code-mcp.nix` — the seeding logic.
- `~/.claude.json` and `~/.claude/settings.local.json` — the live and seed
  registrations. Both are Syncthing-synced.
- `~/.local/state/nix/gcroots/ollama-mcp` — a gcroot created outside Nix.
- p620 and razer, which run Claude Code. p510 does not.
- Six MCP servers across two pinning styles.

## Constraints

- **`~/.claude` is Syncthing-synced.** Nothing in it may become a nix-store
  symlink; that breaks sync.
- **`settings.local.json` cannot be read-only** (#398). Claude Code writes to
  it at runtime — `claude mcp add`, accepted permissions — and a read-only
  symlink fails with EACCES. Whatever is done must preserve that.
- **Do not clobber what Claude Code owns at runtime.** The live file holds
  state this repo did not put there and must not discard.
- **The fix must be verifiable by effect, not by edit.** This whole issue
  exists because two changes were confirmed by reading a diff rather than by
  observing the running system. Any verification that amounts to "the Nix
  attribute now says X" is insufficient by construction.
- p510 is not involved.

## Open questions

1. **Reconcile, or just detect?** Reconciling `~/.claude.json` means writing to
   a file Claude Code owns, which is the thing #398 backed away from. Detecting
   drift and failing loudly is far less invasive and solves the silent half of
   the problem, but leaves a manual resync step. A detector is worth having
   either way; the question is whether it is the whole fix.
2. **Should the five frozen store paths become real GC roots?** That fixes the
   latent garbage-collection failure but entrenches the pinning rather than
   removing it.
3. **Is `ollama-code`'s gcroot repointed, removed, or brought under Nix?** It
   was created outside this repo, so adopting it is a decision about ownership,
   not just a path change.
