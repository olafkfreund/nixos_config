# Intent: Install nix-skills on every host

## Problem

We maintain our own collection of portable Nix skills,
[olafkfreund/nix-skills](https://github.com/olafkfreund/nix-skills), but
nothing installs it. None of the agents on our hosts can use it. Its skills
fill real gaps next to what is installed today (nixarchy's `nixos*` skills,
our `nixos-standards`, and the mcp-nixos server):

- `nix-language`: Nix syntax, laziness, scoping and builtins
- `nixpkgs-development`: packages, overrides, overlays and lib APIs,
  checked against the project's own pin
- `microvm-nix`: declarative microVMs, which p510 runs
- `home-manager`: HM configuration and its NixOS integration

The collection ships a Home Manager module, `programs.nix-skills`. Since
nix-skills#18 it has an `agents` option that installs the same skills into
each agent's own directory in one setup.

## Proposed outcome

- On p620, razer and p510, the four skills above are available to Claude
  Code (`~/.claude/skills`), Codex (`~/.agents/skills`) and Antigravity
  (`~/.gemini/config/skills`).
- They are pinned through `flake.lock` and updated with
  `nix flake update nix-skills`, like every other input.
- Two skills are left out on purpose:
  - `devenv-project` overlaps nixarchy's `devenv` skill, which knows this
    machine's setup and is marked required for the same requests.
  - `nixos-wiki` is a 17-topic snapshot that the mcp-nixos server already
    searches live.

## Affected users and systems

- Hosts: p620, razer and p510. All three already load
  `home/development`, where the current skills are declared.
- Files, roughly: `flake.nix` and `flake.lock` (new input, following our
  nixpkgs and home-manager) and `home/development/claude-code-skills/default.nix`
  (import the module and enable it).
- User: olafkfreund.

## Constraints

- `~/.claude` is synced between hosts by Syncthing. Store symlinks under
  `skills/` must not sync. `home/syncthing-stignore.nix` already excludes
  every `home.file` under `.claude/skills/`, and this module installs
  through `home.file`, so no change is needed there. This must be verified,
  not assumed.
- The input must `follows` our nixpkgs and home-manager, so the lock does
  not carry second copies.
- No existing skill is replaced or overwritten. The new names do not
  collide with any existing ones.
- p510 is deployed only with the user's go-ahead, which is given for this
  task ("deploy nix-skills to all hosts"). The managed deploy guard may
  still require the user to run the p510 command.

## Open questions

- Gemini CLI reads `~/.gemini/skills`, which the module's agent list does
  not cover (it has Antigravity's `~/.gemini/config/skills`). Is Antigravity
  enough, or should nix-skills gain a `gemini` agent first? Proposal:
  Antigravity only for now.
