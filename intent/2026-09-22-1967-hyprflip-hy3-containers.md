# Intent: load the hy3 container provider for Hyprflip on p620

## Problem

OmaCards (the Omarchy bar plugin `io.github.nocstah.omacards`, installed on p620
on 2026-09-22) can only make two-window flip pairs. Its multi-app cards, with up
to three apps per side, need Hyprflip's container provider: the hy3 Hyprland
plugin, loaded next to Hyprflip. On p620 that provider is built but never loaded.

- `programs.hyprflip.containers.enable = true` builds a patched hy3 and installs
  it at `/etc/hyprflip/libhy3.so`. That is all the NixOS module does.
- The only thing that loads Hyprflip into the session is
  `~/.config/hypr/hyprflip.lua` (required from `autostart.lua`). It loads
  `/etc/hyprflip/hyprflip.so` only. It is a hand-written file: not generated by
  Nix, and not in this repo.
- The result: `hyprctl -j plugin list` shows `hyprflip` only, and the Hyprflip
  helper that OmaCards calls reports `"containers": false, "max_panes": 0`.

There is a second, related gap. The Lua loader that decides what the live session
runs sits outside the repo, so a new home, a re-install or a mistaken edit loses
it silently.

## Proposed outcome

On p620, after a rebuild and a re-login:

- `hyprctl -j plugin list` shows both `hyprflip` and `hy3`.
- `hyprctl hyprflip status` reports `container_provider: true` and
  `container_max_panes: 3`.
- OmaCards' helper `snapshot` reports `containers: true`, and OmaCards offers
  multi-app cards.
- The Lua that loads Hyprflip and hy3 is declared in this repo, not hand-kept in
  `~/.config/hypr/`.
- Existing Hyprflip pairs and every current keybinding keep working.

## Affected users and systems

- **p620 only.** It is the only host with `programs.hyprflip`. razer and p510 are
  untouched.
- The live Hyprland session (a plugin loads into the compositor itself), the
  Omarchy session's Lua config under `~/.config/hypr/`, and OmaCards.
- **Workspace 8 on DP-1.** Upstream's container module puts it on the hy3
  layout. It is empty today.

## Constraints

- **Depends on uncommitted work.** `programs.hyprflip` (flake input
  `nixarchy-hyprflip`, the module import and the `hosts/p620/nixos/nixarchy.nix`
  block) exists only as staged, uncommitted changes in the shared `~/.config/nixos`
  checkout, made by another agent, and is what p620 runs now. It must land (or
  be on a branch) before this work can build on it. This work must not commit
  that change under another name.
- **Version pairing.** Upstream Hyprflip pins hy3 `42b7ed8` (bridge ABI 6). The
  `nixarchy-hyprflip` fork builds a patched hy3 at `12a73ab` against Hyprland main
  `23118f9f`. The pair must be proven to load together before the live session
  gets it. A plugin crash takes down the compositor and the whole desktop.
- **No `hyprctl reload` on the live session.** Earlier today it left every
  Omarchy shell keybinding dead. Load with `hyprctl plugin load`, or through a
  re-login.
- hy3 loads **after** Hyprflip, and only one hy3 may be loaded.
- Keybindings must not collide. Upstream's module adds Super+Ctrl+Alt+H/V/E/O.
  None is taken on p620 today. This repo already remaps upstream's P to S,
  because Super+Ctrl+Alt+P is GitLab Pipelines.
- Services-in-modules and the other AGENTS.md rules apply to whatever is
  declared.

## Open questions

- **Workspace 8 for hy3:** keep upstream's choice, or use another workspace?
  Recommendation: keep 8, since it is empty.
- **Scope of "declared":** move only the new hy3 and container Lua into the repo,
  or also take over the existing hand-written `hyprflip.lua`? Recommendation:
  both. Otherwise the loader for the core plugin stays unmanaged.
- **The OmaCards helper** (`~/.local/lib/hyprflip/*.py`, copied by hand today):
  declare it here too, or leave it for a separate issue? Recommendation: a separate
  issue, to keep this one about the compositor.
