# Intent: gliff remote desktop on razer and p510

## Problem

gliff (Omarchy's Hyprland remote desktop over ssh, shipped with nixarchy's
preinstalls) does not work against razer, and is not installed on p510.

- **razer** (Intel + NVIDIA Optimus): `gliff-server` defaults to the first
  render node, `/dev/dri/renderD128`, which is the NVIDIA card. Hyprland
  renders on the Intel iGPU (`/dev/dri/renderD129`), so every capture fails
  with `gbm: allocate 1920x1080 DrmFourcc(XR24): Invalid argument`. The client
  reconnects every 1-2 s and never shows a picture. Running the server with
  `--render-node /dev/dri/renderD129` was tested on 2026-10-11 and works
  (GPU→GPU, frames decoded).
- **p510** (NVIDIA only): `preinstalls = false`, so gliff is absent. A store
  copy tested on 2026-10-11 fails in both `--video gpu` and `--video cpu` with
  `gbm: map: No such file or directory`: gliff has no NVENC encoder and its CPU
  path cannot map NVIDIA's GBM buffers. That is an upstream limitation.

## Proposed outcome

- From p620, `gliff olafkfreund@razer.tail833f7.ts.net` (and the
  gliff-manager plugin entry) shows razer's desktop.
- gliff is installed on p510, so it starts working once upstream supports
  NVIDIA capture. Until then it fails as above; that is expected.
- An upstream issue on omacom/gliff reports both bugs (wrong render node on
  hybrid GPUs; CPU capture on NVIDIA GBM).

## Affected users and systems

- razer: system packages (gliff-server render node).
- p510: system packages (gliff added).
- p620: unchanged (client side already works).

## Constraints

- Explicit imports, no new auto-discovery; follow `docs/PATTERNS.md`.
- Do not enable nixarchy's full `preinstalls` on p510 (4 GiB, `/` space).
- p510 is never built or deployed without explicit approval at that time.
- razer heavy builds go via p620 (`just deploy-via-p620 razer`).
- The razer render node path must stay correct across boots
  (`renderD128`/`renderD129` numbering is by probe order).

## Open questions

- Is a renderD number stable enough on razer, or should the node be resolved
  by driver (i915) at runtime? Spec will decide; runtime lookup is the safer
  default.
