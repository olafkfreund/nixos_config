# Intent: live theme switch reaches GTK apps

## Problem

`omarchy theme set <name>` changes the bar, terminals, editors and the
browser at once, but GTK apps (Nautilus, file pickers, settings dialogs,
anything GTK 3 or non-libadwaita GTK 4) keep the previous colours until
the next rebuild.

Two systems write GTK colours, and the stale one wins:

- The theme engine (hyprchroma, enabled by nixarchy as
  `programs.nixarchyThemeEngine` with `targets.gtk = true`) writes the
  live palette to `~/.config/gtk-{3,4}.0/hyprchroma.css` on every theme
  switch, and adds `@import url("hyprchroma.css");` to the top of
  `gtk.css`.
- Stylix's GTK target, enabled in `modules/desktop/stylix-theme.nix` and
  `Users/common/base-home.nix`, has Home Manager install `gtk.css` with
  88 `@define-color` rules from the palette baked in at build time
  (`nixarchy-theme.nix`).

hyprchroma keeps Stylix's rules below its import line, and in CSS the
later definition wins. So the engine reports "GTK synchronized" and
nothing on screen changes. Seen on p620 on 2026-10-19: theme gruvbox,
`hyprchroma.css` gruvbox (`window_bg #282828`), and `gtk.css`
pastelppuccin from the last rebuild (`window_bg #1d1f20`).

`docs/architecture/desktop.md` and AGENTS.md describe GTK as following
"at the next rebuild", which matches what happens but not what the
engine is installed for.

## Proposed outcome

- After `omarchy theme set X`, a newly opened GTK app uses X's colours,
  with no rebuild.
- A rebuild does not put the old palette back: rebuild after a switch,
  and GTK still shows X.
- Everything else Stylix owns at build time (Plymouth, GRUB, console,
  Qt, fonts, the other Home Manager targets) behaves as it does today.
- The docs say which parts of the desktop follow a theme switch live and
  which wait for a rebuild.

## Affected users and systems

- Hosts: p620, razer and p510. All three run the Omarchy session, the
  theme engine and Stylix through `inputs.nixarchy`.
- User: olafkfreund.
- Files likely touched: `modules/desktop/stylix-theme.nix`,
  `Users/common/base-home.nix`, `docs/architecture/desktop.md`,
  AGENTS.md (the Omarchy theme note).
- The GNOME session on the same hosts also reads `gtk.css`.

## Constraints

- No hand-written colours: the Omarchy theme stays the single source of
  the palette.
- `gtk.css` must not become a nix-store link that the engine cannot
  write. It must also not be a file Home Manager clobbers or backs up on
  every activation (see the HM backupCommand memory note).
- p510 is built and deployed only after asking.
- The engine and Stylix both come in through `inputs.nixarchy`. A fix in
  this repo is preferred to patching or overlaying them.

## Open questions

1. Should the GNOME session also follow the live palette? Today it gets
   the Stylix palette from the same `gtk.css`. Only Stylix's GTK target
   decides that, not its GNOME target.
2. Qt apps may have the same conflict. Stylix's Qt target is on at the
   system level (`qtct`), hyprchroma writes `~/.config/kdeglobals`, and
   `qt6ct.conf` still holds leftovers from COSMIC and Noctalia. Fix that
   in this issue, or open a separate one?
3. Icons: gruvbox asks for `Yaru-olive`, which is not installed, so the
   icon theme does not change either. Install the Yaru icon themes the
   Omarchy themes name, or leave icons to Stylix's Papirus?

## Decisions at approval

1. GNOME: follows the live palette as well.
2. Qt: in scope. A theme switch must recolour every app it can reach, so
   if Qt has the same conflict, it is fixed here.
3. Icons: install the icon themes the Omarchy themes name (Yaru variants).
