# Intent: hello-lock lock screen on p620 and razer

## Problem

The user wants hello-lock, a third-party Omarchy lock screen plugin
(<https://github.com/denonmaryland/hello-lock>, MIT, QML), in place of
Omarchy's stock lock screen. The upstream install is
`omarchy plugin add … --enable`. That clones into `~/.config/omarchy/plugins`
outside Nix, follows upstream HEAD, and would differ between hosts.

A lock screen is security-critical. If it fails, the screen either does not
lock or cannot be unlocked. It has to be pinned and reproducible, and it
must not break locking.

## Proposed outcome

- **Hosts:** p620 and razer lock with hello-lock instead of the stock
  Omarchy lock screen.
- **Unlock:** unlocking works with the account password, as today.
- **Pinned source:** the plugin comes from a pinned upstream revision built
  into the Nix store, like omateams. It changes only through a reviewed
  bump, never `omarchy plugin update`.
- **Rollback:** reverting the change brings the stock lock screen back.
- **First run:** on the first shell start, hello-lock's first-run setup
  (name, logo, unlock symbol) runs once per host. Its answers live in
  `~/.config/hello-lock/`, which is user state and not managed by Nix.
- **Docs:** a page covering the plugin, its settings entry, upgrades, and
  how to get back to the stock lock screen.

## Affected users and systems

- Hosts: p620 and razer. p510 is not touched (it autologins for Sunshine
  and its lock is out of scope).
- Code: a new `hosts/common/nixos/omarchy-hello-lock.nix`, following
  `omarchy-omateams.nix` (`programs.nixarchy.plugins.<id>.src` plus
  `local.omarchy.enableOnce`), and a package under `pkgs/` or a pinned
  source.
- PAM: hello-lock authenticates through the existing
  `/etc/pam.d/omarchy-lock-password` (present today). It also uses
  `omarchy-lock-fingerprint` when that file exists, which it does not on
  either host.

## Constraints

- **Locking must never silently stop.** Upstream's own test shows that
  hello-lock refuses to lock when the PAM file is missing. The verification
  must prove the screen locks and unlocks on each host before the work is
  called done.
- **Recovery:** a way out of a broken lock must be known before deploying:
  a TTY or SSH, then disable the plugin and restart the shell. The docs
  must record it.
- **Pinned and offline:** the plugin is pinned to a revision with a hash.
  Nothing is fetched at runtime except the optional weather (wttr.in).
- **One lock service:** only one lock plugin may be active (hello-lock
  declares the `authentication` capability and replaces `omarchy.lock`).
  The stock lock screen must come back if hello-lock is disabled.
- **Arch-only helpers:** the helper scripts in `bin/` (`hello-status`
  uses `checkupdates`, a pacman tool) may only degrade gracefully on NixOS.
  None of them may be required for locking.
- **Deploys:** go through the agent-bus announcement. razer builds on
  p620. A shell restart is needed for a lock service to load. Every host's
  config is checked before a deploy.

## Open questions

- Should weather after unlock stay on (one wttr.in request per unlock), or
  be switched off by default?
- Should the first-run setup run on each host, or should a shared
  `~/.config/hello-lock/config.json` be declared in Nix so both hosts
  greet the same way? Upstream expects the file to be user-edited through
  its settings screen, so declaring it would make that screen read-only.
