# Intent: p620 boots cleanly: k3d comes up fast, boot-time downloads have DNS

## Problem

A log review after p620's 08:30 reboot on 2026-11-04 found three problems.

1. **The k3d cluster takes over 15 minutes to come back after a reboot.**
   - **What happened:** `k3d-cluster-bootstrap` hit its 15-minute start
     timeout and succeeded only on the retry, at 09:03. Until then the k3s
     server was reading its kine/SQLite datastore.
   - **The datastore's size:** `state.db` is 11.5 GB, yet the cluster was
     created on 2026-10-22, about 0.9 GB a day.
   - **Likely cause, unconfirmed:** p510's old cluster had the same bloat
     (2026-08-19). 69% of its rows were lease renewals, and with
     `auto_vacuum` off the file never shrank; a manual compaction took it
     from 11 GB to 766 MB. p620's row mix has not been checked yet, so this
     is a hypothesis for the spec to confirm.
   - **Two timeouts disagree:** the unit's `TimeoutStartSec = "15min"`
     (`modules/containers/k3d.nix:911`) kills the bootstrap partway through
     the script's own longer API wait (`apiWaitSeconds`, `k3d.nix:682`, used
     at `:316–318`), so its self-heal attempts never get their full time.
   - **Raising the timeout alone** would hide the growth, and the boot would
     get slower each week.
2. **Boot-time downloads start before DNS answers.** `ollama-model-loader`
   failed twice with `lookup registry.ollama.ai: no such host`, 6 seconds
   after `network-online.target`. It recovered on its own. `k3d.nix` already
   documents the same failure during `nixos-rebuild switch`, and avoids it
   there by not restarting the loader on switch (`ollama.nix:183–191`). The
   boot case is not covered.
3. **p620's DNS pin is ignored.** `hosts/p620/nixos/dns-fallback.nix:24–27`
   sets `ipv4.dns` and `ipv4.ignore-auto-dns` through
   `networking.networkmanager.connectionConfig`. NetworkManager logs
   `unknown key` for both at every start, and p620 uses the router's DNS
   from DHCP (`192.168.1.254`). The pin existed because DHCP used to hand out
   p620's own dead IP, which stopped with the router change. The rest of the
   file (systemd-resolved settings, `Domains = ~.`, and the Nix-managed
   `resolved.conf.d/performance.conf` override) is in effect, and is not
   part of this problem.

## Proposed outcome

- After a p620 reboot, `k3d-cluster-bootstrap` succeeds on its first try,
  and the cluster API is reachable within 5 minutes of boot.
- `state.db` stays below 2 GB without anyone compacting it by hand. A check
  shows its size, so growth is noticed before it slows a boot.
- `ollama-model-loader` does not fail on DNS at boot.
- No `unknown key` warning from NetworkManager at boot, and p620's DNS works
  as it does today: lookups, Tailscale MagicDNS and the resolved fallbacks.

## Affected users and systems

- p620:
  - `modules/containers/k3d.nix` (`modules.containers.k3d.*`)
  - `modules/services/ollama.nix` (`features.ollama-server`)
  - `hosts/p620/nixos/dns-fallback.nix`
- The k3d `factory` cluster, and the agents and CI that use it. Any
  compaction, migration or recreation takes the cluster down for a while.
  It holds stateful workloads (Keycloak, `skillai-db` with its
  `postgres-backup`), PV state and cluster-rotated credentials
  (`factory-cli-creds`).
- razer and p510 only if a shared module changes. p510 is not deployed
  without asking.

## Constraints

- **No cluster state may be lost.** The cluster's workloads, persistent
  volumes, databases and rotated credentials must survive. That includes a
  move to a different datastore, if the spec chooses one. There must be a
  backup, and a restore path that is tested before the change. `k3d.nix`
  documents earlier PVC data loss after a cluster was recreated.
- The cluster's downtime is announced on the agent bus. Agents and CI use
  the cluster.
- Follow the repo rules:
  - services live in `modules/` behind their enable option
  - no secrets in the store
  - any new unit gets the systemd hardening from AGENTS.md, or a written
    reason why not. The existing k3d units run as root to reach Docker.
- No change to the DNS resolvers p620 actually uses today without checking
  that lookups still work, including Tailscale MagicDNS.

## Open questions

1. How should the datastore's growth be bounded, and how should a slow
   start be recovered? Options include a scheduled SQLite cleanup and k3s's
   embedded etcd; the spec should compare the viable ones, including their
   migration risk.
2. Should a one-time compaction happen now, separately from this change, so
   the next reboot is fast? It costs about 30–45 minutes of cluster
   downtime.
3. Should the ignored `connectionConfig` pin be fixed or just removed? Its
   reason went away with the router change.
