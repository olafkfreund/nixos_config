# Intent: p620 boots cleanly: k3d comes up fast, boot-time downloads have DNS

## Problem

A log review after p620's 08:30 reboot on 2026-11-04 found three problems.

1. **The k3d cluster takes over 15 minutes to come back after a reboot.**
   `k3d-cluster-bootstrap` hit its 15-minute start timeout and succeeded only
   on the retry, at 09:03. The k3s server spent that time reading its
   kine/SQLite datastore. `state.db` is 11.5 GB, yet the cluster was created
   on 2026-10-22, so it grows about 0.9 GB a day. p510's old cluster had the
   same bloat (2026-08-19): 69% of its rows were lease renewals, and with
   `auto_vacuum` off the file never shrank. A manual compaction took it
   from 11 GB to 766 MB. Nothing stops it from growing again. Raising the
   timeout would hide the problem, and the boot would get slower each week.
2. **Boot-time downloads start before DNS answers.** `ollama-model-loader`
   failed twice with `lookup registry.ollama.ai: no such host`, 6 seconds
   after `network-online.target`. It recovered on its own, but any unit that
   needs the network at boot can hit the same race.
3. **p620's DNS pin is ignored.** `hosts/p620/nixos/dns-fallback.nix` sets
   `ipv4.dns` and `ipv4.ignore-auto-dns` in NetworkManager's `[connection]`
   section. NetworkManager logs `unknown key` for both at every start, and
   p620 uses the router's DNS from DHCP (`192.168.1.254`). The comment
   explains why the pin exists: DHCP used to hand out p620's own dead IP.
   That no longer happens since the router changed, but the pin does
   nothing, and the file says it does.

## Proposed outcome

- After a p620 reboot, the k3d cluster is reachable within a few minutes,
  and `k3d-cluster-bootstrap` succeeds on its first try.
- `state.db` stays small without anyone compacting it by hand.
- `ollama-model-loader` and other boot-time network jobs do not fail on DNS
  at boot.
- p620's DNS configuration either takes effect or is removed, and no
  `unknown key` warning is logged at boot.

## Affected users and systems

- p620: `modules/containers/k3d.nix`, `modules/services/ollama.nix` and
  `hosts/p620/nixos/dns-fallback.nix`.
- The k3d `factory` cluster and the agents and CI that use it. The one-time
  compaction takes the cluster down for a while.
- razer and p510 only if a shared module changes. p510 is not deployed
  without asking.

## Constraints

- No data the cluster needs may be lost. Compaction keeps the latest
  revision of every key, so only watch history goes; clients re-list.
  Back up `state.db` first.
- The cluster downtime is announced on the agent bus. Agents and CI use the
  cluster.
- Follow the repo rules: services in `modules/`, behind `features.*`, no
  secrets in the store.
- No change to the DNS resolvers p620 actually uses today without checking
  that lookups still work, including Tailscale MagicDNS.

## Open questions

1. Should the cluster's datastore move to k3s's embedded etcd, which
   compacts and defragments itself, or stay on SQLite with a scheduled
   cleanup? The spec should weigh both.
2. Should the one-time compaction happen now, separately from this change,
   so the next reboot is fast? It costs about 30–45 minutes of cluster
   downtime.
3. Should the DNS pin in `dns-fallback.nix` be fixed or removed? Its reason
   went away with the router change.
