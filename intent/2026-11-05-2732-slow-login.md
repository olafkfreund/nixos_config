# Intent: Omarchy login takes 20-27 s to settle

## Problem

After SDDM accepts the password, the desktop keeps changing for 20-27 s. The
compositor and the shell config are not the slow parts. The journal for the last
five logins on p620 shows the config loaded in about 3 s, followed by a long tail
of work that mostly repeats itself:

| Login                   | Shell config loaded | Plugins finished loading | hyprchromad started |
| ----------------------- | ------------------- | ------------------------ | ------------------- |
| Nov 02 11:21            | +2.9 s              | +7 s (no second pass)    | +24.7 s             |
| Nov 02 12:29            | +3.0 s              | +10 s                    | +20.8 s             |
| Nov 02 20:15            | +3.7 s              | +13 s                    | +21.4 s             |
| Nov 04 08:36 (1st boot) | +7.8 s              | +19 s                    | +27.3 s             |
| Nov 05 06:27            | +3.0 s              | +11 s                    | +20.1 s             |

Three causes are confirmed from the journal and the source:

- **Repeated theme syncs.** `hyprchromad.service` has nine `ExecStartPre` steps.
  Four are `--set-enabled=true`. A targeted run never takes the unchanged-state
  exit, which requires `--target=all` (`bin/hyprchroma:756`), and `--set-enabled=true`
  also sets `force=1` (`:537`). Each one syncs its target and then always runs
  terminals, shell and editors (`:1019-1021`). The two `--set-enabled=false` steps
  revert flatpak and browsers on every login. Steps seven and eight run shell and
  editors once more.
- **One more forced sync.** `omarchy-theme-gnome.service` runs
  `hyprchroma --target=gtk --force` in `ExecStartPost`. On Nov 05 that made six
  shell colour syncs in one login, with nothing changed.
- **Plugin rebuild at login.** `nixarchy-theme-engine-enable-plugin` runs
  `rescanPlugins` and `enablePlugin` every time. `rescanPlugins` reaches
  `reloadPlugins`, which unloads and rebuilds every panel, plugin service and
  widget. `setEnabled` has no already-enabled exit, so it also rewrites
  `shell.json`. In four of the five logins the whole plugin load runs twice: the
  log order repeats exactly (27:46.9-27:49.4, then 27:52.3-27:53.6 on Nov 05).

The units come from `modules/nixos.nix` in nixarchy-omatheme, which nixarchy
pins. Only the package override is in this repo, in
`hosts/common/nixos/omarchy-stylix-theme.nix`.

Some login work is useful and must survive:

- The daemon's own unforced sync applies a theme set while it was down
  (`bin/hyprchroma:182-185`).
- Unforced runs clear per-app colour overrides, recycle apps left stale by a theme
  change, and resume pending browser and Qt work (`:709-760`).
- The forced syncs currently also overwrite destination files edited out of band.
  The fingerprint does not hash those files, so an unforced run would not notice.

Not yet established:

- Which call starts the second plugin pass. The helper finished at 27:48.8 and the
  teardown began at 27:51.5, much later than the 150 ms debounce explains. Whether
  `enablePlugin` needed its 1 s and 2 s retries is also unknown.
- What is on screen. Nothing waits on `hyprchromad`: `graphical-session.target` is
  reached at about +2.7 s. The journal shows when work ends, and the Hyprland log
  has no timestamps, so the first visible frame has not been measured. The SDDM
  greeter is stopped at about +5.3 s, and whether that delays the handover is
  unmeasured too.
- How much of the delay is left after this. Removing the repeats may reveal other
  causes.

## Proposed outcome

Measured on a re-login on p620, with the theme unchanged:

- Exactly one theme sync pass runs, and the shell colours are synced at most once.
- The shell loads its plugins once, so there is no second pass.
- Theme work and plugin loading finish by about +8 s in the journal. The shell's
  own first plugin pass ends at about +7 s today, so 5 s is not reachable by this
  change alone.
- The user sees the desktop stop changing sooner than today. This is the user's
  own judgement at a real login, because the journal cannot measure it.

The first login after a boot is slower (+7.8 s for the shell config alone on
Nov 04). It is reported, but it has no target.

These must keep working:

- A real theme change still reaches GTK, Qt, icons, kitty, editors and Dark Reader.
- A theme set while the session was down is applied at the next login.
- Changing a target's enabled state in Nix takes effect, including switching one
  off, which reverts it.
- The Omarchroma plugin is enabled on a login where it was not enabled before.

## Affected users and systems

- p620, razer and p510: all three run this session and the same units, so the
  fix reaches every host.
- nixarchy-omatheme (`bin/hyprchroma`, `modules/nixos.nix`) and nixarchy, which
  pins it. Both are the user's own repositories.
- This repo, if a local override carries the fix until nixarchy publishes it.

## Constraints

- p510 is never built or deployed without asking first.
- Announce on the agent bus before any deploy or session restart.
- The change only proves itself at a real login, which ends the running session,
  so the logout is the user's to schedule.
- Do not change what the theme looks like, or stop it from following
  `omarchy theme set`.

## Open questions

1. Where should the fix live: upstream in nixarchy-omatheme with a nixarchy bump,
   a local override here first, or both? A local override takes effect sooner but
   adds a second shortcut to `omarchy-stylix-theme.nix`. Upstream fixes it for
   everyone, subject to nixarchy's publish lag.
2. Is it acceptable that a login no longer repairs destination files edited out of
   band while the palette is unchanged? They would stay edited until the next
   theme change or a manual forced sync.
