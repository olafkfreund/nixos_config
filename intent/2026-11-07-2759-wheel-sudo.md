# Intent: limit passwordless sudo for wheel

Split out of the Nix `trusted-users` work (issue 2758), by the owner's decision on its intent.

## Problem

`modules/security/default.nix:7` sets `security.sudo.wheelNeedsPassword = false`. The module is imported by
`modules/core.nix`, which `hosts/templates/desktop.nix` pulls in, so it applies to p620, razer and p510.
razer states the same setting again at `hosts/razer/configuration.nix:56`, with a comment that remote
`nhs razer` deploys need it.

The effect: any process running as `olafkfreund` can become root without a prompt. `sudo -n -l` on p620
prints `(ALL : ALL) SETENV: NOPASSWD: ALL`. That includes every coding agent's shell command, Codex and agy
implementer sessions, and anything a compromised npm, pip or editor plugin runs as the user.

The guards that stand between an agent and root today are PreToolUse hooks that match words in command text.
`modules/programs/claude-coder-guard.sh:8-10` calls itself "best-effort tripwire, not a sandbox", and the
bus guard (`modules/programs/claude-code-managed.nix`) is the same kind of check. An agent that writes a
script and runs it, or spells a verb indirectly, reaches root through `sudo -n` in one step.

Issue 2758 closes the other path to root, the Nix daemon socket for trusted users. Without this change,
closing that one leaves this one open, and the overall result is unchanged.

### What relies on passwordless sudo today (read-only survey)

| Caller | Where | How it elevates |
| ------ | ----- | --------------- |
| `nhs` / `just update-commit-deploy` | `scripts/update-commit-deploy.sh:407-411` | `nh os ... --elevation-strategy passwordless`, local and `--target-host` |
| `nhs` rollback | `scripts/update-commit-deploy.sh:592-593` | `sudo <old-gen>/bin/switch-to-configuration`, local and over `ssh` |
| `just p620` and local recipes | `Justfile:497` | `sudo nixos-rebuild ...` |
| `just razer`, `just p510`, remote recipes, `deploy-via-p620` | `Justfile:493, 502, 868, 978, 983, 1007, 1021` | `nixos-rebuild --target-host ... --sudo` over SSH, no TTY |
| GC and store recipes | `Justfile:563-638, 880-882` | `sudo nix-collect-garbage`, `sudo nix-store --optimize` |
| Agenix recipes | `Justfile:941-950` | `ssh HOST "sudo systemctl ..."`, `sudo rm -rf /run/agenix.d` |

Not affected, confirmed:

- The nightly `nixos-upgrade` (`modules/nix/nix.nix:7-25`) is a system unit with no `User=`;
  `systemctl show nixos-upgrade -p User` on p620 is empty, so it runs as root. p510 has it off
  (`hosts/p510/configuration.nix:547`).
- The `nixos-update-checker` timer runs as its own system user `nixos-update-checker` and only checks;
  it never calls sudo.
- No sudo `extraRules` exist anywhere in the repo today; the only policy is `wheelNeedsPassword`.
- No systemd unit, system or user, in the repo calls sudo (grep of `modules/`, `home/`, `hosts/`, `pkgs/`).
  Every other hit is a comment, a doc string or a
  test fixture.
- The k3s and nixvm microVM guests (`hosts/p510/nixos/microvm/*.nix`, `hosts/p620/microvm/flake.nix`) set
  their own `wheelNeedsPassword = false` inside the guest. They are out of scope.

### Why "NOPASSWD for exact deploy commands" does not close the hole

The obvious fix, `security.sudo.extraRules` with `NOPASSWD` on `nixos-rebuild` and `switch-to-configuration`,
cannot name exact paths: every deploy activates a new `/nix/store/<hash>-nixos-system-*/bin/switch-to-configuration`.
The rule would need a store-path wildcard. Any local user, trusted or not, can put a derivation in the store
whose `bin/switch-to-configuration` is a shell, and then run it as root through that rule. The chain is: build
any derivation (no trust needed), then run the wildcard-matched path through sudo. Allowing
`nix-env -p /nix/var/nix/profiles/system --set <path>` as root does not execute anything by itself, but it
points the boot profile at an arbitrary closure that runs as root at the next boot or activation.
So a wildcard allow-list over store paths is still root for the user. Whether a narrower mechanism exists
(for example a fixed root-owned wrapper that only activates a closure built from a reviewed commit) is for the
spec to evaluate; this note only rules out the obvious rule. This is stated here so the spec
does not pick it by default.

## Proposed outcome

- A process running as `olafkfreund` with no human present cannot become root on p620 or razer:
  `sudo -n true` fails there, and so do `run0`, `pkexec` and `doas` when they are not answered by the owner.
- The owner can still deploy p620 and razer with `nhs`, the `just` recipes and `deploy-via-p620`, by
  approving the elevation (a password, a touch or a click), and the switch, the boot-mode fallback and the
  rollback all still work. Few prompts per deploy is a goal, not a requirement.
- An owner approval is not reusable by an agent afterwards: not from another terminal, not after the owner
  leaves, and not by a later process in the same session. This is tested, not assumed.
- Unattended jobs keep working: the nightly upgrade and every timer.
- p510 behaves as it does today until the owner agrees to change it.

## Affected users and systems

- Hosts: p620 and razer. p510 only with the owner's agreement; p510 inherits the setting from
  `modules/security/default.nix` and has no override, so a change to that module reaches it unless the
  spec prevents that.
- Files: `modules/security/default.nix`, `hosts/razer/configuration.nix`, `scripts/update-commit-deploy.sh`,
  `Justfile` deploy, GC and agenix recipes, `modules/services/nixos-update-checker/default.nix`,
  `home/shell/{bash,zsh}.nix` aliases, and the docs that describe deploys (`docs/UPDATE-DEPLOY.md`).
- People: the owner, who will be asked to approve each elevation; every agent, which loses root.

## Constraints

- `nhs`, the `just` deploy recipes and `deploy-via-p620` must keep working on p620 and razer, local and
  remote, including the NVIDIA boot-mode fallback and the rollback path in `update-commit-deploy.sh`.
- Unattended jobs must keep working with no prompt. Today that is the root `nixos-upgrade` unit and the timers.
- No lockout on a remote host. razer is reached over SSH and may be away from p620 and from its owner's
  console. The rollback in `update-commit-deploy.sh:592-593` itself elevates through a fresh, TTY-less SSH
  command, so it breaks with the same change it is meant to undo. Each host must keep a recovery path that
  works remotely after the new policy is active, including when an activation changed sudo or PAM: the spec
  must name it and test it on the host before NOPASSWD is removed there.
- p510 is changed only with the owner's agreement, and never built or deployed by an agent.
- Secrets stay out of the Nix store. A sudo password, if one is used, is the user's login password. That
  password is not declared through agenix: the `user-password-olafkfreund` secret is commented out as broken
  (`modules/security/secrets.nix:35-40`), and no `hashedPassword` or `mutableUsers` setting was found for the
  user, so it was most likely set by hand. On p620, `passwd -S olafkfreund` (checked live) shows one set
  (`P`, 2024-12-19). razer and p510 are not checked, and the owner
  must know the password on each host before it gates root.
- Nothing an agent can reach by itself may answer the prompt: no password file the user can read, no
  `SUDO_ASKPASS` helper, no ssh-agent key that signs without the owner's touch or confirmation.
- What an owner approves is a deploy of whatever the checkout holds, and agents can write that checkout
  (`Justfile:497` builds `.#p620` from the current directory). This change stops unattended elevation; it does
  not make an approved deploy safe from agent-written configuration. That stays with review of the diff.
- The word-matching guards stay as they are. This change is meant to make them a second line, not to replace them.

## Open questions

1. **Password, or a different elevation path?** Options: a sudo password with the default per-TTY timestamp;
   `security.pam.sshAgentAuth` with a key that needs a touch or `ssh-add -c` confirmation; polkit `run0` with
   a desktop prompt; or a separate root SSH key for remote activation.
   Recommendation: start the spec from a sudo password, the simplest and supported by both tools
   (`nixos-rebuild --ask-elevate-password`, nh `auto`), but only if the spec shows that a cached approval
   cannot be reused by an agent (agents can run inside a terminal the owner typed into, such as a tmux pane).
   ssh-agent auth is weaker unless the key requires a touch, because agents share `SSH_AUTH_SOCK`.
2. **Any NOPASSWD left at all?** Recommendation: none for wheel. The store-path argument above makes every
   activation rule equivalent to `ALL`. Read-only commands such as `nix-env --list-generations` could be
   allowed, but nothing needs them unattended, so skip them.
3. **Remote deploys with no TTY.** `nixos-rebuild --target-host --sudo` today relies on NOPASSWD.
   Recommendation: the spec evaluates `--ask-elevate-password` (nixos-rebuild) and nh's `auto` strategy first,
   and proves on razer that the password reaches the remote sudo for the main activation, the boot fallback and
   the rollback. A root SSH key needing a touch is the fallback candidate.
4. **Caching approvals.** Any cache trades prompts for reuse by agents. Recommendation: no cache
   (`timestamp_timeout=0`) unless the spec proves the cache is unreachable from agent shells; accept a few
   prompts per deploy.
5. **p510.** Change it now, or keep `NOPASSWD` there with an explicit host override until the owner agrees?
   Recommendation: keep p510's behaviour unchanged in this change and handle it in a follow-up the owner
   schedules; it is never deployed by an agent. Note `p510-clear-sessions` fails silently once it changes.
6. **Order with issue 2758.** Recommendation: land them independently; each closes one path, and neither
   depends on the other. Note that until both land, neither reduces what an agent can do.
7. **polkit rule for `users`.** `modules/security/default.nix` lets any member of `users` reboot and power off
   without auth. Recommendation: out of scope here because it gives no root, though an agent can power-cycle a
   host through it and the hooks do not stop a determined one. Record it as a separate issue.
