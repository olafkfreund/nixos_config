# Intent: run coding agents as a separate low-privilege user

## Problem

Claude Code, Codex and agy all run as `olafkfreund`. So every agent has what the owner has:

- passwordless sudo, through `wheelNeedsPassword = false` (`modules/security/default.nix:7`),
  tracked as #2759;
- Nix daemon trust, through `trusted-users = [ "root" "olafkfreund" ]`
  (`modules/nix/nix.nix:29`), tracked as #2758;
- the owner's whole home: `~/.ssh`, `~/.config/gh`, `~/.config/nix/nix.conf` (which holds
  `access-tokens`), every tool's login, and the session bus;
- every agenix secret with `owner = "olafkfreund"` (`modules/secrets/api-keys.nix`) or
  `group = "users"`, such as the agent-bus admin token (`api-keys.nix:161`).

Today the walls are built per tool. `agent-review` (#2748, `home/development/agent-review.sh`)
puts delegated Codex reviews in bubblewrap. #2757 (intent approved, spec in draft) will do the
same for `codex-implement` and `agy-implement`. Each wall is one more launcher to get right,
and its evidence table shows how easily a tool's own sandbox leaves secrets readable. Nothing
covers the interactive Claude Code session, which reads the same files and holds the same sudo.

A separate Unix user would draw the line once, in the kernel, for every tool: no sudo, no Nix
trust, no owner home, only the worktrees it is given.

## Proposed outcome

- An agent process cannot read the owner's SSH keys, `gh` token, `nix.conf` tokens, other
  tools' logins, or agenix secrets it was not granted, whichever tool it is and however it
  was started. A `test -r` probe like #2757's proves it.
- It cannot run `sudo`, and the Nix daemon treats it as untrusted.
- It can still edit a task worktree, build and test with `nix build` as an untrusted user,
  and use its own subscription login.
- Deploys, pushes the owner signs for, and anything that needs root stay with the owner.
- The everyday workflow (herdr panes, the agent bus, hooks, skills) still works, or each
  thing that stops working is listed and accepted by the owner before the spec.

## What a separate user would have to reach

Found by reading the repo, 2026-11-07. This is the size of the change, not the design.

| Need | Where it lives today | What breaks under a second user |
| ---- | -------------------- | ------------------------------- |
| Launchers | `herdr-run`, `agent-run`, `agent-review` (`home/development/agent-run.nix`), `claude()` wrapper in `home/development/herdr.nix` | All are home-manager packages for `olafkfreund`. `agent-run.sh:28` finds the shared checkout through `$HOME`, so under another user that guard compares against the wrong path |
| herdr panes | herdr socket and state in the owner's home (`HERDR_SOCKET_PATH`, `herdr.nix:19`) | Another user cannot reach the socket. Agents either leave herdr or herdr runs as the agent user |
| Claude login | `~/.claude/.credentials.json`, never synced (`home/syncthing-stignore.nix:92`) but present in the local `~/.claude` | Needs a fresh `/login` per host under the new user |
| Claude config, skills, agents | `~/.claude`, synced by Syncthing as `olafkfreund` (`modules/services/syncthing.nix:116`) | The agent user needs a copy. A second Syncthing folder or a group-readable share; both have the store-symlink trap Syncthing already has |
| agy login | `~/.gemini/oauth_creds.json`, never synced (`syncthing-stignore.nix:119`) | Fresh login per host |
| Codex login | `~/.codex/auth.json`, per host, written by Codex itself (`home/development/codex-cli/module.nix:128`) | Needs its own login under the new user; the codex HM module is per user |
| Managed policy and guards | `/etc/claude-code/managed-settings.json` and its hooks (`modules/programs/claude-code-managed.nix`) | System-wide, so it applies. Hooks that read `$HOME/.local/state` (agent-team mode, line 45) would read the agent's home instead |
| Agent bus | MCP wrapper reads `agent-bus-matrix-token`, `0640 root:users` (`api-keys.nix:161`), read by the MCP wrapper (`claude-code-mcp.nix:331`) and by the managed Stop hook (`claude-code-managed.nix:533`) | The agent user needs that group or its own token, in both places. `users` also grants every other `users`-readable secret and polkit's power actions (`modules/security/default.nix:27`) |
| Other MCP servers | GitHub, LinkedIn, Atlassian tokens, `owner = "olafkfreund"` (`claude-code-mcp.nix:162`) | Lost unless re-granted. Each re-grant is a decision about what agents may hold |
| Repo and worktrees | `~/.config/nixos` (that is `/etc/nixos`) and `~/.config/nixos-<issue>`; the home is mode 700 | Another UID cannot traverse the home at all. A linked worktree also writes objects and refs into the common `~/.config/nixos/.git`, so worktree access alone does not give working git, and that git dir is the shared checkout's |
| Git push and `gh` | owner's `gh` login in the keyring and `~/.config/gh` | Pushing branches and opening PRs move to the owner, or the agent gets its own GitHub identity |
| Desktop tools | ai-mirror, agent-say audio, notifications, `wl-paste` | All need the owner's Wayland and PipeWire session, which another user cannot reach |
| Users in Nix | `hostUsers` in `flake.nix:375`, `Users/olafkfreund/`, `allUsers` in `secrets.nix:13` | A system user is simple. A full HM user means a new `Users/<name>/`, which this repo treats as a person |

## Affected users and systems

- Hosts: p620 and razer. p510 only with the owner's agreement.
- The owner's daily workflow: the interactive Claude Code session, herdr, `codex-implement`,
  `agy-implement`, `agent-review`, the agent bus.
- Modules: `modules/programs/claude-code-managed.nix`, `modules/secrets/api-keys.nix`,
  `modules/services/syncthing.nix`, `home/development/*`, `flake.nix`, `secrets.nix`.

## Constraints

- Subscription logins only, for every tool. No API keys (#1831).
- Deploys, `nhs`, switches, garbage collection and reboots stay with the owner. The agent
  user never gets sudo or Nix trust, not even for one command.
- p510 is not built, deployed or changed without the owner's agreement.
- Secrets still load at runtime only. A secret granted to the agent user is named and justified
  one by one; no blanket group.
- The shared checkout `~/.config/nixos` must not become writable by the agent user.
- Nothing here weakens #2757, #2758 or #2759, and none of them waits on this.

## Open questions

1. **Replace, complement or wait for #2757, #2758 and #2759?** Recommendation: complement,
   and **wait**. #2758 and #2759 take away Nix trust and passwordless sudo from the owner's
   account, which removes the two root paths for every agent at once; a second user adds
   nothing there. #2757 closes the home and secret reads for the implementers with one
   launcher. What would be left for this issue is the interactive Claude Code session.
   Recommendation: do not start this until all three have shipped, then reopen it only if a
   probe shows that the interactive session still reads something it should not.
2. **Which agents would move?** Recommendation, if it goes ahead: the headless implementers
   and reviewers only. Moving the interactive Claude Code session loses ai-mirror, agent-say,
   `wl-paste`, herdr integration and the deploys it runs for the owner today. Those losses look
   larger than the gain once #2758 and #2759 are done. That leaves a gap: #2757 already
   covers the headless tools, so a second user for them buys little beyond defence in depth.
   That is the main reason for the overall recommendation below.
3. **How would agents reach worktrees and their git metadata?** Candidates for the spec: a
   shared group with setgid worktrees, a separate clone per agent, or bind mounts into a
   per-run namespace. Recommendation: leave the choice to the spec, with the requirement that
   git works and the shared checkout's `.git` stays out of the agent's write reach.
4. **Who pushes and opens PRs?** Recommendation: the owner's session, after review. An agent
   GitHub identity is one more credential to guard.
5. **How do skills and config reach the agent user?** Recommendation: read-only, and only the
   synced allowlist (`CLAUDE.md`, `skills`, `commands`, `agents`, `plugins`), never the whole
   directory: the local `~/.claude` holds `.credentials.json`. Not a second Syncthing folder.
6. **The agent bus.** Recommendation: a token of its own for the agent user, not membership
   of `users`, which also carries polkit's power actions.

**Recommendation overall: do this later, if at all.** The owner-level fixes in
issues #2758 and #2759, and the sandbox in #2757, cover most of the risk at a fraction of the cost. A second
user touches logins on every host, Syncthing, herdr, the bus, GitHub access and the desktop
tools at once. Keep the issue open, and revisit it when those three have shipped.

## Owner decisions, 2026-11-07

The owner accepted every recommendation: this complements #2757, #2758 and #2759, and waits. No
agents move for now, and the owner keeps pushing and opening PRs. The agent user, if it comes, gets
its own bus token, not `users` membership. No spec is written until those three have shipped and a
probe shows the interactive session can still read what it should not.
