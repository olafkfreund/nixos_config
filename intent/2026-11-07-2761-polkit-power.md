# Intent: require auth for power actions by the users group (polkit)

Split out of issue 2759 (passwordless sudo), by the owner's decision on its intent.

## Problem

`modules/security/default.nix` (lines 24-41) adds a polkit rule: any member of `users` may use
`org.freedesktop.login1.reboot`, `reboot-multiple-sessions`, `power-off` and `power-off-multiple-sessions`
with `polkit.Result.YES`, whoever and wherever the caller is. Every agent runs as `olafkfreund`, who is in
`users`, so an agent can power-cycle a host. The Claude Code guard hooks match words in command text and do not
stop a determined caller.

The module is imported by `modules/core.nix`, which `hosts/templates/desktop.nix` imports, so the rule is live on
p620, razer and p510. It is the first `addRule` in `/etc/polkit-1/rules.d/10-nixos.rules` on p620 today.

### What the rule adds over systemd's defaults

systemd 262's `org.freedesktop.login1.policy` on p620, read from `/run/current-system/sw/share/polkit-1/actions`:

| Action | any | inactive | active |
| ------ | --- | -------- | ------ |
| `reboot`, `power-off` and both `-multiple-sessions` | auth_admin_keep | auth_admin_keep | yes |
| `suspend`, `hibernate` and both `-multiple-sessions` | auth_admin_keep | auth_admin_keep | yes |
| `halt`, `*-ignore-inhibit` | auth_admin_keep | auth_admin_keep | auth_admin_keep |

So a process in the active local session may already reboot or power off with no rule at all. The rule adds
only callers that are **not** in an active local session: an SSH login (a remote session, `subject.local` is
false), an inactive session (a second seat or a switched-away VT), and processes with no session.
`subject.local && subject.active` would therefore give the same result as deleting the rule.

### An agent on the owner's desktop counts as the active local session

Measured on p620, read-only, with `pkcheck` from an agent's shell (it asks polkit, it performs nothing):

- the agent's process lives in `user@1000.service/app.slice/app-graphical.slice/kitty-….scope`, not in a session
  scope;
- polkit resolves it through the user's display session (`loginctl show-user`: `Display=29`, the seat0 Omarchy
  session, active);
- `pkcheck` authorises `reboot`, `power-off`, `reboot-multiple-sessions` **and `suspend`**, which the rule does
  not mention: that grant comes from `allow_active=yes`;
- `halt` and `power-off-ignore-inhibit` are refused (exit 2), as the table says.

So removing or narrowing the rule does **not** stop an agent that runs inside the owner's graphical session
(kitty, herdr and tmux panes started from it). polkit sees the same uid in the same active session as the owner,
and cannot tell them apart. It does stop an agent that reaches a host over SSH: razer from p620, p510 from
either, or any `ssh host systemctl …` an agent runs. Issue 2760 (a separate agent user), which would have
separated them, was closed as not planned.

### What relies on the rule

Nothing found needs the remote or inactive grant:

- **Omarchy power menu and bar buttons.** `omarchy-system reboot|shutdown` runs `systemctl reboot --no-wall` /
  `systemctl poweroff --no-wall` from inside the session, so the defaults already allow it.
- **razer lid and idle.** `hosts/razer/nixos/laptop.nix:44-47` sets `HandleLidSwitch` in logind; logind acts on
  the lid itself, without polkit. Idle suspend uses `suspend`, which the rule does not cover.
- **Unattended jobs.** `system.autoUpgrade.allowReboot = false` (`modules/nix/nix.nix:16`), and p510 turns
  auto-upgrade off. The p510 hardware watchdog (`hosts/p510/nixos/resilience.nix`) is the kernel and PID 1.
  Root callers do not go through this rule. `scripts/update-commit-deploy.sh` tells the owner to run
  `sudo systemctl reboot`, which is sudo, not polkit. No user timer or user service in the repo calls a power
  action.
- **p510 autologin and Sunshine.** The autologin Omarchy session is the active local session on seat0, and a
  Sunshine stream drives that session, so the power menu keeps working there without the rule.
  `modules/desktop/sunshine.nix` issues no power action.

## Proposed outcome

- A user that is not in the active local session of a host cannot reboot or power it off without the owner's
  authentication. In practice: an agent on p620 can no longer power-cycle razer or p510 over SSH, and an SSH
  login to p620 cannot power-cycle p620.
- The owner's Omarchy power menu, bar buttons, lid and idle handling behave exactly as today, with no new prompt.
- Unattended reboots (watchdog, root jobs) behave as today.
- The intent says plainly that this does not stop an agent inside the owner's own desktop session, and the
  owner decides whether to go further (open question 1).

## Affected users and systems

- Hosts: p620 and razer. p510 only with the owner's agreement; it inherits the rule through
  `modules/core.nix`, so leaving it unchanged needs an explicit p510 override.
- Module: `modules/security/default.nix`.
- People: the owner, who loses passwordless power actions over SSH; every agent, which loses them over SSH.

## Constraints

- The owner's power menu and bar buttons must keep working with no extra prompt (unless the owner chooses
  option C below).
- Unattended reboots and power-offs must keep working.
- No lockout of a remote host: power actions over SSH must still be possible for the owner, through `sudo` with
  a password (issue 2759) or by answering a polkit prompt.
- p510 is changed only with the owner's agreement, and never built or deployed by an agent.
- Must not touch the other rules in the same file or in `10-nixos.rules` (nh's `pkexec`, libvirt, NetworkManager,
  CUPS, fwupd).

## Open questions

1. **How far to go.** Options:
   - A. Delete the rule and rely on systemd's defaults. Smallest change; result as in "Proposed outcome".
   - B. Keep it but add `subject.local && subject.active`. Same effect as A, with more code.
   - C. Require the owner's authentication for these actions even in the active session (`AUTH_ADMIN_KEEP`).
     This is the only option that stops an agent inside the desktop, but every menu reboot then prompts. It
     needs a polkit agent in the Omarchy session; nixarchy's `modules/nixos.nix:1835` says the rebuild "asks
     through the Omarchy polkit dialog", but I did not confirm one answers login1 actions.

   Recommendation: A now. C trades a prompt on every menu reboot for a threat (an agent in the owner's own
   session power-cycling the desk the owner is sitting at) that the owner notices at once; revisit it with
   issue 2760 if that is reopened.
2. **Suspend and hibernate.** They are not in the rule and are allowed to the active session by default, so an
   agent on the desktop can suspend p620 or razer today. Recommendation: out of scope; A changes nothing there.
3. **p510.** Change it with p620 and razer, or pin today's rule on p510 with a host override until the owner
   agrees? p510 is the one host where unattended operation matters, but nothing found needs the remote grant.
   Recommendation: pin it on p510 now, follow up when the owner schedules p510 (as issue 2759 did).
4. **Owner's remote power actions.** After A, the owner powers a remote host off over SSH with
   `sudo systemctl …` and a password (issue 2759). Recommendation: accept; no extra rule for SSH sessions.
