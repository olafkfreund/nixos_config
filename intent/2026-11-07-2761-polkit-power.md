# Intent: require auth for power actions by the users group (polkit)

Split out of issue 2759 (passwordless sudo), by the owner's decision on its intent.

## Problem

`modules/security/default.nix` (lines 24-41) adds a polkit rule: any member of `users` may use
`org.freedesktop.login1.reboot`, `reboot-multiple-sessions`, `power-off` and `power-off-multiple-sessions`
with `polkit.Result.YES`, whoever and wherever the caller is. Every agent runs as `olafkfreund`, who is in
`users`, so an agent can power-cycle a host. The Claude Code guard hooks match words in command text and do not
stop a determined caller.

The module is imported by `modules/core.nix`, which `hosts/templates/desktop.nix` imports, and
`lib/hostTypes.nix` builds every host from that template, so the rule is live on p620, razer and p510. It is the
first `addRule` in `/etc/polkit-1/rules.d/10-nixos.rules` on p620 today.

### What the rule adds over systemd's defaults

systemd 262's `org.freedesktop.login1.policy` on p620, read from `/run/current-system/sw/share/polkit-1/actions`:

| Action | any | inactive | active |
| ------ | --- | -------- | ------ |
| `reboot`, `power-off` and both `-multiple-sessions` | auth_admin_keep | auth_admin_keep | yes |
| `suspend`, `hibernate` and both `-multiple-sessions` | auth_admin_keep | auth_admin_keep | yes |
| `halt`, `*-ignore-inhibit` | auth_admin_keep | auth_admin_keep | auth_admin_keep |

"auth_admin" means an administrator's password; the live `addAdminRule` names `unix-group:wheel`, whose only
member is `olafkfreund`, so in practice it is the owner's password. logind picks which of these actions to check
from the request: `-multiple-sessions` when other users are logged in, `-ignore-inhibit` when an inhibitor lock
is overridden. The rule grants neither `-ignore-inhibit` action today.

So a caller that polkit sees as the active local session may already reboot or power off with no rule at all.
The rule adds callers that polkit does **not** see that way: a process in a remote session (an SSH login, where
`subject.local` is false), a process in an inactive session (a VT switched away from), and a process that has no
session of its own and whose user has no active display session to fall back to (below).
`subject.local && subject.active` would therefore give the same result as deleting the rule.

### Most agents count as the active local session

Measured on p620, read-only, with `pkcheck` from an agent's shell (it asks polkit, it performs nothing):

- the agent's process lives in `user@1000.service/app.slice/app-graphical.slice/kitty-….scope`, not in a session
  scope;
- polkit resolves it through the user's display session (`loginctl show-user`: `Display=29`, the seat0 Omarchy
  session, active);
- `pkcheck` authorises `reboot`, `power-off`, `reboot-multiple-sessions` **and `suspend`**, which the rule does
  not mention: that grant comes from `allow_active=yes`;
- `halt` and `power-off-ignore-inhibit` exit 2: authentication is needed and no interaction was allowed.

Two consequences:

1. Removing or narrowing the rule does **not** stop an agent inside the owner's graphical session (kitty, herdr
   and tmux panes started from it). polkit sees the same uid as the owner, resolved to the same active session.
2. It does not reliably stop an agent over SSH either. A plain `ssh host systemctl …` runs in a remote session
   and would need authentication, but the same caller can start the command in its own user manager
   (`systemd-run --user …`). That process has no session of its own, sits in `user@1000.service` exactly like
   the measured process above, and is resolved to the display session whenever the owner has an active
   graphical login on that host: p620 while the owner is at it, razer while it is logged in, and p510 always,
   because p510 logs in automatically. The SSH case was reasoned from the p620 measurement, not run.

And while issue 2759 has not shipped, `sudo` without a password is a second path to the same end on every host.

Issue 2760 (a separate agent user), which would let polkit tell agents from the owner, was closed as not planned.

### What relies on the rule

A repo-wide search for login1 actions and `systemctl`/`loginctl` power commands found nothing that needs the
remote or inactive grant:

- **Omarchy power menu and bar buttons.** `omarchy-system reboot|shutdown` runs `systemctl reboot --no-wall` /
  `systemctl poweroff --no-wall` from inside the session, so the defaults already allow it.
- **razer lid and idle.** `hosts/razer/nixos/laptop.nix:44-47` sets `HandleLidSwitch` in logind; logind acts on
  the lid itself, without polkit. Idle suspend uses `suspend`, which the rule does not cover.
- **Unattended jobs.** `system.autoUpgrade.allowReboot = false` (`modules/nix/nix.nix:16`), and p510 turns
  auto-upgrade off (`hosts/p510/configuration.nix:547`). The p510 hardware watchdog
  (`hosts/p510/nixos/resilience.nix`) is the kernel and PID 1. Root callers do not go through this rule.
  `scripts/update-commit-deploy.sh` tells the owner to run `sudo systemctl reboot`, which is sudo, not polkit.
  No user timer or user service in the repo calls a power action.
- **p510 autologin and Sunshine.** The autologin Omarchy session is the active local session on seat0, and a
  Sunshine stream drives that session, so the power menu keeps working there without the rule.
  `modules/desktop/sunshine.nix` issues no power action.

## Proposed outcome

What is true when this is done depends on open question 1. Either way:

- The owner's power menu, bar buttons, lid and idle handling keep working, with at most a password prompt that
  the owner chose.
- Unattended reboots (watchdog, root jobs) behave as today.
- The intent and the eventual PR state plainly what an agent can still do afterwards, so nobody reads this as
  "agents cannot power-cycle a host" unless it is true.

## Affected users and systems

- Hosts: p620 and razer. p510 only with the owner's agreement; it inherits the rule through
  `modules/core.nix`, so leaving it unchanged needs an explicit p510 override.
- Module: `modules/security/default.nix`.
- People: the owner, who loses passwordless power actions over SSH and, under option C, from the menu; every
  agent running as the owner.

## Constraints

- The owner's power menu and bar buttons must keep working.
- Unattended reboots and power-offs must keep working.
- No lockout of a remote host: power actions over SSH must still be possible for the owner, through `sudo` with
  a password (issue 2759) or by answering a polkit prompt.
- p510 is changed only with the owner's agreement, and never built or deployed by an agent.
- Must not touch the other rules in the same file or in `10-nixos.rules` (nh's `pkexec`, libvirt, NetworkManager,
  CUPS, fwupd).
- Only stops an agent together with issue 2759; on its own, passwordless `sudo` still powers any host off.

## Open questions

1. **How far to go.** Options:
   - A. Delete the rule and rely on systemd's defaults. Smallest change, no new prompt. It stops only the plain
     `ssh host systemctl …` path; an agent can still reach the display session with `systemd-run --user`, and
     an agent on the desktop is untouched. Hygiene, not a barrier.
   - B. Keep it but add `subject.local && subject.active`. Same effect as A, with more code.
   - C. Return `AUTH_ADMIN_KEEP` for `reboot`, `power-off` and their `-multiple-sessions` actions for every
     non-root caller, active session included. This is the only option that makes an agent need the owner's
     password, wherever it runs. Costs: every menu reboot or power-off asks for the password; "keep" lets a
     second request within a few minutes pass without asking, which matters little for an action that ends the
     session; it needs a polkit agent that answers login1 actions in the Omarchy session (nixarchy's
     `modules/nixos.nix:1835` says rebuilds ask "through the Omarchy polkit dialog", but I did not confirm it
     answers these actions, and `pgrep` found no standalone agent process); and with no agent registered (at a
     greeter, over SSH) the request fails rather than prompts.

   Recommendation: C on p620 and razer, if the spec confirms the Omarchy dialog answers login1 actions;
   otherwise A, stated as hygiene. A alone does not meet the issue's aim.
2. **Suspend and hibernate.** Not in the rule; the active session (and so any agent on the desktop) may use them
   by default. Recommendation: include them in C only if the owner wants a prompt on suspend too; razer's lid
   and idle suspend go through logind and hypridle, and idle suspend would then prompt. Default: leave them out.
3. **p510.** Change it with p620 and razer, or pin today's rule on p510 with a host override until the owner
   agrees? Under C, p510's menu would prompt inside the Sunshine stream, and nobody is there to answer an
   unattended request; root jobs are unaffected. Recommendation: pin today's rule on p510 now and follow up when
   the owner schedules p510 (as issue 2759 did).
4. **Owner's remote power actions.** After A or C, the owner powers a remote host off over SSH with
   `sudo systemctl …` and a password (issue 2759). Recommendation: accept; no extra rule for SSH sessions.
