# Intent: herdr-run writes the caller's environment to a file

## Problem

`herdr-run` (`home/development/herdr-run.sh`, packaged in `home/development/agent-run.nix:4-13`)
runs a Codex or agy command in a new herdr tab, the `↳` row. To make the command behave as if
it ran in the caller's shell, it copies the caller's whole exported environment into a file
and the pane sources it:

- `:95-96` creates a private directory with `mktemp -d` (`/tmp`, because `TMPDIR` is unset
  in a Claude Code session) and sets it to `0700`.
- `:114-125` writes one `declare -p` per exported variable to `$dir/env`. Only names that are not
  identifiers, shell internals and read-only names are skipped (`:121-123`). No credential
  is filtered out.
- `:195` runs the command as `env -i bash -c 'source "$0/env" …; exec "$@"'`, so the
  command gets back the caller's exported environment, apart from those exclusions.
- `:220` and `:261-265` write `$dir/run` with the caller's `PATH` and every argument of the
  command. After the rename at `:265` it is `0600` under the session umask. The pane runs it
  as `bash <path>` (`:271`).

What lands on disk, checked by name only (values never printed): in a Claude Code session on
p620 the environment holds literal credentials in `CACHIX_AUTH_TOKEN`,
`CLAUDE_CODE_MESSAGING_TOKEN`, `DAILY_DEV_TOKEN`, `GITHUB_API_TOKEN`, `OLLAMA_API_KEY` and
`SYNECHRON_GITHUB_API_TOKEN`. The `*_API_KEY_FILE` variables hold paths, not keys. Those come
from `modules/secrets/api-keys.nix`. `SSH_AUTH_SOCK` passes too, which is a capability
rather than a value.

Who can read it, and for how long:

- **Mode.** The directory is `0700`. The session umask is `0077`, so `env` is `0600`. The script sets no umask
  of its own, so the file mode follows the caller's, but the `0700` directory keeps other
  users out either way.
  Other users cannot read it. Root and any process running as `olafkfreund` can.
- **Medium.** `/tmp` is on the ext4 root on p620 and razer (`useTmpfs = false`,
  `hosts/p620/nixos/boot.nix:32`, `hosts/razer/nixos/memory.nix:29`). The tokens are written
  to a persistent disk, not to memory.
- **Lifetime.** The file lives for the whole run and a few seconds after (`:313-320`). A
  review is bounded by its `timeout` (600 or 900 s), agy in `agent-run` by
  `--print-timeout 20m` (`agent-run.sh:44`). The Codex implementer (`agent-run.sh:49`) has
  no bound, and `herdr-run` waits as long as the pane and runner live (`:300-311`). It is
  removed by the helper's `EXIT` trap (`:58`), by `headless` (`:82`), or by the runner if the
  helper is gone (`:185`). If those paths do not run, for example the helper is killed with
  `SIGKILL` before the runner starts, or both are, or the host loses power, it stays until the
  next boot (`cleanOnBoot = true`). A deleted file's blocks are not scrubbed either.
- **Now.** A read-only search of `/tmp` and `/run/user/1000` found no leftover
  directory holding both `env` and `run`. Nothing needs cleaning up today.

What the command sees: about the same environment it would see without herdr, because the
headless path is `exec "$@"` (`:11`, `:83`). So the pane adds no new reader inside the run.
The new exposure is the copy on disk and its lifetime. Every caller is affected:
`agent-run` (`agent-run.sh:44,49`) and the `second-opinion` skill
(`claude-code-skills/second-opinion/SKILL.md:92,145,157,188`). Only the Codex reviews go
through `agent-review`, whose `--clearenv` (`agent-review.sh:139-144`) gives the tool a fixed
set of variables and none of the caller's. The file is still written before it starts. Both
agy review paths (`SKILL.md:157-159,188-190`) run `agy` directly after removing only three
`GEMINI`/`GOOGLE` names, so agy holds the six credentials above, in a pane or headless.

Other places the same run writes or shows data, in scope only as far as the spec decides:

- `run` holds every argument. The agy paths pass the whole prompt in argv
  (`SKILL.md:159,190`, `agent-run.sh:44`), so a credential pasted into a prompt lands there,
  and in `/proc/<pid>/cmdline`.
- The runner writes stdout and stderr to `out` and `err` and tails both into the pane
  (`:192,197,214`), so a credential the tool prints reaches files and the pane's scrollback.
- The pane receives only `bash <path>/run` (`:271`), so this code puts neither the
  environment nor the prompt into the pane's shell history.
- The helper and runner themselves still hold the caller's environment in
  `/proc/<pid>/environ` for the run, readable by the same user.

Two side effects of copying everything:

- The caller's `HERDR_PANE_ID` replaces the `↳` pane's own. A herdr hook in the child, such
  as `claude-code-managed.nix:609-647`, would report against the lead's pane. Not tested.
- Whatever the caller had set, the child has, whether or not the command needs it.

The approved spec of #2757 (section 7) gives the implementers `env -i` with an allow-list:
`PATH` (filtered), `HOME`, `LANG`, `TERM`, `TMPDIR`, `SSL_CERT_FILE`, `NIX_REMOTE`,
`NIX_CONFIG`, plus `CODEX_CODER`, or `AGY_CODER`, `AGY_WORKTREE` and `AGY_GUARD_LOG`. It
names this file as out of its scope (its "Risks", the `herdr-run` row), and its open
question 3 names this issue.

## Proposed outcome

- `herdr-run` writes no variable to disk that is not on an allow-list, or no environment at
  all. An allow-list limits names, not values: an allowed variable or a prompt could still
  carry a secret, and that stays the caller's job.
- The command in a `↳` pane gets the variables it needs: `PATH`, `HOME`, `TERM`, `LANG`,
  `XDG_RUNTIME_DIR`, `XDG_CACHE_HOME` (`agy-implement` keeps its probe cache there,
  `antigravity-config.nix:163`), `AGY_GUARD_LOG` and `AGY_IMPLEMENT_PROBING`, and whatever
  `codex`, `agy`, `timeout`, `env -u`, `agent-review` and `agy-guard-probe` need to start.
  `CODEX_CODER`, `AGY_CODER` and `AGY_WORKTREE` are set by the launchers themselves
  (`codex-cli.nix:28`, `antigravity-config.nix:197`), so they need not be inherited. The spec
  settles the exact list.
- A test in `herdr-run-test.sh` fails if a variable outside the allow-list reaches `env`
  or the command.
- `agent-run`, both `second-opinion` paths, the headless fallback and the `↳` rows work as
  they do today.

## Affected users and systems

- Files: `home/development/herdr-run.sh`, `home/development/herdr-run-test.sh`, possibly
  `agent-run.sh` and `second-opinion/SKILL.md` if a caller has to pass a variable
  explicitly.
- Hosts: p620 and razer, where herdr and the agents run. p510 has claude-code, but is not
  built or deployed without asking.
- Agents: every Codex and agy run started from Claude inside herdr.

## Constraints

- `agent-run`, the `↳` rows, `place_tab`, `report-agent`, the lost-run detection and the
  stdin FIFO (#2679) keep working. The existing `herdr-run-test.sh` cases still
  pass, except where they assert that any variable arrives: `multiline-env` (`:296-303`)
  exports an arbitrary name, and several cases pass `TEST_STATE` to the command
  (`:119,143,201`). Those cases change to use an allowed name or a test-only allowance.
- Outside herdr, behaviour is unchanged: `exec "$@"` with the caller's environment.
- Must not weaken #2757: its allow-list stays the inner boundary for implementers, and
  `CODEX_CODER`/`AGY_CODER` still reach the guards (both guards allow everything without
  them).
- Reuse #2757's list as the base where the two overlap. They guard different stages, so
  `herdr-run`'s list may be wider; the spec says where they differ and why.
- No secret value is printed in tests, logs or the PR. Checks use names only.
- `writeShellApplication`'s minimal bash: no `compgen` (memory, `:118`).

## Open questions

1. **Land inside #2757, or on its own?** Recommendation: on its own, but after #2757's
   `agent-sandbox.sh` exists, and reuse its allow-list. #2757's spec is approved without
   this. Folding it in would reopen that spec. Separately it is a small change to one script
   and its test.
2. **Allow-list or nothing?** (a) Write only allow-listed names to `env`. (b) Write no
   environment, and let the pane run with herdr's own environment plus a few names passed
   on the command line. Recommendation: (a). It keeps the pane and headless runs alike, and
   (b) gives the child herdr's environment, which is a second unknown set.
3. **Same list as #2757, or a wider one?** `herdr-run` also runs reviews and arbitrary
   commands (`timeout`, `env -u …`), not only implementers. Recommendation: #2757's list
   plus `XDG_RUNTIME_DIR`, `XDG_CACHE_HOME`, `USER`, `LOGNAME`, `SHELL`,
   `AGY_IMPLEMENT_PROBING`, and nothing
   with `TOKEN`, `KEY`, `SECRET` or `PASSWORD` in the name. The spec checks this against
   what each caller reads.
4. **Should `HERDR_*` pass?** Recommendation: pass none of the caller's. The child is in its
   own pane, and `herdr-run` reports its state itself.
5. **Should `SSH_AUTH_SOCK` pass?** It lets the child sign with the agent's keys. Recommendation:
   no, unless a caller needs it. Implementers do not push.
6. **Should the headless path filter too?** It hands the command the full environment
   today. Recommendation: no, to keep this issue small. For implementers #2757 covers it, and
   for Codex reviews `agent-review` does. That leaves the agy reviews in `second-opinion`
   with the six credentials in their environment, in a pane or not; the owner decides whether
   that is a follow-up issue.

## Owner decisions, 2026-11-07

The owner accepted every recommendation:

1. This lands on its own, after #2757's `agent-sandbox.sh` exists, and reuses its allow-list.
2. The env file holds only allowed variables.
3. The list is #2757's, plus `XDG_RUNTIME_DIR`, `XDG_CACHE_HOME`, `USER`, `LOGNAME`, `SHELL` and
   `AGY_IMPLEMENT_PROBING`.
4. The caller's `HERDR_*` variables are not passed.
5. `SSH_AUTH_SOCK` is not passed.
6. The headless path stays as it is. The agy review paths in the second-opinion skill move to
   `env -i` with the same list in this issue, rather than a follow-up.
