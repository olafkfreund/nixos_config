# Intent: the Herdr desktop app and herdr-core (hc) on p620 and razer

## Problem

We only run the Herdr **TUI** (`herdr 0.9.5`, flake input
`github:ogulcancelik/herdr`, installed by `Users/olafkfreund/profile.nix:205`).
The owner wants the Herdr **desktop app** on p620 and razer, and wants to
start using **herdr-core** (`hc`), the headless runtime the app is built on.
Neither is packaged here.

The TUI and herdr-core are separate. herdr.dev says the TUI "has its own
server" and the two "don't share agents", so this adds a second runtime
next to the TUI; it does not upgrade the TUI.

Upstream only offers `curl … | sh` installers that write into `~/.local`,
and the app updates itself. That doesn't fit a declarative fleet.

Facts, checked on 2026-11-11 from the release manifests and the release
binaries (`readelf`, `strings`; neither was run):

- Both are Apache-2.0 (GitHub repo metadata). They ship from
  `releases.herdr.dev` as tarballs, each pinned by a sha256 in a JSON
  manifest (`app/latest.json`, `core/latest.json`). There are no GitHub
  releases.
  - app `0.1.15`, needs core >= `0.1.11`
  - core `0.1.20`
- **Core:** a static-pie binary (no interpreter, no `NEEDED`). It detects
  a package-manager install and won't update itself ("The package manager
  this hc came from (homebrew, nix, mise, …): it updates hc, `hc update`
  won't"). It starts its server on demand through `systemd-run --user`,
  and it tries to turn on systemd user **linger** for the user by itself
  (`busctl … enable-linger`; "hc: turned on linger for …, so the core
  outlives your logins"). Neither p620 nor razer has an `hc` command today.
- **App:** a dynamically linked GPUI/wgpu GUI binary. NEEDED: `libxcb`,
  `libxkbcommon`, `libgcc_s`. It loads `libvulkan`, `libEGL`,
  `libwayland-client`, `libwayland-egl` and `libxkbcommon-x11` at runtime.
  It runs `curl` as a subprocess (updates, telemetry, release notes), and
  `paplay` / `pw-play` / `ffplay` / `mpg123` / `mpv` for sounds.
  - It starts the core itself (`herdr-core connect`), so no server has to
    run beforehand. It looks for the core in its settings,
    `HERDR_CORE_DIRS`, `PATH`, the login shell's `PATH`, `~/.local/bin`,
    Homebrew, mise, `/run/current-system/sw/bin`, `~/.nix-profile/bin` and
    `~/.cargo/bin`.
  - It respects a Nix-managed **core** ("Managed by nix: update it
    there"), but has **no** such check for **itself**. It checks for
    updates every hour, and on a release build it downloads, stages and
    tries to replace its own binary. Its `settings.json` has no key to turn
    updates off.
  - It reports telemetry daily to `telemetry.herdr.dev`, "on when
    absent". `DO_NOT_TRACK=1` or `HERDR_TELEMETRY=0` turns it off for a
    run; `telemetry: false` in `~/.config/herdr-app/settings.json` turns it
    off and deletes unsent reports. herdr-core sends none.
  - It writes `~/.config/herdr-app/settings.json` live from its settings
    UI, so that file must stay writable.
- **Coexistence:** the paths (`~/.config/herdr-app`, `~/.config/herdr-core`
  vs the TUI's `~/.config/herdr`) and environment variables (`HC_*` vs the
  TUI's `HERDR_ENV` / `HERDR_SOCKET_PATH`) don't overlap, so the `claude()`
  launcher in `home/development/herdr.nix:27-35` won't route an `hc`
  terminal to `herdr-claude-teams`.
- **Skills:** both binaries ship agent skills: `hc --skill` ("hc manual")
  and `herdr-app --skill` ("drive the person's window"). The TUI's skill
  already owns `.claude/skills/herdr` and `.agents/skills/herdr`
  (`home/development/herdr.nix:41-44`).

## Proposed outcome

- On p620 and razer, `herdr-app` starts from the launcher with **no core
  running**, starts the Nix-installed `herdr-core`, and opens a working
  terminal. It runs as a native Wayland window with usable rendering on
  both hosts, including razer's hybrid Intel/NVIDIA setup, without
  changing the fleet's GPU offload policy.
- Closing and reopening the window keeps its terminals, and `hc ls` /
  `hc attach` / `hc read` from a shell see the same terminals.
- `herdr-core` and `hc` are on `PATH`. Agents get the `hc` and `herdr-app`
  skills under their own names, next to the TUI's `herdr` skill, not in
  place of it.
- Both come from Nix with pinned versions and hashes. Neither downloads,
  stages, installs or selects an unmanaged copy of itself or of the other,
  and the app doesn't nag or error because it can't update. When versions
  don't match, the message points at a Nix bump.
- Telemetry is off from the first launch, from the launcher and from a
  shell, and the app's own settings stay writable.
- The Herdr TUI, its skill, its config and `herdr-team` work as before.
- A bump is a documented version + hash change per package (they version
  separately), plus a check that the app still accepts the core.

## Constraints

- Packages go in `pkgs/` (or a flake input), with explicit imports only.
  No `curl | sh`, and no writes into `~/.local/bin`.
- Prebuilt binaries are pinned by sha256 from the upstream manifest.
- No app or core self-update may take effect. A rebuild that changes the
  installed core while an older core server is running must not kill
  running terminals without warning.
- User linger stays a deliberate setting, not something `hc` flips on its
  own (see open question 5).
- No secrets involved. Telemetry is off.
- razer builds on p620 (`just deploy-via-p620 razer`). Announce on the
  agent bus before deploying either host.
- The upstream versions are 0.1.x and move fast: expect frequent bumps.

## Open questions

1. Package as our own `pkgs/` derivations, or as a small flake of our own
   like `nix-craftapps`? Proposed: `pkgs/`, like the other fast-moving
   prebuilt apps in the profile (`okena`, another GPUI app, is a
   reference). Both reviewers agree.
2. Start `hc` on demand, or as a systemd user service? Proposed: on
   demand. The app starts it itself, and `hc` already runs its own
   `systemd-run --user` unit, which a Nix-managed service would fight.
3. Install it under the `hc` name? Proposed: yes, next to `herdr-core`.
   Neither host has herbstluftwm, and the upstream docs and skills
   hard-code `hc`.
4. Turn telemetry off? Proposed: yes, through the app's launch environment,
   so its `settings.json` stays writable.
5. Linger: `hc` turns on systemd user linger by itself, so the core and
   its agents keep running after you log out. Allow that (declare
   `users.users.olafkfreund.linger = true` on p620 and razer), or keep
   linger off, which means the core stops at the last logout? Proposed:
   declare linger on, since long-running agents are the point of `hc`.
   This is your call.
