# Intent: the Herdr desktop app and herdr-core (hc) on p620 and razer

## Problem

We only run the Herdr **TUI** (`herdr 0.9.5`, flake input
`github:ogulcancelik/herdr`, installed by `Users/olafkfreund/profile.nix:205`).
The owner wants the Herdr **desktop app** on p620 and razer, and wants to
start using **herdr-core** (`hc`), the headless runtime the app is built on.
Neither is packaged here.

The TUI and herdr-core are separate. herdr.dev says the TUI "has its own
server" and the two "don't share agents", so this adds a second runtime
next to the TUI; it does not upgrade the TUI.

Upstream only offers `curl … | sh` installers that write into `~/.local`
and update themselves. That doesn't fit a declarative fleet.

Facts checked on 2026-11-11:

- Both are Apache-2.0. They ship from `releases.herdr.dev` as tarballs,
  each pinned by a sha256 in a JSON manifest (`app/latest.json`,
  `core/latest.json`). There are no GitHub releases.
  - app `0.1.15`, needs core >= `0.1.11`
  - core `0.1.20`
- `herdr-core` is a static-pie binary. The upstream installer adds an `hc`
  beside it only if no `hc` exists (herbstluftwm ships one; neither host
  has `hc` today).
- `hc` detects a Nix install and leaves updating to the package manager
  (its own text: "The package manager this hc came from (homebrew, nix,
  mise, …): it updates hc, `hc update` won't").
- `herdr-app` is a dynamically linked GUI binary: NEEDED `libxcb`,
  `libxkbcommon`, `libgcc_s`; it loads `libvulkan`, `libwayland-client`,
  `libwayland-egl` and `libxkbcommon-x11` at runtime.
- The app finds the core with `command -v herdr-core` (falling back to
  `~/.local/bin/herdr-core`), and has an in-app "Updating herdr-core" flow
  and its own `install.sh` update path.
- The app reads `HERDR_TELEMETRY` / `HERDR_TELEMETRY_URL`, so it reports
  telemetry by default.

## Proposed outcome

- On p620 and razer, `herdr-app` starts from the launcher (Omarchy menu /
  desktop entry) under Hyprland/Wayland, finds `herdr-core` on `PATH`, and
  opens a working terminal.
- `hc` and `herdr-core` are on `PATH`: `hc run`, `hc ls`, `hc attach`,
  `hc read` work from a shell, and `hc --skill` is available to agents the
  same way `herdr --skill` is today.
- Both come from Nix with pinned versions and hashes. Nothing lands in
  `~/.local/bin`, and neither the app nor `hc` replaces itself.
- Telemetry is off.
- The Herdr TUI and `herdr-team` keep working unchanged.
- Bumping a version is a documented one-line change (version + hash).

## Affected users and systems

- p620 and razer: the developer user profile (`Users/olafkfreund/profile.nix`,
  `home/development/herdr.nix`).
- Not p510.
- Agents: Claude Code, Codex and agy can use `hc` once it is on `PATH`.
  Moving `herdr-team` onto `hc` is #2859, not this task.

## Constraints

- Packages go in `pkgs/` (or a flake input), with explicit imports only.
  No `curl | sh`, and no writes into `~/.local/bin`.
- Prebuilt binaries are pinned by sha256 from the upstream manifest.
- The app must not update itself or the core in place, and must not fail
  noisily because it cannot.
- No secrets involved. Telemetry is off.
- razer builds on p620 (`just deploy-via-p620 razer`). Announce on the
  agent bus before deploying either host.
- The upstream versions are 0.1.x and move fast: expect frequent bumps.

## Open questions

1. Package as our own `pkgs/` derivations (like other prebuilt tarballs), or
   as a small flake of our own, like `nix-craftapps`? Proposed: `pkgs/`,
   because it is two derivations and one host profile.
2. Should `hc` be a plain command that starts its server on demand, or a
   systemd user service? Proposed: on demand, unless the spec finds that the
   app needs a running server.
3. Install `hc` under the `hc` name? Proposed: yes; neither host has
   herbstluftwm.
4. Telemetry off: proposed by default. Your call if you want to keep it.
