# Intent: Flux on p620 and razer

## Problem

Flux (olafkfreund/nixarchy-flux) links the desktop to the Android phone:

- files, clipboard and notifications
- calls and texts
- fingerprint approval
- Do Not Disturb sync

**Neither host has Flux declaratively.** On p620 an agent session runs a `fluxd` by hand: pid 2397965, `flux-core
0.19.1+dirty` from that session's scratchpad, in a terminal scope, holding TCP and UDP 12100 and
`$XDG_RUNTIME_DIR/flux/fluxd.sock`. The Pixel 11 Pro XL and the Tab S8 Ultra are paired with it. It stops at logout or
reboot, its build lacks nixarchy-flux#59, and razer has nothing.

The Nixi companion's phone feature (olafkfreund/nixi-nixarchy#231) talks to `fluxd` over that socket. It needs a
lasting `fluxd` with #59's call, approval and Do Not Disturb state. The owner wants Flux on both hosts, and the phone
feature tested live on p620.

## Proposed outcome

- p620 and razer run `fluxd` as a managed user service for `olafkfreund` from the Flux flake, built from master with
  nixarchy-flux#59.
- On p620 the hand-started `fluxd` is retired in a coordinated handover: announced on the agent bus, the owning session
  told, and the existing pairings kept, since they live in the user's Flux state.
- `flux-cli` is available, and Nixi's Phone switch shows "Connected: Pixel 11 Pro XL" on p620.
- On the home LAN the phone connects without new setup. Away from home, Tailscale needs a one-time manual step per
  desktop: the phone joins the tailnet, and its Tailscale name or IP is added as an extra address
  (nixarchy-flux `docs/tailscale.md`). That step is documented, not automated.

## Affected users and systems

- Hosts: p620 and razer. p510 is not affected. Both are shared agent hosts: p620 runs nixarchy CI runners, and razer
  keeps a linger session for `hc`.
- `flake.nix` and `flake.lock` (a new `flux` input), a service module under `modules/` enabled per host through the
  repo's feature flags (AGENTS.md non-negotiable 1), and the two host configs.
- The owner's phones: the Pixel is already paired, and Do Not Disturb set from the desktop (#59) needs the Android app
  from #59 or later.

## Constraints

- **Network exposure.** Both hosts run with the firewall off (`hosts/p620/configuration.nix:101`,
  `hosts/razer/configuration.nix:91`), so Flux's `openFirewall = false` changes nothing. `fluxd` listens on TCP
  12100–12108 and UDP 12100. razer roams on guest and corporate Wi-Fi, where those ports must not be reachable. The
  spec must close them on untrusted networks, through Flux's bind address or an interface-scoped rule. p620 sits on the
  trusted home LAN.
- **Avahi.** Flux's module turns on Avahi publishing. It must not undo p620's `allow-interfaces = [ "enp1s0" ]` pin
  (#2293, Docker bridges), or advertise razer on untrusted networks.
- **Service hardening.** Flux's user service has none of the protections AGENTS.md asks for, and `DynamicUser` or
  `ProtectHome` would break a desktop daemon that sends the user's files. The spec records an explicit, reasoned
  exception and applies what fits (`NoNewPrivileges`, for example).
- **No PAM change.** Fingerprint sudo approval stays off (`approve.services = [ ]`): it changes how sudo authenticates
  on a host where agents run sudo, and razer is NOPASSWD.
- **No webcam module** (`v4l2loopback`).
- **One owner of `fluxd.service`.** The NixOS module and the Home Manager module must not both define it.
- **Deploy** from `~/.config/nixos` on main after the PR merges, per AGENTS.md: bus check and announcement first, `just
  test-host` before switching. razer deploys via p620. Merge nixarchy-flux#59 first.

## Open questions

- Should the Omarchy shell plugin (Flux in the bar) and the browser extension also come? They need the Home Manager
  side of Flux. This draft says yes for the shell plugin and no for the browser extension, with the module split left
  to the spec.
- Should the Tab S8 Ultra stay paired to both hosts? Pairing is per desktop, so razer pairs separately by hand.
