# Intent: T3 Code follows the Omarchy theme declaratively

## Problem

T3 Code is enabled on p620 with `programs.nixarchy.apps.t3-code.enable`. It
does not follow the desktop theme on a fresh NixOS host.

On Arch, Omarchy's installer `omarchy-install-ai-t3-code` does four things
after installing the app (lines 70-82):

1. creates `~/.t3/userdata`;
2. runs `omarchy-theme-refresh` if the current theme has no generated
   `~/.local/state/omarchy/current/theme/t3code.json`;
3. publishes the current palette with `omarchy-theme-set-t3code`, which writes
   `~/.t3/userdata/themes/omarchy.json`;
4. selects that theme with `t3 theme set omarchy`, which writes
   `defaultTheme` to `~/.t3/userdata/settings.json`.

The order matters, for two reasons:

- `t3 theme set omarchy` fails until `themes/omarchy.json` exists. It reports
  `ThemeIdUnknownError: No theme named "omarchy"` and exits 1. Tested on
  2026-11-16 against an empty `--base-dir`.
- `omarchy-theme-set-t3code` exits 0 without writing anything when the
  generated `t3code.json` is missing or still contains `{{` placeholders.

On NixOS the app comes from the apps option, so none of these steps run.
`omarchy-theme-set` calls `omarchy-theme-set-t3code` on every theme switch,
but that script exits early when `~/.t3/userdata` does not exist. Even once
the palette is written, nothing selects it.

This happened on p620 on 2026-11-16:

- The state folder was created when the app first ran, after the last theme
  switch.
- The palette was never written, and the app stayed on its built-in theme.
- It was fixed by hand there.

Razer, p510 and any reinstall would hit the same problem. A fresh install is
worse: before the first graphical login there is no current Omarchy theme, so
nothing can be published or selected when the system is rebuilt.

## Proposed outcome

On every host where `programs.nixarchy.apps.t3-code.enable` is true:

- `~/.t3/userdata/themes/omarchy.json` holds the current palette and T3 Code's
  selected theme is `omarchy`, with no manual step. This takes effect once
  the user's Omarchy session has a current theme:
  - after the first login on a fresh install;
  - after the next rebuild on a running host.
- If that cannot be done yet, a later activation or login retries it. Causes
  include no palette or a CLI error. The failure is logged, not silent.
- Later theme switches recolour T3 Code live, through Omarchy's existing hook.
- Hosts without T3 Code are unchanged.

## Affected users and systems

- `olafkfreund` on p620, where the app is enabled today.
- Razer and p510 only if `t3-code` is enabled there later. The change does
  nothing while the option is off.
- Files: one shared module under `hosts/common/nixos/` (proposed location).
  All three hosts import shared modules through their `nixarchy.nix`.

## Constraints

- No change to T3 Code settings other than `defaultTheme`. `settings.json` is
  app-owned state: never overwrite it as a whole file.
- A missing CLI or palette file must not fail the activation.
- When it skips, it must log why and retry later.
- Binaries are called by store path or explicit path, not looked up on the
  minimal activation `PATH`. A bare `t3` there would silently do nothing.
- Everything under `~/.t3` is created as the user, not root, and stays
  editable app state.
- No `home.file` links into `themes/`, because Omarchy's hook replaces
  `omarchy.json` atomically.
- Changes go through Home Manager's `run`, so a dry run changes nothing.
- `programs.nixarchy.apps.t3-code.enable` is a NixOS-level option. This was
  checked by evaluating it for p620.
- The change is gated on that option, so hosts without the app get no `~/.t3`
  folder.
- Only the default `~/.t3` location is supported (`T3CODE_HOME` unset). The
  config does not set `T3CODE_HOME` today.
- Do not re-run `t3 theme set` when the theme is already `omarchy`. Each run
  rewrites `defaultThemeSetAt` and notifies running clients.
- p510 builds need the owner's OK. Nothing changes there until the option is
  enabled.

## Open questions

1. Should the config force `omarchy` back on every rebuild, overriding a theme
   picked in the app?
   - Proposed: yes, because declarative means the config wins. A theme picked
     in the app lasts until the next rebuild.
   - agy recommends the alternative: set it once per host. A marker file is
     written only after `t3 theme set` succeeds. This matches
     `omarchy-enable-once.nix` and lets a later in-app choice stick.
2. Should this go in this repo, or upstream in nixarchy's apps module so every
   Nixarchy user gets it?
   - Proposed: this repo now, as asked. Open an upstream nixarchy issue, link
     it in the module header, and delete the local module once upstream ships
     it.

## Owner decisions (2026-11-16)

1. Force `omarchy` on every rebuild and login when it differs. The config
   wins, and an in-app choice lasts until the next activation.
2. Fix it in this repo now; open an upstream nixarchy issue and link it in the
   module header.
