# Intent: herdr-app argv launches get their own systemd scope

## Problem

herdr-app starts `argv` launches (agents from the + menu, `tab.new --argv`, our `ctrl+shift+g`/zoetrope keys and
`herdr-team`'s placeholder tabs) as `$SHELL -ic "<argv>"; exec $SHELL -i`. That skips hc's configured `shell`
(`hcShell` in `home/development/herdr.nix`), so these processes:

- stay in hc's single shared `hc-hold-*` unit instead of a per-shell `herdr-pane-<pid>.scope` (#2959). When
  systemd-oomd kills one runaway agent there, it takes every app terminal with it;
- keep whatever environment hc inherited from its first starter, without `hcShell`'s strip of `HERDR_*` and the
  Claude session variables (the leak #2989 describes).

Plain app shells are already covered. Upstream does not offer a setting for argv launches.

## Proposed outcome

Every app terminal, argv launches included, runs in its own `herdr-pane-<pid>.scope` with the `hcShell`
environment. An oomd kill of one agent leaves the other app terminals running. Checked on p620 for a + menu agent,
a `tab.new --argv` tab, a split argv launch (`ctrl+shift+y`) and the shell that replaces each command when it exits:
each PID sits in its own `herdr-pane-*` scope, and killing one scope leaves the others running.

## Affected users and systems

- p620 and razer (the hosts with herdr-app, gated by `programs.herdrSkill.enable`).
- Bash startup for the owner's interactive shells (`home/shell/bash.nix` or `home/development/herdr.nix`).
- The Herdr TUI is unaffected: its panes already start through `paneShell`.

## Constraints

- Builds on #2978 (`hcShell`, not yet on `main`): this branch is stacked on `feat/2978-herdr-app-parity`.
- The process hc tracks must keep its PID (as `paneShell` does: `systemd-run --scope` execs in place), or hc loses
  the terminal.
- The argv command must still run exactly once, with its arguments intact.
- The command is replayed from the shell's exact original arguments (`/proc/$$/cmdline`), never rebuilt from a
  string, so quotes, spaces, `$` and empty arguments survive.
- No loop: the wrappers mark a shell as handled (one environment variable), so the re-exec happens at most once,
  including when the user bus is missing and `paneShell` falls back to plain bash.
- Interactive bash only, and only when `HC_TERMINAL_ID` is set, `HERDR_ENV` is not (never a TUI shell) and the
  marker is unset. SSH commands, scripts and shells nested in an already handled shell are untouched.
- `herdr-team` members (`hc run … -- bash launch`) are out of scope: they are not argv launches and already have
  their own scope check.
- p510 untouched; bus announcement before deploys.

## Open questions

- This covers bash only. `$SHELL` is bash on both hosts (memory: login shell is bash); another login shell would
  need the same guard.

- Fix it locally (an early `.bashrc` guard that re-execs the shell through `hcShell` when it runs in an app
  terminal outside a pane scope), or also file the upstream request for argv launches to use the configured
  `shell`? Recommendation: both; the local guard now, the upstream issue as the long-term fix.
