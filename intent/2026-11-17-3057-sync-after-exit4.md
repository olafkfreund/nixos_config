# Intent: the checkout sync also runs after a switch that exits 4 but activated

## Problem

Since #3039, `scripts/sync-remote-checkout.sh around HOST -- COMMAND` fast-forwards a remote host's
`~/.config/nixos` after a deploy, but only when COMMAND exits 0. A remote switch that activated the new generation
but saw a unit fail reports exit 4 (the activation step's documented code; whether `nixos-rebuild` and the recipe
pass it through unchanged is to be verified, see Constraints). On p510 that is reported on every deploy (the user
dbus-broker reload during activation), and razer sometimes hits it. The new system runs, the checkout stays behind,
and the drift #3039 removed comes back on the host that deploys least often.

## Proposed outcome

- When COMMAND exits 4 and the target is verifiably running **the exact system this deploy built**, the checkout is
  synced as after exit 0. That includes re-deploying a generation that is already running (a retry repairs the
  drift instead of skipping forever).
- The recipe still returns 4, so the failed unit is still reported.
- Any other non-zero exit, or exit 4 without that proof (a rollback, another machine's deploy in between, a profile
  set but not activated, an unreadable state), still skips with a one-line reason.
- Verified with a real p510 deploy (`just p510`), which the owner asked for on 2026-11-17.

## Affected users and systems

- `scripts/sync-remote-checkout.sh` and `scripts/test-sync-remote-checkout.sh`; `docs/UPDATE-DEPLOY.md` (the exit-4
  note added in #3039).
- Hosts: p510 (live test, owner-approved), razer.
- Not `nhs`: it deploys p510 in boot mode and handles its own outcomes.

## Constraints

- Never sync unless the target's running system equals the store path this deploy built; check it as late as
  possible, right before the fast-forward, so a deploy from elsewhere in between is caught.
- No extra SSH call: the check belongs in the sync's existing one.
- The deploy's exit code is unchanged.
- The exit-code chain is verified, not assumed: the activation step, `nixos-rebuild`, the wrapper and the `just`
  recipe each pass 4 through (checked in the p510 test).
- All #3039 git protections stay.
- The p510 deploy follows the usual rules: bus announcement, `P510_DEPLOY_APPROVED=1` on the owner's request, free
  space and running jobs checked first (p510 deploys have hit ENOSPC and test timeouts before).

## Open questions

Decided by the owner on 2026-11-17 (the recommendations):

1. On exit 4 only, the wrapper evaluates `.#nixosConfigurations.HOST.config.system.build.toplevel` in the deploying
   checkout and passes the path to the remote script, which compares it with `readlink -f /run/current-system`.
2. Only exit 4 is treated this way.
