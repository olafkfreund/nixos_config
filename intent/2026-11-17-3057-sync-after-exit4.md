# Intent: the checkout sync also runs after a switch that exits 4 but activated

## Problem

Since #3039, `scripts/sync-remote-checkout.sh around HOST -- COMMAND` fast-forwards a remote host's
`~/.config/nixos` after a deploy, but only when COMMAND exits 0. A remote `nixos-rebuild switch` that has activated
the new generation but saw a unit fail returns exit 4. On p510 that happens on every deploy (the user dbus-broker
reload during activation), and razer sometimes hits it (a syncthing unit race). The new system is running, the
checkout stays behind, and the drift #3039 removed comes back on exactly the host that deploys least often.

## Proposed outcome

- When COMMAND exits 4 and the target is verifiably running the generation this deploy produced, the checkout is
  synced as after exit 0.
- The recipe still returns 4, so the failed unit is still reported.
- Any other non-zero exit, or exit 4 without proof the new generation is active, still skips with a one-line reason.
- Verified with a real p510 deploy (`just p510`), which the owner asked for on 2026-11-17.

## Affected users and systems

- `scripts/sync-remote-checkout.sh` and `scripts/test-sync-remote-checkout.sh`; `docs/UPDATE-DEPLOY.md` (the exit-4
  note added in #3039).
- Hosts: p510 (live test, owner-approved), razer.
- Not `nhs`: it deploys p510 in boot mode and handles its own outcomes.

## Constraints

- Never sync when the running system is not the one just deployed.
- At most one extra SSH call, and only on exit 4.
- The deploy's exit code is unchanged.
- The p510 deploy follows the usual rules: bus announcement, `P510_DEPLOY_APPROVED=1` on the owner's request,
  check free space and running jobs first (p510 deploys have hit ENOSPC and test timeouts before).

## Open questions

1. How to prove "running the generation this deploy produced"? Recommended: compare the target's
   `/run/current-system` before COMMAND and after it; on exit 4, sync only if it changed and now equals the target's
   `/nix/var/nix/profiles/system` (the switch set the profile and activated it). A redeploy of the same generation
   then does not sync on exit 4, which is harmless.
2. Treat other activation exit codes the same way? Recommended: no, only 4, which `switch-to-configuration`
   documents as "activated, some units failed".
