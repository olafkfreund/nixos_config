# Intent: less Omarchy shell startup work (keepLoaded, app-dir rescans, dead bar keys)

## Problem

On p620 the desktop (shell, top bar and wallpaper) appears about 9.5 s after
login (journal, login of 2026-11-17 15:44:31). Hyprland is up within a
second and the shell starts 2 s after login. `BackgroundIntro.qml` then keeps
a cover over every screen until `desktopReady` (no plugin reload or registry
scan in flight, bar present, `BackgroundIntro.qml:21`), the background
service is ready, and the `omarchy-theme-bg-boot-intro` script has exited
(`startupSettled`, `BackgroundIntro.qml:420-426`), then fades for 420 ms.
Which of these gates opened last on that login is not recorded. owed was
ready at 34.35 s but reached the shell only at 37.8 s, which suggests a busy
shell main thread.

Three sources of avoidable shell work were found. None is proven to hold the
cover; each adds work on the shell's single QML thread during or right after
startup:

1. **keepLoaded panels.** 18 enabled plugins with a panel, overlay or menu
   set `"keepLoaded": true`, so those views are built at every start, after
   the registry scan (`PluginRegistry.qml:672-674`, `shell.qml:1438-1439`),
   asynchronously, instead of on first use. Some also run work while closed:
   winvm polls `virsh` every 4 s, herdr's menu holds a second herdr-app
   subscription.
2. **Application-folder rescans.** Quickshell rescans every desktop entry
   (~600) on any create, delete or rename in a watched applications folder
   (`desktopentrymonitor.cpp:28-35,64-68`). Every shell start and plugin
   reload triggers one: hyprforge deletes `hyprforge.desktop` when its
   service is destroyed and recreates it through a temp file in that folder;
   omamail rewrites `omamail.desktop` and runs `update-desktop-database`
   (temp file plus rename); hyprchroma then rewrites both icons, so the next
   start differs again. 109 rescans were logged in one shell's lifetime.
3. **Dead bar settings (cleanup, no speed effect).** `shell.json` holds ten
   per-entry `"hidden"` strings and `bar.hiddenRevealByRegion` /
   `bar.revealIcons`, left from the skal.bar era. Nothing reads them; they
   suggest icons are hidden when they are not.

## Proposed outcome

- Before and after the change, the login reveal is timed per gate, so the
  effect is measured rather than assumed.
- Our own plugins that do not need to stay loaded no longer build their
  views, or run their work, at startup. Every keybind, menu row, watch,
  consent dialog and running job keeps working.
- A shell start or plugin reload leaves `~/.local/share/applications`
  untouched when the hyprforge and omamail entries are already current.
- The three dead bar settings are gone from `shell.json` on p620 and razer.

## Affected users and systems

- Hosts: p620 and razer. p510 runs the desktop too but is not built or
  deployed without the owner's OK.
- Own repos: olafkfreund/nixarchy-devenv, -distrobox, -flatsnap, -microvm,
  -winvm, -herdr, -hyprsettngs (hyprforge), and olafkfreund/nixarchy for the
  pin bumps; the local `olafkfreund.govee` plugin folder.
- Third-party: huacnlee/omamail (local checkout).
- This repo: flake input bumps; runtime cleanup of `shell.json`.

## Constraints

- No keybind, menu row, watch, notification, consent dialog or in-flight job
  may break. A plugin keeps keepLoaded if closing its view would kill work
  or state (audit 2026-11-19: pkg, podman, github-actions, gitlab-pipelines,
  ai-mirror, nixi keep it).
- The flag also keeps a plugin's service alive across hot reload
  (`shell.qml:1076-1094`); it is never removed from a plugin with a service
  entry point without checking that.
- Third-party plugins are not changed for item 1 (owner, 2026-11-19).
- `shell.json` is edited only by the shell's own reload path (jq, rename,
  `omarchy-shell shell reloadConfig`), with a backup.
- Agent-bus announcement before any switch or shell restart; p510 untouched.

## Open questions

  launcher entry if the plugin is later disabled. Accept?
- omamail: carry a local patch in the checkout (lost on
  `omarchy plugin update`), open an upstream PR to huacnlee/omamail (needs
  the owner's OK to post), or both?
