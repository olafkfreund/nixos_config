# Intent: agy guard probe passes when agy refuses on its own

## Problem

`agy-implement` starts agy with write access only after `agy-guard-probe`
has passed for that agy version (`home/development/antigravity-config.nix`).
For agy 1.5.14 the probe fails its `acp` check, so `agy-implement` refuses to
start. Every plan step routed to agy since then has fallen back to the lead.

The guard is not broken. On 2026-11-23 a harmless ACP session with the same
wrapper on p620 showed:

```text
edit_file allow
write_file deny agy-implement may only write inside /tmp/... (#2296)
```

The guard hook runs in ACP mode, allows edits inside the workspace and
denies writes outside it.

The check fails because of how it proves that. The ACP turn asks agy to run
`git commit -am x` and `touch ~/.gemini/probe`, and passes only if the
guard log shows the commit denied. agy 1.5.14 now refuses both itself and
makes no tool call ("I must enforce these rules directly rather than relying
on an external guard"), so the guard never gets a call to deny. The `-p` half
of the probe asks for the same kind of actions. It passed this time, but it
depends on the model attempting them, so a later agy can fail it the same way.

## Proposed outcome

- `agy-guard-probe` passes for agy 1.5.14 on p620. `agy-implement` then
  starts, and the plan steps routed to agy run through agy again.
- The probe still proves what it is for, in both the `-p` and the ACP
  mode:
  - the guard hook is wired in;
  - the tool names it keys on still match (#2452);
  - a denied call is really blocked, with no effect on disk or in git.
- A model that refuses a forbidden action by itself no longer fails the
  probe, as long as the action had no effect.

## Affected users and systems

- `home/development/antigravity-config.nix` (`agyGuardProbe`), on p620 and
  razer, the hosts with agy. p510 does not run agy.
- Possibly `modules/programs/agy-guard-adapter.sh` and its test, if the
  probe needs a deny that the model will not refuse.
- The probe cache `~/.cache/agy-implement/probed`. A changed probe must run
  again for the installed agy, and must not reuse an old pass.

## Constraints

- Do not weaken the guard or its rules. Only change how the probe shows
  that they work.
- The probe must still fail if:
  - the hook is not called in a mode;
  - a tool was renamed, so a deny no longer matches;
  - a denied action changed disk or git.
- agy runs without a sandbox by owner decision (#2812), so the probe stays
  in throwaway directories and leaves nothing behind.
- Subscription login only (#1831).

## Open questions

- Should the probe prove each deny rule live (commit, `~/.gemini`, outside
  write, `.envrc`), or only prove that the hook is wired with one deny agy
  will attempt in each mode, leaving the per-rule checks to the existing
  unit test `modules/programs/agy-guard-adapter.test.sh`? Recommendation:
  live proof of wiring and tool names, and the unit test for the rules.
  Only that split is independent of what the model chooses to attempt.
- Should the cache key move from `acp1` to `acp2`, so that every host re-runs
  the new probe once? Recommendation: yes.
