# Intent: login cover lifts through the normal path on p620

Follows the measurement in #3165 (timeline: issue 3165, comment 7094482325).
Times below are seconds after the shell launched (07:32:34.38). The bars
completed at +1.3 s.

## Problem

At a p620 login the black startup cover stays up about 12 s after the Omarchy
shell starts, and lifts only because the 10 s safety timer in
`services/BackgroundIntro.qml` fires (`fade-start timeout` at +11.5 s). The
normal reveal (`revealStartup`, `BackgroundIntro.qml:63`) needs three inputs
at once: the wallpaper ready (`startupMediaReady`), `desktopReady`, and two
`FrameAnimation` ticks on each cover. On 2026-11-23:

- **A second plugin scan from the shell's own startup chain.**
  `PluginRegistry`'s `Component.onCompleted` runs `ensureUserDir()`. That
  `mkdir` process's exit starts the orphaned-watcher reaper, and the reaper's
  exit calls `registry.rescan()` (`PluginRegistry.qml:690-706`, `:810`).
  `shell.qml:194` also scans at startup. `rescan()` only skips while a scan is
  running (`PluginRegistry.qml:755`), so a reaper that exits after the first
  scan starts a second one. Here the exit handler ran 93 ms after the last bar
  widget registered (+5.1 s), once the main loop was free. The scan ran 4.0 s
  and held `desktopReady` false. The log rules out the other callers:
  `finishPluginReload` would show `reloading=true`, and there is no
  `Local plugin changed` line. An outside IPC `rescanPlugins` is not logged,
  so it is not ruled out.
- **A 2.4 s main-loop block right after that scan ends** (+9.1 to +11.5 s).
  It starts at the synchronous `pluginsChanged()` + `scanFinished()`
  dispatch (`PluginRegistry.qml:674-676`). Both handlers sync again:
  `onPluginsChanged` runs `syncPluginApis` and `_syncServices`, and
  `onScanFinished` runs `_syncServices`, `syncPanelEntries` and
  `syncPluginWidgets` (`shell.qml:1114-1117`, `:1636-1638`). Each bar-widget
  registry change runs `syncPluginApis` again (`shell.qml:1120-1123`). Which
  handler takes the time is not measured. This block is why the covers missed
  their two frames before the timer.
- **Earlier main-loop work that also holds the covers.** `desktopReady` was
  true from +1.5 to +5.1 s, yet no cover reached two frames. In that window:
  - plugin services were compiled synchronously (`Component.PreferSynchronous`,
    `shell.qml:971`), 1.74 s in total, of which `omarchy.background` took
    1.37 s;
  - 54 bar widgets were registered, 1.7 s.
- **Wallpaper readiness is late too.** `media-ready` came at +7.8 s (6.4 s
  after the bars). Removing the second scan alone cannot reveal earlier than
  that.
- **16 `keepLoaded` panels** were created after the first scan, not by the
  second. They finish loading from +6.5 to +9.0 s, with a 2.0 s stall. This
  stall stays even without the second scan.

Corrected from the #3165 comment: bar widgets are **not** built twice.
The 4 lines per instance are 2 bars × (an empty placeholder loader, then
the real widget, `plugins/bar/Bar.qml:2713-2740`). The nine
`IpcHandler ... another handler is registered` warnings come from plugins
that put an `IpcHandler` in a per-bar widget on a two-monitor desktop. They
are not a startup cost. `omarchy.background` is created a second time at
+13.3 s, after the reveal, and that takes 7 ms. It is out of scope here.

## Proposed outcome

At a p620 login, the cover lifts through the normal path (`fade-start
normal`), clearly before the 10 s safety timer. This is shown by one login
with the #3165 timing patch applied again, extended with lines for the
reaper's rescan, each post-scan handler and the wallpaper path. In that log:

1. The startup chain starts no second scan, or the second scan finds nothing
   new and costs no sync work. A plugin added or edited during the session is
   still picked up.
2. The block after a scan is measured per handler and cut, so the covers get
   their frames as soon as the other inputs are ready.
3. The reveal time is reported against the wallpaper's ready time. If the
   wallpaper becomes the last input, the next step is a separate issue for
   it: the background service's 1.37 s synchronous compile, and `media-ready`
   at +7.8 s.

There is no fixed seconds target until the wallpaper path is measured. The
measure of success is a normal-path reveal, and the reveal coming earlier than
on 2026-11-23 (+11.5 s).

## Affected users and systems

- Hosts: p620 for the measurement. razer and p510 run the same Omarchy shell
  through nixarchy, so a source fix reaches them too. Expected effect there: a
  faster login, not checked on those hosts.
- Code: the Omarchy shell (`services/PluginRegistry.qml`, `shell.qml`,
  `services/BackgroundIntro.qml`) as nixarchy ships it. The reaper chain is
  upstream Omarchy code, so the fix goes to omacom/omarchy, and nixarchy
  carries a patch until upstream releases it.
- This repo: the nixarchy pin, plus the p620 timing patch for the measurement
  login, applied and reverted the same way as #3179/#3180.

## Constraints

- Remove causes; don't hide them. Do not shorten the 10 s safety timer, drop
  the two-frame check, or simply stop the scan from clearing `desktopReady`.
- Plugin behaviour stays the same:
  - first discovery on a fresh profile still works;
  - a plugin added in a running session still appears (in-place rescan);
  - an edited plugin still reloads with fresh code (full reload);
  - the watcher reaper still stops orphaned watchers.
- Deferring work until after the reveal is in bounds, as long as every plugin
  still loads in the same session: `keepLoaded` panel preloading, and
  asynchronous service compilation. Changing which plugins load is not.
- Each measurement needs one logout and login by the owner. The timing patch
  stays temporary and gated, as in #3165.
- p510 is never built or deployed without the owner's OK. Announce on the
  agent bus before any deploy.

## Open questions

- **Scope:** this task covers the second scan and the block after it.
  Wallpaper readiness and synchronous service compilation get their own
  issue, opened if the new log shows them as the last input. Recommended.
- **Where the patch lives until upstream:** nixarchy (all hosts get it) or
  this repo for p620 only. Recommendation: nixarchy, gated behind upstream
  acceptance like earlier shell fixes, so the spec decides after reading
  how nixarchy carries Omarchy patches today.
