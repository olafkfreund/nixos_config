# Intent: a dedicated NVMe for builds and the GitHub runners on p620

## Problem

p620 has a new, unused disk: `nvme0n1`, a Lexar EQ790 1 TB NVMe, at
`/dev/disk/by-id/nvme-Lexar_SSD_EQ790_1TB_QJC054R004014P221Q`. Checked on 2026-11-23:

- `wipefs` and `blkid` find no signatures, and there are no partitions;
- SMART reports healthy, with 0 power-on hours and 0 bytes written;
- it supports discard.

The build-heavy work on p620 sits on disks that suit it less well:

- **The nix `build-dir`,** `/var/lib/nix-build`, is on a 480 GB SATA SSD labelled `scratch` (#2182). It is
  machine-wide: `services.nixarchy-runner` sets both `nix.settings.build-dir` and the daemon's `TMPDIR`. So every
  build on the host uses it: the four nixarchy runners' 16 GB VM installs, agents' builds, and razer's builds via
  `deploy-via-p620`. SATA is slower than NVMe, and the disk is half the new one's size.
- **The agents' nixarchy VM workspace,** `services.nixarchy-runner.vmImageDir = "/mnt/data/vmtest"` (4.4 GB now),
  is on `/mnt/data`. nixarchy's `CLAUDE.md` sends agents there to keep VM disk images, and the same directory
  holds their git worktrees. The NixOS option only points the daily prune timer at it. `/mnt/data` is a QLC disk,
  and `hosts/p620/configuration.nix` records that its fsync stalls under bulk writes, which crash-looped postgres.
- **What does not need to move:** runner state (`/var/lib/private/github-runner`, 300 MB of checkouts and
  `_diag`). The runner module itself says moving `workDir` is the wrong lever: the 16 GB belongs to the nix build,
  in the build-dir. Moving it would also reopen the DynamicUser trap the module records.

## Proposed outcome

- The new NVMe is formatted, labelled and mounted at a permanent mount point, by UUID or label.
- The nix build-dir is on it. A rebuild on p620, a razer build via p620, and a nixarchy runner job (including a VM
  install check) all write their build trees there.
- If the owner wants it (question 2), the agents' VM workspace moves there too, together with the nixarchy
  `CLAUDE.md` text that tells agents where it is.
- If the build disk is missing or fails, p620 still boots and can still rebuild itself. CI must not be able to fill
  the root disk in that state (question 1).
- Nothing else changes: `/nix/store` stays on the root NVMe, and so do its `min-free`/`max-free` limits. Build
  outputs are still copied into the store across filesystems, as they are today from `scratch`.

## Affected users and systems

- **Host:** p620 only. razer and p510 are not changed (p510 has had no nixarchy runners since #1738), though
  razer's builds run on p620.
- **Services:** the nix daemon, the four nixarchy GitHub runners (`p620-nixarchy` to `-4`), the VM image prune
  timer, and nixarchy's `omarchy-edge` verify job, which boots VM checks on p620's runners.
- **People and agents:** every agent that builds on p620, and agents that keep VM images and worktrees in the
  workspace.

## Constraints

- **Formatting:** the disk is formatted only after the plan is approved, and the plan names it by the by-id path
  above, never `nvme0n1`. NVMe names have already swapped once on p620: `/home` was `nvme0`, and is now `nvme1n1`.
- **Quiet window for the cutover:** changing `build-dir` affects every build on p620. Announce on the agent bus,
  and switch only with no nixarchy runner busy, no edge verify running, and no other build in flight (an agent's,
  or a razer build via p620).
- **Disk scheduling:** keep the nix daemon's I/O priority working. p620 runs BFQ on NVMe; its udev rule already
  matches `nvme0n1`. Also keep periodic TRIM working: `common-pc-ssd` runs `fstrim`, and one p620 disk needed an
  opt-out after TRIM stalled it for 10 hours.
- **No data loss:** nothing on the old disks is deleted in this task. Today's build-dir holds only temporary build
  trees, but the workspace holds git worktrees, which may include uncommitted work. Any move of it copies, and does
  not remove the old copy.
- **p510** is not touched.

## Open questions

1. **When the build disk is missing:** should the nix daemon fall back to `/`, so p620 can still rebuild itself,
   while the GitHub runners refuse to start? The runners would depend on the mount, as Docker already does for its
   disk, so CI cannot fill `/`. Or should the disk be required, with no fallback?
2. **The agents' VM workspace** (`/mnt/data/vmtest`): move it to the new disk, and update nixarchy's `CLAUDE.md` to
   match? Or leave it where it is, and use the disk only for the build-dir?
3. **Mount point and naming:** a general build mount with subdirectories (the spec would propose a name, for
   example `/mnt/build`, labelled `build`)? Or mount the disk directly at `/var/lib/nix-build`, keeping today's
   path?
4. **The old 480 GB `scratch` SSD:** keep it mounted, unused, as a fallback; leave it unmounted for a later task;
   or reuse it now for something else?
5. **Runner count:** keep four runners? The host's sizing note says two runners peaked at about 64 GB together.
   The module limits runners by CPU and RAM during VM tests, not by disk, so the new space alone is no reason to
   add more.
