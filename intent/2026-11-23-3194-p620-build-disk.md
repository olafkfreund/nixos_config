# Intent: a dedicated NVMe for builds and the GitHub runners on p620

## Problem

p620 has a new disk, unused: `nvme0n1`, a Lexar EQ790 1 TB NVMe (serial QJC054R004014P221Q). It is blank (no
partitions, no signatures) and healthy (SMART passed, 0 power-on hours, 0 bytes written).

The build-heavy work on p620 is spread over disks that are not suited to it:

- **The nix `build-dir`** (`/var/lib/nix-build`) is machine-wide, so every build on the host uses it, including the
  four nixarchy runners' 16 GB VM installs. It is on a 480 GB SATA SSD labelled `scratch` (#2182), slower than NVMe
  and half the size.
- **Runner VM images** (`services.nixarchy-runner.vmImageDir = "/mnt/data/vmtest"`, 4.4 GB now) are on the
  Fanxiang QLC SATA disk. That disk is known to stall under sustained writes (a Steam copy onto it crash-looped k3d
  postgres), and it is shared with other data.
- **Runner state** (git checkouts and `_diag` under `/var/lib/private/github-runner*`) is on the root NVMe, which
  also holds the store and is 53% full.

## Proposed outcome

- The new NVMe is partitioned, formatted, labelled and mounted at a clear, permanent mount point.
- The nix build-dir and the runners' disk-heavy data use it.
- A rebuild on p620, and a nixarchy runner job (including a VM install check), run on the new disk, with no change
  in behaviour other than speed and headroom.
- A missing or failed build disk does not stop p620 from booting or from rebuilding itself, as with today's
  `nofail` build-dir.

## Affected users and systems

- **Host:** p620 only. razer and p510 are not affected (p510's runners were removed in #1738).
- **Code:** `hosts/p620/nixos/hardware-configuration.nix` (filesystems), `hosts/p620/configuration.nix`
  (`services.nixarchy-runner`), possibly `modules/services/nixarchy-runner.nix`, and the BFQ udev rule that matches
  NVMe names (`nvme[0-9]n1`), because NVMe names can swap when a disk is added.
- **Agents and CI:** the four nixarchy GitHub runners on p620 (`p620-nixarchy`, `-2`, `-3`, `-4`), and every agent
  that builds on p620.

## Constraints

- **Destructive step:** the disk is formatted only after the plan is approved. The plan names it by stable ID
  (`/dev/disk/by-id/…QJC054R004014P221Q`), never by `nvme0n1`, which can change between boots.
- **Mounts by UUID or label** in the config, like the other p620 disks.
- **Runner state:** the module's comment records that pointing the runners' `workDir` at a `tmpfiles` directory
  broke them (a DynamicUser cannot write a root-owned directory). Any move of runner state must avoid that trap.
- **Shared host:** announce on the agent bus before the format, the switch and any runner restart. Switch only with
  no nixarchy runner busy, and never while an edge verify job runs on p620.
- **No data loss:** the current build-dir holds only temporary build directories, and the VM images are
  disposable test images. Nothing on the old disks is deleted as part of this task.
- **p510** is not touched.

## Open questions

1. **Mount point and label:** proposed `/mnt/build`, label `build`, with subdirectories for the nix build-dir
   (`/mnt/build/nix`), the runner VM images (`/mnt/build/vmtest`) and, if wanted, runner state. The alternative is
   to mount it straight at `/var/lib/nix-build`, keeping today's path. Which do you prefer?
2. **Runner state:** should the runners' work directories move to the new disk too (more involved, see the
   DynamicUser trap), or only the build-dir and VM images, which hold nearly all of the bytes?
3. **The old 480 GB `scratch` SSD:** keep it mounted as a fallback, repurpose it later (a separate task), or leave
   it unmounted?
4. **Runner count:** four runners peaked at about 64 GB each, sized to the 480 GB disk. With 1 TB, should the plan
   raise `instances`, or keep four?
