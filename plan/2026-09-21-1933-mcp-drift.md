# Plan: MCP servers do not follow a rebuild

## Approved decisions carried over

Self-contained. Do not reopen the intent or spec to implement this.

1. **Use the existing mechanism.** `home.activation.claudeSharedMcpServers`
   (`home/development/claude-code-mcp.nix:299`) already reconciles declared
   servers into `~/.claude.json` on every activation. Add to it; do not build
   a second mechanism beside it.
2. **The `nix-store --add-root` gcroot design is dropped.** It was verified to
   work, and is redundant once the registration tracks the config.
3. **Do not take over hand-registered servers.** Anything not declared in this
   repo stays the user's to manage. Declaring one means an activation would
   overwrite a hand edit.
4. **The drift check reports; it does not rewrite.**
5. **Verification observes the running system.** A registration pointing at
   the right path proves nothing about what the model receives. Reading
   `server.py` or `~/.claude.json` is not sufficient evidence.
6. **p510 is not built or deployed.** It does not run Claude Code.

## Verified before this plan was written

- `agent-bus` is declared in `claudeSharedMcpServers`, and its registered
  command in `~/.claude.json` is byte-identical to what the current
  configuration builds. The mechanism works.
- The merge is `jq '.mcpServers = ((.mcpServers // {}) + $d[0].mcpServers)'`:
  `+` replaces each declared server wholesale, leaves undeclared ones
  untouched. It writes via a temp file, keeps `$target.bak`, and warns and
  leaves the file unchanged on failure.
- `ollama-code` is **not** in that block. It appears only in the seed
  template, which is written once and never re-read (#398). That is the bug.
- `mcp-nixos`, `mcp-server-fetch`, `mcp-server-git` and `nixos` are **not
  declared anywhere in this repo** — `grep` for each as a declared key in
  `claude-code-mcp.nix` returns nothing. They are hand-registered.
- They have visibly drifted: `mcp-server-fetch` is registered at
  `2026.1.26-unstable-2026-05-17` while nixpkgs now builds `2026.8.31`, and
  `mcp-nixos` is registered at both `2.3.1` and `3.0.1`.

## Steps

1. `home/development/claude-code-mcp.nix`: move the `ollama-code` declaration
   into the `claudeSharedMcpServers` activation block, beside `agent-bus`,
   keeping its existing `command`, `args` and per-host `OLLAMA_HOST` `env`.
   Leave the seed template's copy in place — it is what a fresh machine gets
   before the first activation — and add a comment on both saying which one is
   authoritative after first run.
   → verify by `just check-syntax`, then by the before/after registration
   check in Tests

2. Same file: add a comment above the activation block recording that a
   reconciled registration **only takes effect when the session restarts**.
   An already-running Claude Code keeps its spawned process and its loaded
   tool schemas. Without this written down, the next person rebuilds, sees no
   change, and concludes the fix failed — which is how this issue was born.
   → verify by reading it

3. `Justfile`: add a `check-mcp` recipe that, for each server registered in
   `~/.claude.json`, reports:
   - **drifted** — declared in this repo but the registered command differs
     from what the configuration builds (should normally be empty);
   - **missing** — the registered command path does not exist on disk, the
     post-garbage-collection case;
   - **unmanaged** — registered but not declared here, listed for information
     only, with no suggestion to adopt it.

   It derives the declared set from the configuration rather than a
   hand-written array, so a newly declared server is covered automatically.
   It reports and exits 0 unless something is **missing**, which is a real
   breakage.
   → verify by running it, and by the deliberate-break test

4. Leave `~/.local/state/nix/gcroots/ollama-mcp` in place. Once `ollama-code`
   is reconciled to a store path directly, that root is vestigial — it pins an
   old build and nothing reads it. It was created outside this repo, so
   removing it is the user's call, not an activation's. `check-mcp` mentions
   it as vestigial so it can be deleted at leisure.
   → verify by `check-mcp` output naming it

## Tests

```bash
just check-syntax
just test-host p620
just test-host razer
```

Expected: all succeed. razer is built because it also runs Claude Code.

Registration reconciliation:

```bash
jq -r '.mcpServers."ollama-code".command' ~/.claude.json   # before
jq -r '.mcpServers | keys | length' ~/.claude.json          # before
# switch p620
jq -r '.mcpServers."ollama-code".command' ~/.claude.json   # after
jq -r '.mcpServers | keys | length' ~/.claude.json          # after
ls -l ~/.claude.json.bak
```

Expected: the command now names the store path the current configuration
builds; the key count is unchanged or larger, never smaller; `.bak` exists.

**The end-to-end check this whole issue exists for:** restart the session,
load the live `ollama_code` tool schema, and confirm it contains the
cloud-model text added in #1931. That text is absent today. Its appearance is
the proof. A correct-looking `~/.claude.json` is not.

Deliberate break, to prove the check is not vacuous:

```bash
# point ollama-code at an older store path by hand
just check-mcp        # must report it as drifted
# switch p620
just check-mcp        # must be clean again
```

p510: not built, not deployed, not asked.

## Rollback

- Steps 1–2 are declarative: revert and rebuild. The activation block then
  stops declaring `ollama-code`, and the registration keeps whatever it last
  had — which is the current behaviour, so reverting is safe rather than
  destructive.
- Step 3 is a new `Justfile` recipe: revert it; nothing depends on it.
- Step 4 changes nothing.
- If an activation ever mangles `~/.claude.json`, `~/.claude.json.bak` holds
  the previous content — the existing block already writes it, and this change
  inherits that rather than reinventing it.
