# Plan: put p620's three new disks to use

## Approved decisions (carried from the spec)

- Each disk mounts at the path its workload already uses. All are ext4,
  declared by UUID, with `noatime`:

  | Disk (`/dev/disk/by-id/…`) | Label | Mount | `nofail` |
  | -------------------------- | ----- | ----- | -------- |
  | `nvme-Fanxiang_S501Q_1TB_26060256623000377` | `home` | `/home` | **no** (missing → emergency mode) |
  | `ata-MS4SC2JH2ORA480G_S2UBNX0J100050` | `scratch` | `/var/lib/nix-build` | yes (degrades to `/`, deliberately) |
  | `ata-MTFDDAK256TBN-1AR1ZABHA_UFZMN01J186ZIF` | `docker` | `/mnt/img_pool` | yes, plus Docker `RequiresMountsFor` |

- The Micron's pfSense install is wiped (decided at intent approval).
- `services.nixarchy-runner.buildDir` stays `/var/lib/nix-build`; `instances`
  goes 2 → 4. Docker `dataRoot` stays `/mnt/img_pool/docker`.
- The BFQ udev rule matches `KERNEL=="nvme[0-9]n1"`, not `nvme0n1`.
- Deploy with `nh os boot` and a reboot, **never `switch`**. A switch starts
  the new mount units live, over a running `/home`.
- Cutover happens logged out, from a TTY, with a final `rsync --delete`
  delta. Old data stays hidden under the mounts until the reclaim step.
- Out of scope: the old `/mnt/games` drive (left untouched) and the
  `/mnt/data` boot dropout (a hardware fix for the user).

## Repo traps that apply to every step

- `sdX` letters shuffle on every boot. Address disks **only** by
  `/dev/disk/by-id/…` or by UUID.
- Commit prose goes through `-F - <<'MSG'`, never `-m` with backticks.
- The bus guard matches words like deploy and reboot in command text.
  Announce on `#agents:freundcloud.org.uk`, then rerun the command with
  `AGENT_BUS_ANNOUNCED=1`.
- Never check out the branch in `~/.config/nixos`. Deploy from `main` after
  the PR merges.
- p510 is not built or deployed.

## Steps

1. **Wipe the Micron** (live, irreversible):
   `blkdiscard -f /dev/disk/by-id/ata-MTFDDAK256TBN-1AR1ZABHA_UFZMN01J186ZIF`
   → verify with `wipefs -n` on the same path: no output.
   Traps: double-check the by-id serial before running. `blkdiscard` does
   not ask.

2. **Partition and format all three** (live). For each disk D with label L:
   `nix shell nixpkgs#gptfdisk -c sgdisk --zap-all -n1:0:0 -t1:8300 -c1:L D`,
   then `mkfs.ext4 -L L D-part1`.
   → verify with `lsblk -o NAME,LABEL,UUID,SERIAL`. Record the three UUIDs
   for step 4.
   Traps: wait for udev (`udevadm settle`) before `-part1` exists.

3. **Pre-copy** (live, about 230 GB). Mount `home` at `/mnt/new-home` and
   `docker` at `/mnt/new-docker`, then:
   `rsync -aHAXS --numeric-ids --info=progress2 /home/ /mnt/new-home/`
   `rsync -aHAXS --numeric-ids --info=progress2 /mnt/img_pool/ /mnt/new-docker/`
   → verify with `du -sxh` of each, which should land near 208 GB and 19 GB.
   Traps: as root. Without `-X`, overlay2 whiteout xattrs and ACLs are lost.
   The live copy is allowed to be inconsistent; step 7 fixes it.

4. **`hosts/p620/nixos/hardware-configuration.nix`**:
   - After `/mnt/code` (ends line 72), add the three `fileSystems` entries
     with the step 2 UUIDs, options as in the table, plus
     `x-systemd.device-timeout=10s` on the two `nofail` ones.
   - Line 85: `KERNEL=="nvme0n1"` → `KERNEL=="nvme[0-9]n1"`, and the comment
     says "both NVMe disks".

   → verify with `just check-syntax`.
   Traps: no `nofail` on `/home`.

5. **`hosts/p620/configuration.nix`**:
   - Lines 71-75: `instances = 4`. The comment says builds and runner VMs
     have their own 480 GB SSD (Issue #2182), and to drop to 3 if the peak
     exceeds about 350 GB.
   - Next to the docker block (around line 559), add
     `systemd.services.docker.unitConfig.RequiresMountsFor = [ "/mnt/img_pool" ];`
     and update the comment above `dataRoot`: `/mnt/img_pool` is now its
     own disk.

   → verify with `just test-host p620`, which must build.
   Traps: none beyond the global ones.

6. **Commit, PR, merge, deploy in boot mode**:
   - Commit steps 4-5 as `feat(p620): mount new disks for home, build
     scratch and docker (#2182)` and open a PR linking all three artifacts.
   - After merge, in `~/.config/nixos` on `main`: post to the bus, then
     `nh os boot ~/.config/nixos`.

   → verify with `nixos-rebuild list-generations`: the newest generation is
   marked for the next boot, and `findmnt /home` is **still** the root fs.
   Traps: not `switch`, not `just p620` (it switches). Check
   `ps aux | grep -E 'update-commit-deploy|nh os'` first.

7. **Offline cutover** (the user runs it; it ends this Claude session).
   I write `/var/tmp/cutover-2182.sh`; the user runs it as root from a TTY
   (Ctrl+Alt+F3) after logging out of the desktop. It does:
   - `loginctl terminate-user olafkfreund`
   - `systemctl stop docker.socket docker.service 'github-runner-nixarchy*'`
   - Remounts the temp mounts if the boot cleared them, then the final
     `rsync -aHAXS --numeric-ids --delete --exclude=/lost+found` for both
     trees.
   - `sync`, prints `du -sxh` of source vs target, and asks before
     `systemctl reboot`.

   → verify by eye: the two `du` pairs match within a few MB.
   Traps: post to the bus before step 7. The script must not live under
   `/home`.

8. **Verify after reboot** (Claude, new session):
   - `findmnt /home /var/lib/nix-build /mnt/img_pool` shows the three UUIDs.
   - `cat /sys/block/nvme*n1/queue/scheduler` shows `[bfq]` on both.
   - `nix config show build-dir` → `/var/lib/nix-build`.
   - `docker ps -a` shows the same containers, and the k3d cluster is up.
   - `getfacl /home/olafkfreund` matches before cutover. The Syncthing REST
     status shows every folder idle.
   - Four `github-runner-nixarchy*` units are active.

   → the PR's verification checklist is ticked.

9. **Reclaim** (no sooner than 3 days after step 8, with the user's OK):
   `mount --bind / /mnt/rootfs`, inspect, then delete
   `/mnt/rootfs/home/{olafkfreund,ollama}` and `/mnt/rootfs/mnt/img_pool/*`.
   → verify `df /` frees about 227 GB.
   Traps: `-x`/bind only. Never `rm` through the real `/home` path.

## Rollback

- **Before step 7**: nothing has moved. Boot the previous generation, or
  `nh os boot` back to main's previous commit.
- **After step 7**: pick the previous generation in the boot menu. It has
  no new mounts, so `/home` and `/mnt/img_pool` are the untouched originals
  on `/` from before the cutover. Changes made on the new disks since then
  would need copying back.
- **After step 9**: no rollback for the data location. The new disks are
  the only copy, so step 9 waits for the user's go-ahead.
