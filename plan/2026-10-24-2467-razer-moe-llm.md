# Plan: a fast local MoE model for razer, served by p620

## Approved decisions (from intent and spec)

- p620's existing Ollama (0.40.4, `features.ollama-server`) serves the model.
  razer uses it over the tailnet at `http://p620:11434`. razer and p510
  don't change, and no new cache or package is added.
- **Model:** `hf.co/unsloth/Qwen3.6-35B-A3B-GGUF:UD-IQ4_XS`. That's 17.7 GB of
  weights, about 21 GB in VRAM with the shared 32K context. Use
  `…:UD-Q3_K_XL` (16.8 GB) only if `ollama ps` shows less than 100% GPU.
  Never Ollama's own `qwen3.6:35b-a3b`, which is 21.7 GB and spills to the
  CPU.
- The model is on-demand, not persistent. While loaded it evicts
  `qwen3.8:27b` (`MAX_LOADED_MODELS=1`).
- Check first: if p620's Ollama can't load the GGUF, stop and report. Don't
  fall back silently.

This touches one file in three steps, which is below the model-split
threshold, so I do it myself.

## Steps

1. **Check by hand on p620, before any edit.**

   ```bash
   ollama pull hf.co/unsloth/Qwen3.6-35B-A3B-GGUF:UD-IQ4_XS
   ollama run --verbose hf.co/unsloth/Qwen3.6-35B-A3B-GGUF:UD-IQ4_XS "Explain MoE offload in two sentences."
   ollama ps
   ```

   - Pass means it answers, `ollama ps` shows `100% GPU`, and the eval rate
     is recorded.
   - If it shows less than 100% GPU, repeat with `:UD-Q3_K_XL` and use that
     name from here on, recorded as a deviation in this plan.
   - If it fails to load, stop and report to the user.
   - Then a request from razer:

     ```bash
     ssh razer 'curl -s http://p620:11434/api/generate -d "{\"model\":\"<name>\",\"prompt\":\"say ok\",\"stream\":false}"'
     ```

     Its `eval_count` / `eval_duration` gives the tokens/s.
   - Traps:
     - The pull is 17.7 GB to `/mnt/data`, which uses the network and disk
       but isn't a deploy.
     - Running it evicts `qwen3.8:27b` from VRAM. Check the agent bus first
       in case someone is using p620's model.

2. **`hosts/p620/configuration.nix:143`: add the model to `onDemandModels`.**
   Put the new entry on its own line, with a one-line comment above it:
   `# MoE: 17.7GB IQ4_XS + 32K KV fits the 24GB card; ollama's own qwen3.6:35b-a3b (21.7GB) spills to CPU (#2467).`
   Re-wrap the list in the file's style.
   - Verify: `just check-syntax`, then `just test-host p620`.
   - Traps: keep the existing entries, especially `qwen2.5:7b`, which the
     audiobook import depends on.

3. **Deploy p620, check, PR.**
   - Post on the agent bus, then `just quick-deploy p620` from the worktree
     with `ALLOW_BRANCH_DEPLOY=1`, after merging main.
   - `ollama list` shows the model. It's already pulled from step 1; the
     loader doesn't re-run on `switch`.
   - Open the PR linking the three files, with step 1's measured tokens/s
     and `ollama ps` output.
   - Traps: razer and p510 aren't deployed (they don't change). Merge main
     first.

## Deviations

- Added at the user's request: a "Local LLM (served by p620)" section in

## Tests

```bash
just check-syntax && just test-host p620
ollama ps   # after a request → 100% GPU
```

Step 1's numbers are the acceptance test: 20 or more tokens/s from razer.

## Rollback

Remove the line, redeploy p620, and run `ollama rm <name>` to free 17.7 GB on
`/mnt/data`.
