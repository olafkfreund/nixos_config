# Plan: T3 Code follows the Omarchy theme declaratively

This plan carries every decision from the approved spec
(`spec/2026-11-16-2973-t3code-theme.md`), so it can be followed without
opening the spec. One PR, branch `feat/2973-t3code-theme`, worktree
`~/.config/nixos-2973`.

## Approved decisions

- **One trigger.** A Home Manager activation entry,
  `home.activation.t3codeOmarchyTheme`, ordered
  `lib.hm.dag.entryAfter [ "writeBoundary" "nixarchySeed" ]`, whose body is
  `run ${script}`.
  - `nixarchySeed` exists on p620 (`nix eval` of its `.after` gives
    `["writeBoundary"]`). It stages the first-run theme headless, which
    covers a fresh install.
  - Home Manager activation runs at every boot and every switch, so a skipped
    run is retried.
  - No post-boot hook. No `omarchy-theme-refresh`.
- **Gating.** `enabled = config.programs.nixarchy.apps.t3-code.enable` is read
  in the outer NixOS module. `lib.mkIf enabled` wraps the activation entry
  inside `home-manager.users.olafkfreund = { lib, ... }: { … }`, never the
  module function. Off on Razer and p510 today.
- **Binaries.** The script's `PATH` is
  `${binPath}:$PATH`. In production, `binPath` is
  `${lib.makeBinPath [ coreutils gnugrep jq ]}:/etc/profiles/per-user/olafkfreund/bin:/run/current-system/sw/bin`.
  Each of `omarchy-theme-set-t3code` and `t3` is checked with `command -v`; a
  missing one is logged and the script stops. `t3` works with an empty
  environment (tested: 0.4 s).
- **The script** has these steps, as in the spec's design:
  `set -u`, no `-e`, and an explicit `exit 0` at the end; all logs go to
  stderr, prefixed `t3code-theme:`.
  0. `export T3CODE_HOME="$HOME/.t3"`; every `t3` call passes
     `--base-dir "$T3CODE_HOME"`.
  1. `mkdir -p "$T3CODE_HOME/userdata"`.
  2. If `$HOME/.local/state/omarchy/current/theme/t3code.json` is missing,
     log `no Omarchy palette staged yet; next activation retries` and stop.
  3. Run `omarchy-theme-set-t3code`.
     - Non-zero exit: log the code and stop.
     - Exit 0 while the source contains `{{`: log `palette has unresolved
       colours; kept the previous one`, and continue.
  4. Select the theme.
     - `themes/${themeId}.json` missing: log and stop.
     - Current theme = `jq -r '.defaultTheme // empty'` of `settings.json`,
       or empty when that file is missing.
     - If the current theme equals `themeId`, do nothing.
     - Otherwise run
       `timeout -k ${killSecs} ${timeoutSecs} t3 theme set ${themeId} --base-dir "$T3CODE_HOME"`,
       with stdout and stderr redirected to a `mktemp` file, never a pipe.
     - On a non-zero result, including 124 and 137, log the code and the last
       5 lines of that file. Remove the file afterwards.
- **Theme id.** `themeId = "omarchy"` is a parameter (default `"omarchy"`). The
  publish step is unconditional. #2974 will set `omarchy-plus`.
- **Owner decisions.**
  - Force `themeId` whenever it differs, on every activation.
  - Open an upstream nixarchy issue, linked in the module header, so the
    module can be deleted once upstream ships it.

### 3. Check (coder)

New file: `checks/t3code-theme.nix`. Add one line to `checks/default.nix`:

```nix
t3code-theme = import ./t3code-theme.nix { inherit pkgs; };
```

It is a `pkgs.runCommand` that:

- builds the step 1 script with `binPath` set to a stub directory plus
  coreutils, gnugrep and jq, with `timeoutSecs = 2; killSecs = 1;`;
- runs it with `HOME` set to a temporary folder and `PATH` set to the minimal
  tools needed for the test itself;
- uses stubs that append their arguments to a call log;
- has a stub `t3` that writes `defaultTheme` to `settings.json` on
  `theme set`.

Cases. Each one asserts exit 0 and checks the call log and stderr:

1. No staged `t3code.json`: no `t3` call; stderr contains `no Omarchy palette`.
2. The publisher stub exits 1: no `t3` call; the exit code is logged.
3. The source contains `{{` and the publisher stub exits 0 without writing:
   the warning is logged, and `t3 theme set omarchy` is called, because
   `themes/omarchy.json` already exists from the fixture.
4. No `settings.json`: `t3 theme set omarchy --base-dir <HOME>/.t3` is
   called.
5. `defaultTheme` is `ember`: `t3` is called.
6. `defaultTheme` is `omarchy`: `t3` is not called.
7. `t3` exits 1: the error is logged, and the script exits 0.
8. `t3` traps TERM and sleeps for 60 s: the script finishes in under 10 s, and
   exit code 124 or 137 is logged.
9. No `t3` in `binPath`: `not found` is logged, and the script exits 0.

Verify:

```bash
nix build .#checks.x86_64-linux.t3code-theme -L
```

Then make one case fail on purpose, confirm the build fails, and revert the
change.

Traps: no network or `$HOME` in the sandbox, so use `mktemp -d` under
`$TMPDIR`.

## Rollback

To undo the change:

1. Revert the PR.
2. Run `just p620`.

The activation step only writes the T3 Code theme setting, through the
supported CLI, and `omarchy.json`, which Omarchy writes on every theme switch
anyway. Nothing needs cleaning up.

To keep a theme picked inside T3 Code, revert or set `themeId`. With the
module in place, an in-app pick reverts at the next boot or switch, by design.
