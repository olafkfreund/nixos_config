# Plan: login cover lifts through the normal path on p620

## Approved decisions (from the spec)

Line numbers in this plan are for the base tree `$S` (see below), not for the
timing-patched tree that #3165 logged from.

- **The reaper's scan becomes a check.** The startup reaper's
  `registry.rescan()` (`services/PluginRegistry.qml:700-705`) becomes
  `registry.rescan(true)`:
  - the check sets its own `checking` flag, not `scanning`, so
    `desktopReady` (`BackgroundIntro.qml:21`, reads `scanning` only) is not
    held;
  - `rescan()`'s guard (`:753`) and the shell's three guards test
    `scanning || checking`: `rescanPlugins()` (`shell.qml:1576`),
    `reloadPlugins()` (`:1584`) and `finishPluginReload()` (`:1597`);
  - requests that arrive during a check go pending, as during a scan today.
- **Skip when unchanged.** The check skips only when it exited 0 and its
  stdout equals the stored output of the last successful full scan
  (`hasScanOutput`). Then the registry:
  - clears `checking`;
  - sets `lastScanSkipped = true`;
  - emits `scanFinished()` only.

  There is no `pluginsChanged()`, and `installedPlugins` and
  `registryRevision` stay untouched.
- **Publish when changed.** When the output differs, the registry sets
  `scanning = true` (before clearing `checking`) for the synchronous parse.
  Then it parses and publishes exactly as today.
- **Clarification of the spec: no snapshot means a full scan.** A
  `rescan(true)` with no `hasScanOutput` is an ordinary full scan under
  `scanning` for its whole run, because there is nothing to compare against.
  The spec's "only for the synchronous parse" applies to a real check.
- **A failed full scan invalidates the snapshot.** A non-zero exit sets
  `hasScanOutput = false`, so the next check cannot skip against output older
  than what is installed. It still publishes, as today. The comparison state
  is finalised before `parseScanOutput()` emits its signals.
- **A skipped check never touches a reload.** `onScanFinished`
  (`shell.qml:1615-1631`) keeps its pending-reload branch first. Then, when
  `lastScanSkipped` is true:
  - **a reload is in flight** (`pluginReloading` true): return without
    changing anything. `pluginReloading` true with no pending reload means
    `reloadPlugins()` queued `finishPluginReload()` and it has not run yet:
    had it run during the check, it would have set `pluginReloadPending`. It
    then runs with no scan or check active, clears the component cache and
    starts the full scan of that reload;
  - **otherwise:** skip the three syncs, still drain `pluginRescanPending`,
    and return.

  A full scan takes the existing path unchanged.
- **Existing gaps stay.** The check is dropped if the first scan is still
  running; the watcher starts without waiting for its watches; a scan whose
  script masks a read error can exit 0.
- **Owner decisions (spec approval, 2026-11-23):**
  - the check does not hold `desktopReady`;
  - the fix is carried in nixarchy, and an upstream PR to `basecamp/omarchy`
    is the owner's separate call.
- **Phase 1, p620 only, in this repo:** in `postInstall` of an
  `overrideAttrs` on `programs.nixarchy.package`, in order:
  1. `hosts/p620/nixos/omarchy-3181-reaper-check.patch`;
  2. `hosts/p620/nixos/omarchy-startup-timing.patch`, gated by
     `OMARCHY_STARTUP_TIMING=1`.

  Both apply with `patch -d $out/share/omarchy -p1 --forward --fuzz=0`. The
  host also gets `environment.sessionVariables.OMARCHY_STARTUP_TIMING = "1"`.
- **Phase 2 gate:**
  - the login log shows `check-skip unchanged`, with no sync after it;
  - nothing is missing;
  - the behaviour checks pass.

  `fade-start normal` is not a gate. If the timer still wins, the intent's
  outcome stays open and a follow-up issue is opened.

         scanFinished()
         return

## Deviations

- **Step 5, behaviour check 4:** the reload logged `reloading true` then
  `reloading false`, but the edited QML did not run in the bar widget already
  on screen. That is Omarchy's known stale-component behaviour from before this
  fix, so it was reported on #3181 and not treated as a gate failure.
- **Step 6, deploy:** an owner nhs run built p620 before the step-6 merge and
  switched it, so the lead ran `just p620` again from main afterwards.
- **Step 7, two patches (nixarchy #1923, PR #1924):** nixarchy main pins
  Omarchy v4.5.0, not the edge tree `$S`, and v4.5.0 has no shell-level
  `rescanPlugins()`. The fix's first `shell.qml` hunk moved to
  `1923-rescan-guard.patch`. `default.nix` applies it only when `shell.qml`
  has that function (a `grep`, as agy's review suggested, not the version).
  The rest is `1923-reaper-check.patch`, which applies under both pins. Both
  pins were built. On edge the tree is byte-identical to Phase 1's, minus the
  timing lines. The lead finished the step after the coder handed it back.
- **Step 7, edge publish:** the lead dispatched `omarchy-edge` by hand. The
  previous run had been interrupted (exit 130) by the p620 switch.
  - That run then failed `checks.install-phase-budget`: edge's installPhase was 534 bytes over budget.
  - nixarchy #1926 moved the #1923 and #901 comments into `pkgs/AGENTS.md`.
  - Edge `982037b0` (Omarchy quattro `fef807e`) then published the fix. Step 8 pins that.
