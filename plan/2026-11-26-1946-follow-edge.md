# Plan (nixos_config half): bump after green edge, razer follows, p620 built but off

Approved by the owner (2026-11-26). Decisions: the spec's sections 1-4 on the nixos_config side, with the owner's scope:
p620's unattended activation is an option defaulting to false.

## Steps

1. The bump workflow (section 1), the guarded upgrade module on the existing nixos-upgrade timer (sections 2-3: gates,
   staging, health check, rollback, pause flag), enabled for razer and present-but-off for p620, notification (section
   4), and the fixtures section 4 names. → the fixtures fail under their mutations and pass; `nix build` of both hosts'
   toplevels evaluates; actionlint.

2. (Deviation, by the lead.) Codex stopped before the session/rollback health checks, the runner drain acknowledgement
   and the lock shared with manual deploys were finished, and found razer wired for unattended activation regardless.
   The lead found the razer path also ignored `autoActivate`, so the flag could not have stopped it: `may_activate` now
   gates every host, with a fixture that fails without it. Both hosts keep the module imported and disabled. What goes
   live is the bump workflow; razer's switch waits for the missing gates, a follow-up under #1946.

3. (Follow-up, by the lead; Codex and agy review.) The two gates razer needs. A manual deploy and the guarded upgrade
   refuse each other: `deploy_conflict` stops activation while another process runs `nixos-rebuild`,
   `switch-to-configuration` or `nh os`, and the `razer`, `p620` and `deploy-via-p620` recipes depend on
   `_no-guarded-upgrade`, which refuses while the target's `nixos-upgrade.service` is active or a transaction is open
   (and when it cannot ask). A Hyprland session running before the switch must still run after it, or the switch rolls
   back (`session_regressed`). Each has a fixture that fails with the rule removed. The runner drain stays out: p620's
   activation remains off. Enabling razer is a separate one-line change, after review.

4. (Rework after the Codex and agy review of step 3, which found it would not have protected anything: `pgrep -x
   Hyprland` never matches the NixOS process `.Hyprland-wrapped` (its comm, cut at 15 characters), a oneshot upgrade reads `activating` so the probe passed
   mid-run, and the transaction file is root-only.) One lock on the target, `/run/lock/nixos-deploy.lock`:
   `scripts/deploy-hold.sh` takes it for every switching recipe through a transient unit, and the guarded upgrade takes
   it around reconciling and from its last gate through verify or rollback. Sessions are logind Wayland ids, so a
   replaced session counts as lost. `deploy_conflict` matches the program name only. A failed rollback keeps its
   transaction and exits non-zero. Both hosts get the window and idle gate; Home Manager must have finished. Proven live
   on razer: a free hold succeeds and releases, a second hold is refused, and a hold is refused while the lock is held as
   the guarded upgrade holds it.

5. (After the second Codex and agy review.) Each hold names its own unit, so flock alone decides who holds the lock
   (agy: a fixed name let one run take another's hold for its own); `deploy-hold.sh` watches its hold and stops the
   deploy if the hold ends, only when it is definitely gone, since a switch can drop the network (Codex: a 6 h expiry
   left a deploy unguarded); signals release it. Sessions are logind `Class=user` and any Type, so the SDDM greeter no
   longer counts and an SSH or console login blocks; the idle report must name the one live session.
   `switch-to-configuration`'s exit status triggers rollback; the old system gets a GC root for the transaction; a
   rollback after a failed activation exits 1; the bus is told only under the lock; `deploy_conflict` sees `.X-wrapped`
   names and interpreter flags. Fifteen fixtures; four live scenarios on razer pass, including the watchdog stopping a
   deploy 10 s after its hold was stopped.
