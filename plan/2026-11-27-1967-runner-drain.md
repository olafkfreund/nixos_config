# Plan: p620 switches itself after a green edge, without killing CI jobs

Revision 2. It folds in the Codex and agy reviews of revision 1. Every
interface between the steps is fixed in the spec's section 1 (files, schema,
states) and section 3 (journal phases), so steps 1, 2 and 4 can run in
parallel, and step 3 codes against the same contract.

Work in the worktree `/mnt/data/vmtest/wt-nc-drain`, on branch
`feat/1967-runner-drain`. Each implementer gets its own worktree off that
branch; the lead merges the results. Implementers never stage, commit, push,
build, deploy or switch, and never touch the live runner services. The lead

## Tests

The verifications in steps 1 to 5.

## Rollback

`autoActivate = false` on p620 stops unattended switching at once. Dropping
the package override returns nixpkgs' runner. Reverting the module removes the
condition. If a marker is left behind, the next run's recovery reopens the
runners.

## Deviations during implementation

- Step 1: the first patch broke three existing listener tests, because a
  1-second drain poll could win the race at shutdown. The loop now awaits a
  pending message once its token is cancelled. All 1127 L0 tests pass. With
  the admission check removed (the proof variant), only the drain test fails:
  `Expected: 1, Actual: 2` dispatches.
- Step 2: `import` is used, not `callPackage`, because the upstream module's
  `.override { nodeRuntimes; }` must reach `github-runner`. `TimeoutStartSec`
  is 5min; the unit is `simple`, so a start timeout never covers a job.
- Step 3, which went to the coder after Codex's edit guard refused the file:
  - the journal also carries `candidate` and `invocations`;
  - defer also starts units that are `failed`, and waits up to 60 seconds for
    a listener that is exiting;
  - recovery ends the run;
  - a missing ack waits out the deadline rather than deferring early;
  - the env overrides are named `GUARDED_*`.
  53 unit tests pass. 42 guards were each broken in turn, and every break
  turned the suite red.
- Review round 1 (Codex, agy, a fresh Opus review). All three found the same
  bug: the listener checked that a request existed, then read it, and a defer
  removing it between the two calls could cancel a running job. Fixes:
  - Patch (Codex): a missing or unreadable request means cancel. Admission is
    checked right before the broker acknowledgement and acquisition. The poll
    leaves an outstanding offer in the loop. The listener rechecks for
    cancellation after its exit ack, and catches any exception from the
    cancelled poll. The L0 fixture now covers each case. RunnerL0 passes 17
    of 17; with the proof variant, only the drain test fails.
  - Orchestration (coder): phase `cancelling`; journal fields `settled` (kept
    across reopen retries) and `unresolved`. A defer clears the journal only
    when every runner is resolved, either by `cancelled` for this request, by a
    new active invocation, or at the 60 s settle timeout as a runner that never
    saw the request: on its original invocation, its request removed, no ack
    for this id. The listener writes `draining` as soon as it reads a request,
    which is what makes that last case safe. An unresolved defer exits 1. Each
    runner's request is handled on its own, so one broken drain path cannot
    keep the others closed. Readiness rechecks invocations after the GitHub
    call. deploy-hold.sh also refuses on an orphan marker. 60 unit tests.
  - Harness (agy and lead): the barrier sits after the in-lock gate, at the
    journal write. The orchestration drains only when every runner was idle at
    that gate, so the scenarios put their job in the window between the gate
    and the request. Every attempt writes its own record, and an unreadable
    record still counts. The harness checks `ConditionResult=no` explicitly
    and records GitHub status transitions. Kills target the python PID at the
    real transitions. The script runs unmodified.
- Review round 2 (Codex, agy, Opus). The fixes:
  - Patch (Codex):
    - a faulted poll no longer wedges the listener (agy);
    - an ack write failure stays inside the listener, and a failed `draining`
      write means the listener never acts on that request;
    - acquisition is guarded on whether the broker ack succeeded;
    - a poll still pending at a session restart reaches normal handling.
    RunnerL0 passes 18 of 18, and the full suite 1128 of 1128 under nix.
  - Orchestration (coder):
    - the transaction is deleted only after `settled-commit` is written, and
      recovery handles all four journal and transaction combinations;
    - a new invocation is not counted as resumed while its own ack says
      `draining` or `exited-*`;
    - an invocation that changes mid-drain defers at once;
    - a runner whose request was never written resolves once it is active;
    - runners are judged at the end of the settle window;
    - an unparseable journal is handled as an orphan;
    - `save()` fsyncs;
    - a new `<host> recover` mode runs at boot (`guarded-upgrade-recover`,
      p620 only). It never changes generation: with a transaction left over,
      the runners stay closed until the next timer run handles it, so a reboot
      mid-transaction leaves CI offline until 04:00.
    77 unit tests pass.
  - Harness (agy):
    - an unreadable ack directory reads as unreadable;
    - the live counter uses the same reader as the unit tests;
    - scenarios (a) to (c) use guest-side transition timestamps.
- Review round 3 found nothing high. The fixes:
  - Patch (Codex):
    - an idle session restart cancels a retained empty poll;
    - a failed `cancelled` ack stays pending and is retried.
    RunnerL0 passes 47 of 47; the proof variant fails only its admission test.
  - Orchestration (coder):
    - a failed rollback-root unlink no longer erases a recorded commit;
    - `valid_journal()` checks every field recovery reads, and an invalid or
      `null` journal goes through orphan recovery;
    - boot recovery exits 1 whenever it leaves the runners closed, so the unit
      shows the failure;
    - with `settled-commit` recorded, boot recovery finishes the cleanup and
      reopens, without changing generation.
    80 unit tests pass.
  - Harness (agy): scenario (f) compares against the guest-recorded
    `cancelling_at`.
- Documented behaviour, not fixed:
  - `system.autoUpgrade.persistent` fires a missed 04:00 run at boot, and it
    races the recover unit for `STATE/lock`. Whichever loses waits, so a
    leftover uncommitted transaction can wait one more night.
  - The 5-minute `TimeoutStartSec` applies to every runner start, not only the
    upgrade's own. A registration that hangs leaves that runner down until it
    is restarted.
