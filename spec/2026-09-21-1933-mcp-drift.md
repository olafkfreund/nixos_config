# Spec: MCP servers do not follow a rebuild

## Design

The insight that makes this cheap: **`~/.claude.json` already points
`ollama-code` at a symlink, not at a store path.** If Nix owns that symlink
and repoints it on every activation, the live registration follows a rebuild
automatically — without writing a single byte to a file Claude Code owns, and
without touching the Syncthing-synced `~/.claude` at all. The gcroot lives
under `~/.local/state/nix/`, which is neither.

So the answer to open question 1 is **both, but in that order**: reconcile
where it costs nothing (the symlink), detect where reconciling would be
invasive (the five store-path-pinned servers).

### 1. Nix-managed gcroots for every locally-built MCP server

A home-manager activation step that, for each MCP server this repo builds
from `customPkgs`, runs:

```bash
nix-store --add-root "$HOME/.local/state/nix/gcroots/<name>" \
  --realise <store-path-of-the-package>
```

Verified behaviour, tested both directions before this spec was written:
`--add-root` **repoints an existing root in place**, needs no `sudo`, and
registers the link under `/nix/var/nix/gcroots/auto/` so Nix treats it as a
real indirect root. The existing `ollama-mcp` root has been registered that
way since 2026-08-27.

This gives two things at once:

- the registered command path resolves to the current build after a rebuild,
  so a package or docstring change actually takes effect (open question 3:
  the gcroot is **adopted**, not removed);
- the binary becomes a genuine GC root, closing the latent
  garbage-collection failure (open question 2, for the servers we build).

`ollama-code` is fixed outright by this, because its registration already
points at the gcroot path.

### 2. A drift detector

The five servers pinned to frozen `/nix/store` paths — `agent-bus`,
`mcp-nixos`, `mcp-server-fetch`, `mcp-server-git`, `nixos` — cannot be fixed
by the symlink trick, because their registrations name store paths directly.
Repointing them means rewriting `~/.claude.json`, which is the thing #398
deliberately avoided.

Instead: a `just` recipe that compares each registered MCP command against
what the current configuration builds, and reports every divergence by name,
with the exact `claude mcp remove` / `claude mcp add` pair that would fix it.

It reports; it does not rewrite. The problem this issue exists to solve is
that the drift was *silent*, not that it was manual.

It must also flag a registered command path that **no longer exists** — the
post-garbage-collection case, which presents as a server that mysteriously
stops working.

### 3. Do not rewrite `~/.claude.json`

Stated as a design decision so a later pass does not quietly adopt it:
automatic reconciliation of the live file is rejected. It holds runtime state
this repo did not create, Claude Code writes to it concurrently, and #398
already established that fighting it causes EACCES failures. A detector plus
an explicit command is the honest boundary.

## Alternatives rejected

- **Rewrite `~/.claude.json` from activation.** Rejected above: concurrent
  writer, foreign state, and the #398 precedent.
- **Make `settings.local.json` a nix-store symlink.** Rejected by #398 —
  EACCES when Claude Code writes to it — and by the Syncthing constraint.
- **Register MCP servers by a `$PATH` name instead of an absolute path.**
  Would decouple them from the store entirely, but loses the GC root and makes
  which build is running unknowable. The gcroot keeps both properties.
- **Auto-repoint the five store-pinned servers by editing the live file
  once.** Same objection as rewriting it, and a one-off migration that has to
  run on two hosts is worse than a check that tells you when it matters.
- **Do nothing but document the resync.** Rejected: the failure is silent, and
  three changes have already shipped inert because of it.

## Risks

- **A repointed gcroot changes which binary a *running* server uses only on
  restart.** Activation updates the symlink; a Claude Code session already
  running keeps its process. The detector and the docs must say that a session
  restart is required, or a change will again look inert.
- **`--add-root` on a path a user created by hand.** The `ollama-mcp` root was
  not created by this repo. Adopting it means activation now overwrites it. If
  someone was relying on it pinning an old build, that pin disappears. Judged
  acceptable — pinning an old build silently is the bug.
- **Activation cost.** One `nix-store --add-root` per locally-built MCP
  server, on every activation. Small, but it is in the activation path on p620
  and razer.
- **The detector can go stale.** If a new MCP server is added to the config
  and not to the detector's list, it is unchecked. The detector should derive
  its list from the configuration rather than from a hand-written array.
- p510 does not run Claude Code and is unaffected.

## Verification

Every check below observes the running system. "The Nix attribute now says X"
is not acceptable evidence in this issue — that is what produced the three
inert changes.

1. Before/after on the gcroot: record `readlink -f
   ~/.local/state/nix/gcroots/ollama-mcp`, rebuild and switch, then confirm it
   resolves to the newly built store path.
2. Confirm it is still a real root afterwards: `nix-store --query --roots
   <new path>` names the gcroot.
3. **The end-to-end check that this whole issue is about:** restart the MCP
   server, load the live `ollama_code` tool schema, and confirm it contains
   the cloud-model text added in #1931. That text is currently absent; its
   appearance is the proof the drift is fixed.
4. Run the detector against the current machine and confirm it names exactly
   the five store-path-pinned servers, and that its suggested
   `claude mcp` commands are correct.
5. Break one deliberately — point a gcroot at an older build — and confirm the
   detector reports it rather than passing.
6. `just check-syntax`, `just test-host p620`, and a build of razer's
   configuration since it also runs Claude Code.
7. p510: not built, not deployed.
