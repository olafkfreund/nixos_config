# Spec: MCP servers do not follow a rebuild

## Design

**Revised after the first draft was approved.** The first draft proposed a new
gcroot mechanism plus a drift detector, and explicitly rejected reconciling
`~/.claude.json` from activation. That rejection was wrong: **this repo
already does exactly that, and it works.**

`home/development/claude-code-mcp.nix:299` defines
`home.activation.claudeSharedMcpServers`, which writes declared servers into
the live `~/.claude.json` on every activation. It already handles every
objection the first draft raised against the approach:

- **Concurrent writer / foreign state** — it merges with
  `jq '.mcpServers = ((.mcpServers // {}) + $d[0].mcpServers)'`. The `+`
  replaces each *declared* server wholesale and leaves undeclared ones
  untouched. The existing comment explains why `*` would be wrong: deep-merging
  an `{type:"sse",url}` with an `{type:"stdio",command}` leaves a dead `url`
  behind.
- **Failure safety** — it writes to a temp file, copies the original to
  `$target.bak`, and on any failure leaves the file unchanged with a warning.
- **#398** — that issue is about `settings.local.json` not being a read-only
  *symlink*. It is not an objection to writing `~/.claude.json` from an
  activation script, which is a different file and a different mechanism.

Verified: `agent-bus` is declared in that block, and its registered command in
`~/.claude.json` is byte-identical to what the current configuration builds.
It does not drift. The first draft misclassified it as "frozen" from a
snapshot, without checking whether anything maintained it.

**So the actual bug is much narrower than the intent implies:
`ollama-code` is not in that block.** It exists only in the seed template,
which is written once and never re-read. Everything else follows from that.

### 1. Move the locally-built MCP servers into `claudeSharedMcpServers`

Add `ollama-code` to the declared set in the activation block, alongside
`agent-bus`. Its command becomes the current
`${pkgs.customPkgs.ollama-mcp}/bin/ollama-mcp` store path, reconciled on every
activation exactly as `agent-bus` already is.

The same applies to any other MCP server this repo builds from `customPkgs`
whose registration would otherwise be frozen at first write.

This fixes the reported bug outright. A package or docstring change reaches
the live registration at the next activation.

### 2. The remaining store-pinned servers

`mcp-nixos`, `mcp-server-fetch`, `mcp-server-git` and `nixos` are registered
with frozen store paths and are **not** declared in the activation block.
Two of them are the same package at different versions (`mcp-nixos` 2.3.1 and
3.0.1 are both registered), which is the drift visible in the file.

Whether each of these should be declared is a per-server question: some may be
registered by hand on purpose. The spec's position is that any MCP server
**this repo builds or declares** belongs in the activation block, and anything
registered by hand stays the user's business. The plan enumerates which is
which rather than assuming.

### 3. The garbage-collection exposure

The intent noted that frozen store paths are not GC roots. This remains true
for hand-registered servers, and is now a smaller problem: a server declared
in the activation block is repaired by the next activation, so a collected
path is self-healing rather than permanent.

The `nix-store --add-root` mechanism from the first draft is **dropped**.
Verified working, but unnecessary once the registration itself tracks the
config. The existing `~/.local/state/nix/gcroots/ollama-mcp` root, created
outside this repo, becomes vestigial once `ollama-code`'s registration points
at a store path directly; the plan decides whether to leave or remove it.

### 4. A drift check, reduced in scope

Still worth having, but no longer load-bearing: a `just` recipe that compares
each registered MCP command against what the configuration builds, flags a
registered path that no longer exists, and names anything declared-but-drifted.
With change 1 in place this should normally report nothing, which is the point
— it turns a silent failure into a loud one if the mechanism ever breaks
again.

## Alternatives rejected

- **A new `nix-store --add-root` gcroot mechanism** (the first draft's
  centrepiece). The behaviour was verified — `--add-root` repoints an existing
  root in place, needs no `sudo`, registers under `/nix/var/nix/gcroots/auto/`
  — but it is a second mechanism solving a problem the existing activation
  block already solves. Rejected as redundant.
- **A detector as the primary fix.** Rejected: reconciliation is available and
  proven here, so detection alone would leave a manual step for no reason.
- **Make `settings.local.json` a nix-store symlink.** Rejected by #398 —
  EACCES when Claude Code writes to it — and by the Syncthing constraint.
- **Register MCP servers by a `$PATH` name instead of an absolute path.**
  Loses the ability to know which build is running.
- **Do nothing but document the resync.** Rejected: the failure is silent, and
  three changes have already shipped inert because of it.

## Risks

- **A reconciled registration only takes effect on restart.** Activation
  rewrites `~/.claude.json`; a Claude Code session already running keeps its
  spawned process and its loaded tool schemas. This must be said out loud in
  the docs and in the drift check's output, or someone will rebuild, see no
  change, and conclude the fix failed — the same confusion that produced this
  issue.
- **Writing `~/.claude.json` is writing a file Claude Code owns.** The
  existing block's safeguards are inherited, not reinvented: temp file,
  `.bak` copy, `+` merge that leaves undeclared servers alone, warn-and-leave
  on failure. Adding a server to that block does not widen the blast radius,
  but it does mean `ollama-code`'s registration is no longer the user's to
  edit by hand — an activation will put it back.
- **The file is Syncthing-synced.** Two hosts activating against the same
  synced `~/.claude.json` could interleave. This risk already exists for
  `agent-bus` and is not made worse here, but the plan should not pretend it
  is absent.
- **Declaring a hand-registered server would take it over.** Anything added to
  the block stops being editable by hand. The plan enumerates which of
  `mcp-nixos`, `mcp-server-fetch`, `mcp-server-git`, `nixos` this repo
  actually builds before declaring any of them.
- **The drift check can go stale.** It should derive its list from the
  configuration rather than a hand-written array.
- p510 does not run Claude Code and is unaffected.

## Verification

Every check below observes the running system. "The Nix attribute now says X"
is not acceptable evidence in this issue — that is what produced the three
inert changes.

1. Before/after on the registration: record
   `jq -r '.mcpServers."ollama-code".command' ~/.claude.json`, rebuild and
   switch, then confirm it now names the store path the current configuration
   builds — the same equality that already holds for `agent-bus`.
2. Confirm undeclared servers survived the merge: the set of keys under
   `.mcpServers` before and after must differ only by what was declared, and
   `$target.bak` must exist.
3. **The end-to-end check that this whole issue is about:** restart the
   session, load the live `ollama_code` tool schema, and confirm it contains
   the cloud-model text added in #1931. That text is absent today; its
   appearance is the proof. Reading `server.py`, or reading `~/.claude.json`,
   is not sufficient — a registration pointing at the right path still proves
   nothing about what the model receives.
4. Run the drift check on the current machine and confirm it reports the
   genuinely-drifted servers and not `agent-bus`, which is known-good.
5. Break one deliberately — hand-edit a registration to an older store path —
   and confirm the check reports it rather than passing, and that the next
   activation repairs it.
6. `just check-syntax`, `just test-host p620`, and a build of razer's
   configuration since it also runs Claude Code.
7. p510: not built, not deployed.
