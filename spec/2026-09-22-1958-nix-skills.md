# Spec: Install nix-skills on every host

## Design

Three files, plus the lock. Every step below was tried on 2026-09-22 with
uncommitted edits, then reverted.

### 1. Flake input

`flake.nix`, next to `claude-skills-borghei`:

```nix
nix-skills = {
  url = "github:olafkfreund/nix-skills";
  inputs.nixpkgs.follows = "nixpkgs";
  inputs.home-manager.follows = "home-manager";
};
```

`nix flake lock` adds exactly one node with a rev (nix-skills `86609598b`,
which includes #18's `agents` option). Its `nixpkgs` and `home-manager`
point at ours, so there are no second copies. `inputs` already reaches
Home Manager through `extraSpecialArgs`.

### 2. Module

`home/development/claude-code-skills/default.nix`, which p620, razer and
p510 all load today. Import the module at the top level, and enable it
inside the existing `mkIf cfg.enable` so it follows the same switch as
the other declarative skills:

```nix
imports = [ inputs.nix-skills.homeManagerModules.default ];
...
programs.nix-skills = {
  enable = true;
  agents = [ "claude" "codex" "antigravity" ];
  skills = [ "nix-language" "nixpkgs-development" "microvm-nix" "home-manager" ];
};
```

A short comment records why `devenv-project` and `nixos-wiki` are left out,
and that Gemini CLI's `~/.gemini/skills` is not covered (the intent's
decision: Antigravity only).

Result, measured on all three hosts: 12 `home.file` links, 4 skills × 3
directories (`.claude/skills`, `.agents/skills`,
`.gemini/config/skills`). No names collide with existing skills.

### 3. Syncthing exclusion, extended to `.gemini/config/skills`

`home/syncthing-stignore.nix` excludes Home Manager-owned skill links from
sync, because a store symlink replicated to another host dangles (the
2026-09-13 incident). It covers `.claude/skills/*` and `.gemini/skills/*`.
The trial showed that `.claude` is fine, since the four new
`/skills/<name>` lines appear in the rendered `.claude/.stignore`.

**It does not cover `.gemini/config/skills/*`.** The Gemini allowlist syncs
`!config/**`, so the four Antigravity links would replicate and dangle.
This is the gap the intent said to verify.

Fix: `managedSkillIgnores` takes the synced subdirectory as a second
argument, and `.gemini` calls it twice:

```nix
managedSkillIgnores = folder: subdir:
  lib.concatMapStrings (name: "/${subdir}/${name}\n") (lib.unique (map
    (path: lib.elemAt (lib.splitString "/" path)
      (lib.length (lib.splitString "/" "${folder}/${subdir}")))
    (lib.filter (lib.hasPrefix "${folder}/${subdir}/") (lib.attrNames config.home.file))));

${managedSkillIgnores ".claude" "skills"}
${managedSkillIgnores ".gemini" "skills"}${managedSkillIgnores ".gemini" "config/skills"}
```

This is still derived from `home.file`, so any later Home Manager skill
under either path is covered automatically. The existing
`~/.gemini/config/skills` entries are real directories, not links, so they
keep syncing as before. `~/.agents` is not a Syncthing folder.

## Alternatives rejected

- **Install without the stignore change.** The Antigravity links would
  ping-pong between hosts and dangle.
- **Drop `antigravity` from `agents`.** That loses the agent the intent
  kept, to avoid a small, general fix.
- **Hand-list the four new paths in the stignore.** The file exists so
  nobody has to remember to do that; deriving the list is its design.
- **Install all six skills.** The intent excluded `devenv-project` and
  `nixos-wiki`.
- **A separate module file for nix-skills.** The existing skills module is
  where every declarative skill lives, and it is loaded on exactly the
  hosts we want.

## Risks

- **The stignore change silently alters existing output.** The refactor
  must render `.claude` and `.gemini` `skills/` lines byte-identically.
  Verify by diffing both rendered stignore texts against main; the only
  additions should be the new `/config/skills/...` lines and the four
  `.claude` lines.
- **Syncthing already replicated a link.** Nothing is linked until the
  first activation, and the stignore ships in the same generation, so
  there is no window. Verify on the second host after both are deployed:
  no dangling links under `~/.gemini/config/skills` or `~/.claude/skills`.
- **p510.** Deploying there needs the user's go-ahead, which is given. The
  managed guard may block the command, in which case the user runs it.
- **A future nix-skills update renames a skill.** The `skills` enum fails
  evaluation loudly, which is the desired behaviour.

## Verification

- `nix flake lock` adds only `nix-skills` (1 new rev) and two follows.
- `nix eval` passes for p620, razer and p510, with the 12 links listed.
- The rendered `.claude/.stignore` and `.gemini/.stignore` diffs against
  main show only additions: 4 `/skills/<name>` lines and 4
  `/config/skills/<name>` lines.
- `just test-host p620` and `just test-host razer` build.
- After deploying p620 and razer: each host has the 12 links resolving into
  its own store (`readlink -f` exists), and no dangling links under the
  synced skill directories on either host.
- p510, after the user's run: the same link check.
