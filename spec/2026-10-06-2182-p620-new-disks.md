# Spec: put p620's three new disks to use

## Design

Each disk is mounted **at the path its workload already uses**. The
configs for Docker, the runners and home directories keep their paths;
only the disk underneath changes. All three are ext4, declared by UUID
in `hosts/p620/nixos/hardware-configuration.nix`, with `noatime`.

| Disk (by-id) | Label | Mount | Workload | Size today |
| ------------ | ----- | ----- | -------- | ---------- |
| `nvme-Fanxiang_S501Q_1TB_26060256623000377` | `home` | `/home` | Home directories | 208 GB |
| `ata-MS4SC2JH2ORA480G_S2UBNX0J100050` | `scratch` | `/var/lib/nix-build` | nix `build-dir`, nix-daemon `TMPDIR`, runner VM disks | ~0 idle, ~64 GB peak for 2 runners |
| `ata-MTFDDAK256TBN-1AR1ZABHA_UFZMN01J186ZIF` | `docker` | `/mnt/img_pool` | Docker `dataRoot = "/mnt/img_pool/docker"`, k3d backup | 19 GB |

### Why each pairing

- **NVMe → `/home`**: decided at intent approval. 208 GB on a 1 TB disk
  leaves room. The root Kingston keeps only the OS and `/nix/store`, and
  about 208 GB comes back to `/` once the old copy is deleted.
- **480 GB → build scratch**: ~54 TB written with only 1% wear marks it as
  a high-endurance (server-pull) SSD. Sustained build and
  VM-install writes are exactly what it is made for. Mounting it at
  `/var/lib/nix-build` means `services.nixarchy-runner.buildDir` does not
  change. The runner module already sets both `nix.settings.build-dir` and
  the nix-daemon `TMPDIR` from it, and its tmpfiles rule creates the
  directory on whatever is mounted there.
- **Micron 256 GB → Docker**: decided at intent approval (wipe it); this is
  the reuse. Mounting at `/mnt/img_pool` keeps `dataRoot` unchanged.
  Docker's `HostConfig` holds absolute paths, so this avoids recreating
  containers. It also takes Docker and k3d image churn, which grows without
  bound (see the k3d image-bloat history), off both `/` and the build disk.

### Runner instances 2 → 4

`hosts/p620/configuration.nix:71-75`: `instances = 4`, and the stale
"failing SSD" comment is replaced. Four runners peak at about 128 GB on a
440 GB filesystem, which leaves room for ordinary nix builds.

### Missing-disk behaviour (intent: "fails visibly")

- **`/home`**: no `nofail`. If the disk is missing, boot stops in emergency
  mode. The alternative is a login into an empty home directory, which then
  starts writing a fresh profile on `/`. That is worse.
- **`/mnt/img_pool`**: `nofail`, plus
  `systemd.services.docker.unitConfig.RequiresMountsFor = [ "/mnt/img_pool" ]`
  in `hosts/p620/configuration.nix`. Docker refuses to start, rather than
  starting on a blank data root that k3d would then repopulate on `/`.
- **`/var/lib/nix-build`**: `nofail`, and it **degrades to `/`** (today's
  behaviour). That is deliberate. Making nix-daemon require the mount would
  mean the host cannot rebuild itself to fix the problem.

### I/O scheduler fix (found while scanning)

`hardware-configuration.nix` sets BFQ with `KERNEL=="nvme0n1"`. That name
now belongs to the new Fanxiang, so the root Kingston (now `nvme1n1`)
silently lost BFQ this boot, and `nix.daemonIOSchedPriority` no longer
protects the desktop. The fix matches by kernel pattern
`KERNEL=="nvme[0-9]n1"`, so both NVMe disks get BFQ and enumeration order
stops mattering. `/home` benefits too: Syncthing and Chrome share it with
the desktop. The scratch SATA disk keeps `none`; nothing interactive
shares it.

### Data migration (one downtime window, one reboot)

1. **Prepare (live)**:
   - `blkdiscard -f` the Micron by its by-id path (ZFS keeps labels at both
     ends of a partition, and discard clears them all).
   - Create one GPT partition per disk; `mkfs.ext4 -L home|scratch|docker`.
   - Pre-copy `/home` and `/mnt/img_pool` with `rsync -aHAXS --numeric-ids`
     to temporary mounts while logged in. That moves the bulk of the 208 GB
     ahead of the downtime.
2. **Config**:
   - Commit the `fileSystems` entries, the udev fix, `instances = 4` and the
     Docker `RequiresMountsFor`.
   - Build-test with `just test-host p620`.
   - Deploy with **`nh os boot`**, never `switch`: a switch would start the
     new mount units live and mount the new disk over a running `/home`.
3. **Cutover (offline)**: announce on the bus, then log out of the desktop.
   From a TTY as root:
   - `loginctl terminate-user olafkfreund`.
   - Stop `docker.service`, `docker.socket` and the runner units.
   - Run the final `rsync -aHAXS --numeric-ids --delete` delta for both trees.
   - Reboot.
4. **Reclaim (after verification, days later)**: bind-mount `/` at a
   temporary path and delete the hidden old `home/olafkfreund`,
   `home/ollama` and `mnt/img_pool/*` from underneath the mounts.

### Out of scope

- **Old `/mnt/games` Fanxiang (intent open question 3)**: left exactly as it
  is (mounted, `notrim`, dirty-page cap). No workload points at it after
  this change, so a failure costs nothing. The write test can be a separate
  issue.
- **`/mnt/data` boot dropout (intent open question 4)**: a hardware fix for
  the user (power lead and cables). This spec adds no guard. Its workloads
  (Ollama models, k3d storage) are unchanged.

## Alternatives rejected

- **NVMe as build scratch, `/home` stays on root**: rejected by the intent
  decision. Builds are also bursty and replaceable, while `/home` is
  read-latency sensitive all day.
- **New mountpoints (`/mnt/scratch`, `/mnt/docker`) and repointing the
  configs**: more lines for nothing. Repointing Docker's `dataRoot`
  invalidates the absolute paths in every container's `HostConfig`.
- **Docker on the 480 GB beside the builds**: a CI VM install and a k3d
  image pull would fight over one SATA link. The Micron would sit idle.
- **Btrfs or LVM spanning the disks**: one failure takes everything, and
  this host has no need for snapshots on these paths.
- **`nofail` on `/home`**: a missing disk would silently give the user an
  empty home on `/`.

## Risks

- **`/home` cutover** is the only step that can lose data. Mitigations:
  - The copy runs offline, and the final pass is a `--delete` delta.
  - The old tree stays on `/`, hidden under the mount, until verified.
  - Rollback is the previous generation plus a reboot.
- **ACLs and xattrs**: `/home/olafkfreund` carries ACLs (`drwx------+`).
  `rsync -A -X` preserves them. Verify with `getfacl` after cutover.
- **Syncthing**: `~/.claude` and `~/.gemini` are synced. Inode changes
  trigger a full rescan, not a resync; the paths do not change.
- **A wrong by-id target in `blkdiscard`**: irreversible. The plan step uses
  the by-id path with the serial, never `sdX` (letters shuffle every boot).
- **A runner peak above the 440 GB scratch** hangs a VM install rather than
  failing it. Watch `df /var/lib/nix-build` during the first nightly with 4
  instances; drop back to 3 if the peak exceeds about 350 GB.
- **p510** shares the runner pool and `nixarchy-runner.nix`, but this change
  touches only p620's host files. p510 is not built or deployed.

## Verification

- `just check-syntax` and `just test-host p620` build.
- After the reboot:
  - `findmnt /home /var/lib/nix-build /mnt/img_pool` shows the three new
    UUIDs.
  - `cat /sys/block/nvme*n1/queue/scheduler` shows `[bfq]` on both NVMe disks.
  - `nix config show build-dir` points to `/var/lib/nix-build`.
  - `docker ps -a` shows the same containers, and the k3d cluster comes up.
  - The desktop session, Syncthing (REST status of all folders idle) and
    `getfacl /home/olafkfreund` all match pre-cutover.
  - `systemctl list-units 'github-runner-nixarchy*'` shows 4 runners
    registered.
  - `df /` drops by about 208 GB after the reclaim step.
