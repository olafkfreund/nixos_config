# Spec: gliff remote desktop on razer and p510

## Design

### razer: point gliff-server at the Intel iGPU

gliff-server already supports this without a wrapper. Upstream
`crates/hypr-capture/src/lib.rs` (`render_node`) resolves the node as
`--render-node` → `$GLIFF_RENDER_NODE` → `/dev/dri/renderD128`.

`hosts/razer/nixos/nixarchy.nix` gets:

```nix
environment.variables.GLIFF_RENDER_NODE = "/dev/dri/by-path/pci-0000:00:02.0-render";
```

- The `by-path` link is keyed on the PCI address, which is fixed on this
  hardware (`00:02.0` = i915, `01:00.0` = nvidia). `renderD128`/`renderD129`
  are assigned in probe order and could swap. This resolves the intent's open
  question.
- `environment.variables` reaches the non-interactive shell that `ssh razer
  gliff-server --stdio` runs in. Checked: `MOZ_ENABLE_WAYLAND`, set the same
  way, shows up in `ssh razer 'echo $MOZ_ENABLE_WAYLAND'`.
- Tested on 2026-10-11 with the same value set in a wrapper. The session
  connects GPU→GPU and logs `first frame decoded`.

### p510: install gliff on its own

`hosts/p510/nixos/nixarchy.nix` keeps `preinstalls = false` and adds:

```nix
environment.systemPackages = [ inputs.nixarchy.packages.${pkgs.stdenv.hostPlatform.system}.gliff ];
```

This is the same derivation nixarchy's preinstalls use on p620/razer
(`/nix/store/bnq9y2x4…-gliff-0.3.1`, confirmed by eval), so all three hosts
stay at the same version. `inputs` is already a module argument in that file.
No render-node setting is needed: renderD128 is p510's only GPU.

p510 will still fail with `gbm: map: No such file or directory` until gliff
supports NVIDIA capture. This change installs it so it is ready then.

### Upstream

File one issue on omacom/gliff covering:

1. The server picks the first render node rather than the compositor's
   device on hybrid GPUs. Suggest asking Hyprland/aquamarine which device it
   renders on.
2. CPU capture cannot map NVIDIA GBM buffers, and there is no NVENC path.

## Alternatives rejected

- **Wrapper `gliff-server` script on razer.** It collides with nixarchy's
  `bin/gliff-server` in `system-path`, and it does more than the env var does.
- **`preinstallsExclude = [ "gliff" ]` plus a wrapped gliff on razer.** More
  code for the same effect.
- **Hard-coded `/dev/dri/renderD129`.** Probe order is not guaranteed.
- **`preinstalls = true` on p510.** Rejected by the intent: 4 GiB on a tight
  `/`.
- **A shared module (`features.gliff`).** Two hosts, one line each, with
  different settings. Nothing to share.

## Risks

- razer: if the PCI address changes (BIOS or hardware change), the link
  vanishes and gliff-server fails to open the node. The error names the path,
  so the cause is obvious. No other software reads `GLIFF_RENDER_NODE`.
- p510: adds one package of about 40 MB to the closure. gliff does not run as
  a service, so nothing runs unless a client connects.
- p510 deploy requires the user's explicit go-ahead at the time.

## Verification

1. `just test-host razer` and `just test-host p510` build.
2. `nix eval .#nixosConfigurations.razer.config.environment.variables.GLIFF_RENDER_NODE`
   returns the by-path value.
3. After razer is deployed: from p620, `RUST_LOG=info gliff
   olafkfreund@razer.tail833f7.ts.net` logs `connected … video=GPU→GPU`
   and `first frame decoded`, with no `capture error`.
4. After p510 is deployed (when approved): `ssh p510 command -v gliff-server`
   prints a path. The connection is expected to fail with `gbm: map` until
   upstream fixes it.
5. The upstream issue URL is linked from #2251.
