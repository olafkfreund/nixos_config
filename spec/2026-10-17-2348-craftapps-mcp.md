# Spec: register the Craft apps' MCP servers with Claude Code

These intent decisions were approved and are carried over:

- A `features.craftapps.mcp` switch, default `true`.
- Every enabled app gets a server.
- Claude Code only. Codex and Antigravity are left for later.

## Design

### Facts checked for this spec (2026-10-17)

- **Pin:** `flake.lock` pins nix-craftapps at `143197e`, which has no MCP
  option. The option landed in `e1d5783` (#4), and `edf59f8` is the
  current `main`.
- **Gating:** `features.ai.mcp.enable` is `true` on both p620 and razer,
  so `home/development/claude-code-mcp.nix` (`config = lib.mkIf
  enabled`) is active on both.
- **Users:** both hosts have one Home Manager user, `olafkfreund`.
- **Where Claude Code's servers come from:**
  `home.activation.claudeSharedMcpServers` builds a JSON `mcpServers`
  map and merges it into `~/.claude.json` with jq `+`. Declared servers
  are replaced whole, and undeclared servers are untouched. It runs on
  every activation, so store paths follow each rebuild.

### `flake.lock`

`nix flake update nix-craftapps`, which moves the pin to `edf59f8` or
later. Nothing else is bumped.

### `modules/desktop/craftapps.nix`

- **New option:**

  ```nix
  options.features.craftapps.mcp = lib.mkOption {
    type = lib.types.bool;
    default = true;
    description = "Register an MCP server for every enabled app (`<app>-cli mcp`).";
  };
  ```

- **Config:** inside the existing
  `programs.craftapps = { … }` block, add
  `mcp.enable = cfg.mcp;`.

The nix-craftapps module then does three things on these hosts:

- **Server set:** `programs.craftapps.mcp.servers` gets one
  `{ command = "<store>/bin/<app>-cli"; args = [ "mcp" … ]; }` per
  enabled app.
- **File:** it writes `/etc/craftapps/mcp.json`.
- **Home Manager:** it adds a `home-manager.sharedModules` entry that sets
  `programs.mcp` for `olafkfreund`. That writes `~/.config/mcp/mcp.json`,
  which is harmless here, since nothing in this tree reads it. It costs
  nothing to leave, and it serves any HM-integrated client added later.

### `home/development/claude-code-mcp.nix`

In the `claudeSharedMcpServers` `mcpServers` attrset, merge in the Craft
servers after the two declared ones:

```nix
mcpServers = {
  agent-bus = { … };
  ollama-code = { … };
}
// lib.mapAttrs (_: s: s // { type = "stdio"; })
  (osConfig.programs.craftapps.mcp.servers or { });
```

- **`type = "stdio"`** matches the other entries in this file.
- **`or { }`** keeps evaluation safe if a host ever drops the craftapps
  module import. With `features.craftapps` off, or `mcp = false`, the set
  is `{ }` and nothing changes.
- **The app names do not clash** with any existing server name. The
  existing names are `agent-bus`, `ollama-code` and the seed-template
  entries.

Add a short comment that this is a reconcile entry like the others (see
#1933). The comment says that removals are not reconciled; see Risks.

### No new flake check

Verification is by eval and by building the hosts. That repeats what
`nix flake check` in nix-craftapps already covers, so an extra check here
adds little.

## Alternatives rejected

- **Turning on Home Manager's `programs.claude-code.enableMcpIntegration`.**
  This tree does not manage Claude Code through that module.
  Introducing it would conflict with the existing `~/.claude.json`
  reconcile and the seeded `settings.local.json`.
- **Reading `/etc/craftapps/mcp.json` at activation time.** The same data
  is available at eval time through `osConfig`. Eval time is simpler and
  fails loudly at build rather than silently at activation.
- **`/etc/claude-code/managed-mcp.json`.** It takes exclusive control and
  would drop every other server. It is rejected by the intent.
- **Adding the servers to the seed template.** The seed is written once
  and never re-read, so the store paths would go stale (#1928, #1931,
  #1933).

## Risks

- **Removals are not reconciled.** The jq merge only adds and replaces.
  If an app is later excluded, or `features.craftapps.mcp` is set to
  `false`, its entry stays in `~/.claude.json` with a store path that is
  eventually garbage-collected. Claude Code then shows that server as
  failed. The fix is `claude mcp remove <app>`. This is the existing
  behaviour for every reconciled server, and the comment says so.
- **More servers.** There are 12 more entries. Claude Code starts them
  per session. Headless startup is quick (under a second each in the
  nix-craftapps check), but each session pays it.
- **Logs.** Headless servers write logs under `~/.config/<app>/logs`,
  per session.
- **Hosts:** p620 and razer only. The pin bump also changes the app
  versions on both. They move to the 0.7–0.12 releases already on
  nix-craftapps `main`. The CLI and MCP checks pass upstream, and the
  GUIs were run on 2026-10-17. On p620, cadcraft, deckcraft, designcraft,
  lightcraft and wordcraft open only on Wayland while Xwayland refuses
  connections. That is a desktop issue, not caused by this change.
- **razer** is built on p620. Its deploy needs razer online.

## Verification

1. **Eval:** `nix eval .#nixosConfigurations.p620.config.programs.craftapps.mcp.servers --apply builtins.attrNames`
   lists the 12 apps. The same holds for razer.
2. **Eval of the activation script:** the Home Manager
   `claudeSharedMcpServers` script for `olafkfreund` contains
   `photocraft-cli`.
3. **Build:** `nix build` of p620 and razer `system.build.toplevel`
   succeeds.
4. **Deploy p620,** after announcing on the agent bus. Then
   `jq '.mcpServers | keys' ~/.claude.json` contains the Craft apps.
5. **New Claude Code session:** `claude mcp list` shows each Craft app as
   connected. One tool call works, for example listing GridCraft's
   tools.
6. **Optional, needs razer online:** deploy razer via p620 and repeat
   step 4 there.
