# Spec: live theme switch reaches GTK apps

## Design

GTK, the GNOME interface keys and the KDE/Qt colour scheme each get one
owner: the theme engine (hyprchroma) at runtime. Stylix keeps everything
that cannot change at runtime.

What a theme switch writes today, and who undoes it at the next rebuild
(seen on p620, 2026-10-19):

| Setting | Written live by | Reset at rebuild by |
| --- | --- | --- |
| GTK colours, `~/.config/gtk-{3,4}.0/gtk.css` | hyprchroma, which adds an import of `hyprchroma.css` | Stylix HM `gtk` target: 88 `@define-color` rules below the import, which win |
| `org/gnome/desktop/interface` icon-theme, accent-color, gtk-theme | Omarchy `omarchy-theme-set-gnome`, hyprchroma | Stylix HM `gnome` target (dconf `icon-theme = "Papirus-Dark"`, `accent-color = "green"`) |
| `gtk-icon-theme-name` in `settings.ini` | nobody | Stylix HM `gtk` target (`Papirus-Dark`) |
| `~/.config/kdeglobals` (Qt/KDE colour scheme) | hyprchroma (`ColorScheme=Hyprchroma`) | Stylix HM `kde` target |
| Qt/KDE icon theme in `kdeglobals` | hyprchroma, but it skips this (see D3) | — |

Qt needs nothing extra. The Omarchy session sets
`QT_QPA_PLATFORMTHEME=gtk3` (Omarchy's `default/hypr/envs.lua`), so Qt
apps take their palette from GTK and their KDE colour scheme from
`kdeglobals`. Fixing those two fixes Qt.

### D1. Stop Stylix's GTK, GNOME and KDE targets in Home Manager

`Users/common/base-home.nix`, in the `stylix.targets` block (lines 61–66; `gtk.enable = true` is line 64):

```nix
gtk.enable = false;   # hyprchroma owns gtk.css (#2370)
gnome.enable = false; # hyprchroma + omarchy-theme-set-gnome own the interface keys
kde.enable = false;   # hyprchroma owns kdeglobals
```

The NixOS-level targets in `modules/desktop/stylix-theme.nix`
(`gtk.enable = true`, `gnome.enable`, `qt`) stay as they are. They write
system defaults (`/etc`, the system dconf database), and the user's own
values override those. The comment block above `gtk.enable` there is
corrected to say that hyprchroma owns the user's `gtk.css`.

`stylix.icons` (Papirus) stays. With the HM `gtk` and `gnome` targets
off, it no longer reaches the user settings. It still supplies the
Papirus package, which `Papirus-Dark` themes such as the one shipped by
Omarchy name in their `icons.theme`.

### D2. Remove the stale `gtk.css` once per host

When Home Manager stops managing `gtk.css`, it leaves the current
regular file in place, Stylix rules included. This is a one-time cleanup
per host, run after the first deploy, and adds no permanent code:

```bash
for v in 3 4; do printf '%s\n' '@import url("hyprchroma.css");' > ~/.config/gtk-$v.0/gtk.css; done
```

Run on p620, razer and p510. None of the hosts has hand-written rules in
`gtk.css` (checked on p620: 88 Stylix colours plus the import, nothing
else). razer and p510 are checked before the file is overwritten.

### D3. hyprchroma finds icon themes on NixOS

`sync-gtk-theme` and `sync-qt-kde-theme` only accept an icon theme found
in `/usr/share/icons` or `~/.local/share/icons`, which are Arch paths.
On NixOS, Yaru (installed by nixarchy) is in
`/run/current-system/sw/share/icons` and Papirus is in
`/etc/profiles/per-user/<user>/share/icons`. So every theme switch logs
"Omarchy theme requests icon theme 'Yaru-olive', which is not installed",
and Qt/KDE never gets the icon theme.

`hosts/common/nixos/omarchy-stylix-theme.nix` (all three hosts import
it) overrides the engine package:

```nix
programs.nixarchyThemeEngine.package =
  inputs.nixarchy.inputs.nixarchy-omatheme.packages.${pkgs.stdenv.hostPlatform.system}.hyprchroma.overrideAttrs (old: {
    # shortcut: hyprchroma looks only in Arch's icon dirs; drop once nixarchy-omatheme patches it
    postFixup = (old.postFixup or "") + ''
      for f in $out/lib/hyprchroma/sync-gtk-theme $out/lib/hyprchroma/sync-qt-kde-theme; do
        substituteInPlace "$f" --replace-fail \
          '-d "/usr/share/icons/$value"' \
          '-d "/usr/share/icons/$value" || -d "/run/current-system/sw/share/icons/$value" || -d "/etc/profiles/per-user/$USER/share/icons/$value"'
      done
    '';
  });
```

`--replace-fail` turns an upstream rewrite of that check into a build
failure, not a silent no-op. The engine package comes from `inputs` and
never from `config.programs.nixarchyThemeEngine.package`, because reading
that option from inside its own definition recurses. An issue on
`olafkfreund/nixarchy-omatheme` asks for the same fix there, so the
override can be dropped later.

The Yaru themes need no install. nixarchy already ships `yaru-theme`
(`modules/nixos.nix`, "Every theme's icons.theme names a Yaru variant"),
and `Yaru-olive` is present on p620. Icons appear to "not switch" because
a rebuild resets them (D1) and Qt is skipped (D3), not because the theme
is missing.

## Alternatives rejected

- **Keep Stylix's GTK target and put the import last.** hyprchroma
  deliberately adds its import at the top, so a user's own rules override
  it. Reversing that means patching hyprchroma, and the Stylix rules would
  still sit in the file.
- **Have Home Manager own a `gtk.css` that contains only the import.**
  This is rebuild-proof and migrates the old file through HM's backup.
  But it makes `gtk.css` a store link nobody can write, which the
  approved intent rules out, and it fights hyprchroma's design that
  `gtk.css` holds the user's own rules.
- **Rebuild on every theme switch.** It takes minutes, dirties the tree
  (`nhs` refuses a dirty tree) and does not reach running apps any sooner.
- **Turn off the engine's GTK target and rely on Stylix.** That is the
  current behaviour the intent rejects.
- **Install more Yaru packages.** They are already installed (D3).

## Risks

- **GNOME session.** Turning off the HM `gnome` target drops the Stylix
  GNOME Shell theme (`org/gnome/shell/extensions/user-theme = "Stylix"`
  stays in dconf, but its package leaves the profile). GNOME Shell falls
  back to its default look. GTK apps under GNOME follow the live palette,
  as decided. The font keys (`font-name`, `document-font-name`) keep their
  last values in the user dconf database, because HM never removes keys.
  All three hosts.
- **libadwaita apps** (Nautilus, Settings) ignore third-party colours by
  upstream policy. They get light/dark and the accent, nothing more. That
  is unchanged.
- **D2 forgotten on a host.** GTK stays on the old palette there until
  `gtk.css` is cleaned. The plan runs it on each host it deploys.
- **D3 override.** The engine is rebuilt locally (a small shell-script
  package with no compile step). If nixarchy's pin moves and the
  substituted line changes, the build fails loudly.
- **p510** gets the change only through an explicit, approved deploy.

## Verification

1. `just test-host p620`, `just test-host razer` and `just test-host p510`
   all build.
2. Eval: HM `stylix.targets.{gtk,gnome,kde}.enable` are `false`, and
   `home-manager-files` no longer contains `.config/gtk-{3,4}.0/gtk.css`
   or a dconf `org/gnome/desktop/interface` `icon-theme`.
3. The built engine's `sync-gtk-theme` and `sync-qt-kde-theme` contain
   `/run/current-system/sw/share/icons`.
4. After the p620 deploy and D2:
   - `omarchy theme set tokyo-night`: `~/.config/gtk-4.0/gtk.css` is the
     single import line, `hyprchroma.css` has tokyo-night's background,
     and a newly opened GTK 3 app (`gtk3-widget-factory`) and a Qt app
     show tokyo-night.
   - The switch log has no "which is not installed" line, and
     `kdeglobals` names the theme's Yaru icon set.
   - `gsettings get org.gnome.desktop.interface icon-theme` is the
     theme's Yaru variant.
5. A rebuild after that switch leaves GTK, Qt, the icon theme and the
   accent on tokyo-night.
6. Switch back to the user's theme (gruvbox).
