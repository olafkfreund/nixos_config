# Spec: `modules.containers.k3d.agents` and one agent on p620

## Design

In `modules/containers/k3d.nix`:

1. New option `agents` (`types.ints.unsigned`, default `0`), passed as
   `--agents ${toString cfg.agents}` in `k3d cluster create`. Its description
   says it takes effect only on create, since k3d does not add nodes to an
   existing cluster.
2. The storage bind mount becomes
   `$STORAGE_DIR:/var/lib/rancher/k3s/storage@server:*;agent:*`, the same
   filter form the resolver mount already uses. With `--agents 0` the
   `agent:*` filter matches nothing, so the create is unchanged for other hosts.
3. The header comment "single-node" is updated.

`hosts/p620/configuration.nix` sets `agents = 1` with a comment that it takes
effect only on a cluster recreate.

### Checks that need no code change

- **Shared host dir, no collisions.** k3s's local-path provisioner names each
  dir `pvc-<uid>_<namespace>_<pvc>` under `/var/lib/rancher/k3s/storage` on the
  node chosen. The PVC uid is cluster-unique, so server-0 and agent-0 writing
  into one host dir cannot collide.
- **Resolver mounts.** `/etc/resolv.conf@server:*;agent:*` and
  `/etc/rancher/k3s/resolv.conf@all:*` plus `--resolv-conf@all:*` already cover
  agents.
- **k3d-pv-state.** Snapshot keeps the whole PV spec except claimRef uid and
  resourceVersion, so `nodeAffinity` (hostname `k3d-factory-agent-0` or
  `-server-0`) survives. Restore checks `$STORAGE_DIR/<pvc dir>` on the host,
  which is the one shared dir for both nodes, and applies the PV with its
  affinity. k3d node names are stable (`k3d-<cluster>-agent-<i>`), so a
  restored PV comes back pinned to the same node. The first recreate restores
  today's PVs, all pinned to server-0; they stay there.
- **Reboot / self-heal.** `k3d cluster start/stop` act on every node.
  `server_progress` watches server-0 only, which is right: the API and the
  datastore live there. The serverlb reattach (#2431) is unaffected. The
  existing comment already covers `k3d cluster start` aborting on a broken
  agent, and that output is logged.
- **server-0-only docker calls.** The keycloak backup reads the storage mount
  source from server-0; agents bind the same host dir, so the result is right
  wherever the keycloak pod runs. The node DNS smoke check probes server-0;
  agents mount the same resolver file. The image GC loops over every node.

## Alternatives rejected

- Separate host dirs per node (`$STORAGE_DIR/<node>`): breaks the restore and
  keycloak-backup path arithmetic and moves existing data for no gain, since
  dir names are already unique.
- Adding a node to the running cluster (`k3d node create`): out of scope; the
  owner chose a recreate, and the module only models create.

## Risks

- A snapshot taken with an agent, restored onto a cluster created with
  `agents = 0`, leaves PVs pinned to a missing node and their pods Pending.
  Only if someone lowers `agents` later; the runbook post-check catches it.
- Recreate itself is the usual risk (#1497). Mitigated by the runbook
  pre-checks: fresh PV snapshot and keycloak backup.

## Verification

- `nix eval` of p620's rendered bootstrap script shows `--agents 1` and the
  `@server:*;agent:*` storage mount; another k3d host (if any) shows
  `--agents 0`.
- `bash -n` on the rendered script.
- p620 toplevel dry-run build, and the repo's pre-commit hooks / CI.
