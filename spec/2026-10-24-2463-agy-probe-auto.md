# Spec: run the agy guard probe automatically, and document the coder guard

## Design

### 1. `agy-implement` probes on first use: `home/development/antigravity-config.nix`

Today the gate (`agyImplement`, the block after the hooks.json check)
refuses when `agy --version` differs from
`${XDG_CACHE_HOME:-$HOME/.cache}/agy-implement/probed`. Instead, on a
mismatch it will:

1. Say what it is doing, on stderr:
   `agy-implement: first use of agy <v> on this host -- running the guard probe (about 90s, #2463)`.
2. Take a lock with `flock` on `<cache>/agy-implement/probe.lock`, so two
   `agy-implement` calls at once run one probe, not two. Once it holds the
   lock, it reads `probed` again: if another call has just probed this
   version, it skips the probe.
3. Run the probe as `AGY_IMPLEMENT="$0" ${agyGuardProbe}/bin/agy-guard-probe`,
   with the probe's stdout sent to stderr. That keeps `agy-implement -p`
   output clean for callers that parse it.
4. Read `probed` again. If it matches `agy --version`, continue into agy as
   usual. If it doesn't (the probe failed, timed out or could not run),
   refuse with:
   `agy-implement: the guard probe did not pass for agy <v> -- not starting agy with write access. See the issue it opened, or run agy-guard-probe (#2453).`

Everything else stays as #2453 left it: an empty `agy --version` still
refuses, and `AGY_IMPLEMENT_PROBING=1` still skips the gate for the probe's
own inner run.

**Avoiding a Nix cycle.** `agyGuardProbe` currently calls
`${agyImplement}/bin/agy-implement`, and `agyImplement` will now call
`${agyGuardProbe}`. Two let-bindings that name each other's store paths
can't be built. So the probe stops naming the store path. It calls
`"${AGY_IMPLEMENT:-agy-implement}"`. `agy-implement` passes its own path
(`$0`), so the probe it starts tests exactly that wrapper. Run by hand,
`agy-guard-probe` uses the `agy-implement` on PATH, the same one the user
would run. This is not a security boundary: the guard in
`/etc/antigravity/hooks` is.

`agy-guard-probe` stays a separate command, for running by hand or re-running
after a failure. Its behaviour doesn't change: it writes `probed` on a pass
and opens the deduplicated issue on a fail.

### 2. Docs

- **New `docs/tooling/agy-coder-guard.md`**, for someone who has never read
  the intent, spec or plan files. It covers:
  - **What it is.** `agy-implement` gives agy write access only inside the
    task worktree, behind a PreToolUse hook. Codex has its own path.
  - **What the guard allows and denies.**
    - Read tools are allowed.
    - Writes only inside the worktree, and never to `.git`, `.claude`,
      `.envrc`, `.direnv`, `.githooks`, `.pre-commit-config.yaml` or
      `devenv.nix`.
    - Other denies: hard links, duplicate or non-ASCII keys, unknown
      path-named arguments, and anything touching `~/.gemini`.
    - Shell commands go through the shared coder guard: no commit, deploy,
      restart, GC or reboot, and no `BypassSandbox`.
  - **The version gate and the automatic probe.**
    - What the probe tries, and what pass means.
    - The `probed` file, and that it is per host.
    - That it runs once per agy version per host, and that the first handoff
      after a bump waits about 90 s.
  - **When the probe fails.**
    - The issue it opens, and how to re-run it (`agy-guard-probe`).
    - How to unblock in an emergency (write the version into `probed` by
      hand), and why that is a last resort.
  - **Files.**
    - `modules/programs/agy-guard-adapter.sh` and its test
    - `home/development/antigravity-config.nix`
    - `modules/programs/claude-code-managed.nix`
  - **Known gaps**, copied from PR #2462.
  - **History:** #2087, #2291, #2296, #2298, #2452, #2453, #2463.
- **Nav:** "agy coder guard: tooling/agy-coder-guard.md" under Tooling, in
  both `mkdocs.yml` and `mkdocs-full.yml`.
- **`home/development/claude-code-skills/handoff/SKILL.md`, "After an agy
  update":** replace the manual "run `agy-guard-probe`" instruction with one
  sentence. The first `agy-implement` on a new version probes by itself.
  If it refuses, the probe failed: stop and tell the user. Keep the static
  test line.
- **`.claude/commands/update-antigravity.md`:** reword the #2453 line in the
  same way.

## Alternatives rejected

- **A systemd user timer that probes ahead of time** (intent option b). The
  intent decision was (a). A timer uses quota on days nobody uses agy, needs
  a live login when it fires, and is a second place that has to agree with
  the gate.
- **Probing during Home Manager activation.** This adds about 90 s and a
  network call to every deploy, and fails when agy is logged out (intent
  constraint).
- **`agy-implement` calling the probe by PATH name.** This works too, but
  `$0` → `AGY_IMPLEMENT` means the probe always tests the wrapper that asked
  for it, and only the hand-run case relies on PATH.

## Risks

- **The first handoff after a bump waits about 90 s.** A probe that hangs is
  bounded by the probe's own `--print-timeout 300s`, so at worst about 5
  minutes, then it refuses.
- **A flaky model run fails the probe**, and the handoff refuses: a false
  alarm, never a false pass. The next `agy-implement` call tries again,
  because nothing is recorded on a fail. The deduplication stops a second
  issue.
- **A caller with a short timeout** (a Claude Bash call at the 2-minute
  default) may cut off the first run. The handoff skill already runs agy in
  the background, so the docs and the skill note the first-run wait.
- **Hosts:** p620 and razer. p510 doesn't run agy.

  - remove `~/.cache/agy-implement/probed`
  - run `agy-implement -p "reply with ok"` in a scratch git repo: it must
    print the "first use" line, probe, then answer, and `probed` must hold
    the version again
  - run it a second time: it must start straight away, with no probe
- Concurrency: two `agy-implement` calls started together with no `probed`
  file must run a single probe.
- The same first-use check on razer, after `just deploy-via-p620 razer`.
