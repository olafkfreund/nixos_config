# Spec: a fast local MoE model for razer, served by p620

## Design

**One change.** In `hosts/p620/configuration.nix`, add the model to
`features.ollama-server.onDemandModels` (the list at line 143):

```nix
onDemandModels = [ "qwen2.5-coder:14b" "gemma4:e4b" "gemma4:12b" "qwen2.5:7b"
  "hf.co/unsloth/Qwen3.6-35B-A3B-GGUF:UD-IQ4_XS" ];
```

Put a one-line comment above it saying why this build: an MoE model whose
17.7 GB weights plus the 32K KV cache fit the 24 GB card, where Ollama's own
`qwen3.6:35b-a3b` (21.7 GB plus a 0.9 GB projector) would spill to the CPU.

**Why this model reference** (confirmed 2026-10-24, not guessed):

| Candidate | Weights | Fits 24 GB with 32K context? |
|---|---|---|
| `qwen3.6:35b-a3b` (Ollama library) | 21.7 GB + 0.9 GB projector | No, it spills layers to CPU |
| `qwen3.6:35b-a3b-q4_K_M` | 23.9 GB | No |
| **`hf.co/unsloth/Qwen3.6-35B-A3B-GGUF:UD-IQ4_XS`** | **17.7 GB** | **Yes**, about 21 GB in use |
| `…:UD-Q3_K_XL` (fallback) | 16.8 GB | Yes, with more headroom |

The IQ4_XS build is the one the article benchmarked. Ollama pulls
Hugging Face GGUFs by an `hf.co/<repo>:<quant>` name. nixpkgs' `loadModels`
just runs `ollama pull <name>`, so the existing
`ollama-model-loader.service` handles it.

**How it behaves on p620.**

- It's on-demand, so it loads when first asked for and unloads after the
  module's `keepAlive`.
- `OLLAMA_MAX_LOADED_MODELS=1`, so while it's loaded it evicts the
  persistent `qwen3.8:27b`, which reloads on its next request.
- Its context is the module's shared `contextLength = 32768`.
- The weights go to `/mnt/data/ollama/models`, which has 575 GB free.

**How razer uses it.** No change on razer. Any OpenAI-compatible client
points at `http://p620:11434/v1` with the model name above, or Ollama's
native `/api/chat`. The `ollama-code` MCP tool already reaches
`http://p620:11434` from razer
(`home/development/claude-code-mcp.nix:79`).

## Alternatives rejected

- **llama.cpp with `--n-cpu-moe` on razer** (intent option a). Rejected by
  intent decision 1.
- **Ollama's own `qwen3.6:35b-a3b` tag.** It's 21.7 GB of weights, so it
  spills to the CPU on a 24 GB card with 32K context. Ollama splits by layer,
  not by expert, which is much slower than the article's offload.
- **A persistent model.** It would pin about 21 GB of VRAM and evict the
  coding model for good. On-demand matches how razer will use it.
- **Lowering `contextLength` to fit the library tag.** That shrinks context
  for every model on p620.

## Risks

- **The HF GGUF may not load in p620's Ollama build.** A new architecture can
  need a newer Ollama than the one pinned. This is checked first (plan
  step 1), by pulling and running it by hand before the config changes. If it
  doesn't load, stop and report; don't fall back silently.
- **VRAM headroom is about 2–3 GB.** p620's desktop (three monitors) uses some
  VRAM. If `ollama ps` shows less than 100% GPU, switch to the `UD-Q3_K_XL`
  build.
- **The first pull is 17.7 GB.** The loader doesn't re-run on `switch`
  (`restartIfChanged = false`), so the plan pulls it once by hand. The loader
  finds it already present at the next boot.
- **A coding session loses `qwen3.8:27b` while this model is loaded.** That
  is the existing one-model-at-a-time behaviour.
- **Hosts:** p620's config only. razer and p510 don't change.

## Verification

- **Before the config change**, by hand on p620:
  - `ollama pull hf.co/unsloth/Qwen3.6-35B-A3B-GGUF:UD-IQ4_XS` succeeds.
  - `ollama run --verbose <name> "…"` answers, and shows the eval rate.
  - `ollama ps` shows `100% GPU`.
- **From razer:** a `curl` to `http://p620:11434/api/generate` (or `/v1/chat/completions`)
  with that model answers, at 20 or more tokens/s.
- `just check-syntax` and `just test-host p620` pass. After the deploy,
  `ollama list` on p620 includes the model.
