# Spec: p620 boots cleanly: k3d comes up fast, boot-time downloads have DNS

## What the investigation found (2026-11-04, live on p620)

- `state.db`, the k3s datastore in volume `61eae3cf…` under
  `/mnt/img_pool/docker/volumes/`, measured read-only:

  | Measure | Value |
  |---|---|
  | Size | 11,464,585,216 bytes |
  | Page size | 4096 |
  | Pages | 2,798,971 |
  | Free pages | 2,793,401 (99.8%) |
  | `auto_vacuum` | 0 |
  | Journal mode | WAL |
  | Live rows in `kine` | 4,438 |

- **k3s's compaction works.** The server log shows steady
  `COMPACT deleted 999 rows from 1000 revisions` lines, up to revision
  ~3.98M. So the intent's lease-bloat hypothesis is refuted for p620. Rows
  are deleted on time, but with `auto_vacuum` off SQLite keeps every freed
  page. The live data is about 22 MB; the other 11.4 GB is free pages, which
  k3s still reads at start (12.9 GB read in the 08:34 boot).
- **The two timeouts disagree.** `k3d-cluster-bootstrap`'s
  `TimeoutStartSec = "15min"` (`modules/containers/k3d.nix:911`) is
  shorter than one self-heal wait. `apiWaitSeconds` defaults to 1800
  (`:682–697`) and is used per attempt across up to 3 attempts
  (`:316–356`).
- `ollama-model-loader` comes from nixpkgs' `services.ollama.loadModels`.
  It is ordered `After=network-online.target` with `Restart=on-failure` and
  `RestartSec=1s`, and failed at 08:34:14 on DNS
  (`lookup registry.ollama.ai: no such host`).
- NetworkManager rejects both keys set through
  `networking.networkmanager.connectionConfig` in
  `hosts/p620/nixos/dns-fallback.nix:24–27` as `unknown key`. The link
  uses `192.168.1.254` from DHCP.

## Design

### D1. One-time conversion of the existing datastore (operational, no repo change)

The datastore is converted in place to `auto_vacuum = FULL`. SQLite then
gives freed pages back to the file system at every commit. The setting is
stored in the database header, so it survives restarts. `VACUUM` only
rewrites pages and keeps every row, so no cluster state changes. This is
not the p510 recipe's `DELETE`: compaction already removes the old rows.

Procedure, with the cluster stopped:

1. Announce on the agent bus with a downtime estimate (about 15 minutes).
2. `sudo systemctl mask --runtime k3d-cluster-bootstrap.service` (a plain
   `mask` fails, because the unit is a symlink into the store), then
   `sudo k3d cluster stop factory`.
3. `PRAGMA wal_checkpoint(TRUNCATE);`
4. **Rollback copy:** `cp -a state.db state.db.bak-20261104`. The full
   11.5 GB file is untouched; `/mnt/img_pool` has 108 GB free.
5. **Compact backup:** `VACUUM INTO 'state.db.compact-20261104'`. Run
   `PRAGMA integrity_check` on it and check that its `kine` row count
   matches the live file.
6. `PRAGMA auto_vacuum = FULL; VACUUM;` on `state.db`, then
   `integrity_check`, the row count again, and the new size (expected
   about 25 MB).
7. `k3d cluster start factory`, unmask, then start the bootstrap.
8. **Verify:**
   - API reachable
   - every pod as before (record `kubectl get pods -A` in step 2 and
     compare)
   - PVs Bound
   - Keycloak and `skillai-db` answering
   - ArgoCD apps Synced/Healthy

**Restore path:** stop the cluster, remove `state.db-wal` and
`state.db-shm`, copy `state.db.bak-20261104` back over `state.db`, then
start. This is tested before step 6: the backup opens with
`integrity_check = ok` and the same row count. The original stays
untouched until step 6, and `VACUUM` is atomic.

### D2. New clusters start with `auto_vacuum = FULL` too

D1 fixes only this database; a recreated cluster would start at
`auto_vacuum = 0` again. `k3d.nix` passes k3s the sqlite DSN explicitly,
with `&_auto_vacuum=full` added. That go-sqlite3 option sets the pragma
before kine creates its tables. The exact default DSN of the pinned
`k3sImage` is copied from the k3s source for that version, not
guessed. If the default cannot be confirmed, D2 is dropped and D3's
warning covers a recreated cluster.

k3d applies server arguments only at `k3d cluster create`, so this does
not touch the running cluster.

### D3. The bootstrap reports the datastore size

After the API answers, `k3d-cluster-bootstrap` logs one line:
`[k3d-bootstrap] datastore <N> MiB (auto_vacuum=<mode>)`. When the file is
over 2 GB or `auto_vacuum` is not FULL, it logs at warning level, so a
regression shows up in `journalctl -p warning` and in the next log review.
This is a read-only `stat` plus `PRAGMA` through `docker exec` (or the
volume path). It never fails the bootstrap.

### D4. The bootstrap's timeout matches its own wait

`TimeoutStartSec` becomes `apiWaitSeconds + 5 min`, derived from the
option, so the documented ceiling is honoured. With D1 the API answers in
seconds, so this only matters for a real stall. A stall is still bounded:
the script stops waiting after about 2 minutes without datastore reads
(`:316–356`), and systemd stops it after `apiWaitSeconds + 5 min`.

### D5. `ollama-model-loader` waits for DNS

`modules/services/ollama.nix` adds an `ExecStartPre` that waits up to
60 s for `getent hosts registry.ollama.ai` to answer. The unit then starts
pulling only once names resolve, and it does not fail at boot. The
existing `restartIfChanged = false` (for the switch-time race) stays. If
DNS still fails after 60 s, the unit fails as it does today, and
`Restart=on-failure` applies.

### D6. Remove the ignored DNS pin

Delete `networking.networkmanager.connectionConfig` and its comment from
`hosts/p620/nixos/dns-fallback.nix:19–27`. The rest of the file stays:
systemd-resolved, its fallbacks, `Domains = ~.` and the managed
`performance.conf`. NetworkManager never applied the pin, so removing it
changes no resolver p620 uses. It only removes the `unknown key` warnings
and the misleading comment.

## Alternatives rejected

- **Move to k3s's embedded etcd:** it means recreating or migrating the
  cluster, which puts PVs, Keycloak, `skillai-db` and the rotated
  `factory-cli-creds` at risk (`k3d.nix` records an earlier PVC loss). That
  doesn't fit a problem `auto_vacuum` solves in place.
- **A scheduled `VACUUM` or `incremental_vacuum` timer:** a second writer on
  a live WAL database, from outside the container, plus a new privileged
  unit. `auto_vacuum = FULL` needs no extra process.
- **The p510 recipe's `DELETE` of old revisions:** not needed. Compaction
  already deletes them; only 4,438 rows are live.
- **Only raising `TimeoutStartSec`:** hides the growth (intent).
- **A global wait-for-DNS** (changing `network-online.target` semantics):
  it touches every host and every unit. Only one unit is affected, so the
  fix stays with that unit.
- **Fixing the DNS pin with per-connection profiles:** its reason, DHCP
  handing out p620's dead IP, went away with the router change.

## Risks

- **The conversion fails partway:** `VACUUM` is atomic, and the full
  rollback copy restores the exact previous file. The downtime is bounded
  by the cluster stop/start (minutes) plus a vacuum of about 22 MB of live
  data (seconds).
- **`auto_vacuum = FULL` costs extra writes per commit:** on a 22 MB
  database with lease renewals every few seconds, this is negligible.
- **D2 sets the wrong DSN:** a new cluster would use a different datastore
  path or option. That's why D2 copies the default from the k3s source for
  the pinned version, or is dropped.
- **D5's `getent` blocks for its 60 s** on a host with no DNS at all: the
  unit then fails exactly as today.
- **Hosts:** `k3d.nix` and `dns-fallback.nix` are p620-only. `ollama.nix`
  is also imported by p510, so D5 reaches p510 too. p510 is built in the
  checks, but not deployed without asking.

## Verification

1. **D1, live:**
   - `state.db` about 25 MB, `PRAGMA auto_vacuum` = 1
   - `integrity_check` ok, and the row count unchanged
   - all pods, PVs and ArgoCD apps as before the stop
2. Build: `just check-syntax`, then `just test-host p620` and
   `just test-host p510` (for `ollama.nix`).
3. After deploy:
   - `systemctl show k3d-cluster-bootstrap -p TimeoutStartUSec` shows 35 min
   - the bootstrap's datastore line appears
   - NetworkManager logs no `unknown key` lines
   - `resolvectl query github.com` and a MagicDNS name both resolve
4. **On the next reboot:**
   - `k3d-cluster-bootstrap` succeeds first try, API reachable within 5 min
   - `ollama-model-loader` has no DNS errors
5. A week later, `state.db` is still under 2 GB (the bootstrap line).
