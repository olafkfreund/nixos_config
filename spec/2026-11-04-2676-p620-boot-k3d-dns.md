# Spec: p620 boots cleanly: k3d comes up fast, boot-time downloads have DNS

## What the investigation found (2026-11-04, live on p620)

- **The datastore.** `state.db` lives in volume `61eae3cf…` under
  `/mnt/img_pool/docker/volumes/`. `/mnt/img_pool` is `sde`, a SATA SSD
  (`MTFDDAK256TBN`, ROTA=0), with 108 GB free. Measured read-only:

  | Measure | Value |
  |---|---|
  | Size | 11,464,585,216 bytes |
  | Page size | 4096 |
  | Pages | 2,798,971 |
  | Free pages | 2,793,401 (99.8%) |
  | `auto_vacuum` | 0 |
  | Journal mode | WAL |
  | Live rows in `kine` | 4,438 |

- **k3s's compaction works.** The server log shows steady
  `COMPACT deleted 999 rows from 1000 revisions` lines, up to revision
  ~3.98M. So the intent's lease-bloat hypothesis is refuted for p620. Rows
  are deleted on time, but with `auto_vacuum` off SQLite keeps every freed
  page. The live data is about 22 MB; the other 11.4 GB is free pages, which
  k3s still reads at start (12.9 GB in the 08:34 boot).
- **The default datastore settings,** read from the pinned
  `rancher/k3s:v1.31.5-k3s1` binary:
  `./db/state.db?_journal=WAL&cache=shared&_busy_timeout=30000&_txlock=immediate`
  (relative to `/var/lib/rancher/k3s/server`). The `_auto_vacuum` option of
  its SQLite driver is present in the same binary.
- **The cluster containers** use the Docker restart policy `unless-stopped`.
  Docker does not restart a container stopped with `k3d cluster stop` while
  the daemon stays up. Four k3d timers can touch the cluster:
  `k3d-cluster-bootstrap`, `k3d-image-gc`, `k3d-backup-freshness`, and the
  backup jobs in `k3d.nix` (`keycloak-realm-backup`, `postgres-backup`).
- **The two timeouts disagree.** `k3d-cluster-bootstrap` has
  `TimeoutStartSec = "15min"` (`modules/containers/k3d.nix:911`), and its
  `/etc/hosts` pin loop is hard-coded to the same 15 minutes (`seq 1 450`,
  `:112`). `apiWaitSeconds` defaults to 1800 (`:682–697`) and applies to each
  of up to 3 self-heal attempts (`:316–356`). Each poll also costs more than
  its 2 s sleep (`:688–690`).
- **`ollama-model-loader`** comes from nixpkgs' `services.ollama.loadModels`.
  It is ordered `After=network-online.target` with `Restart=on-failure` and
  `RestartSec=1s`, and failed at 08:34:14 on DNS
  (`lookup registry.ollama.ai: no such host`). `ollama.nix` is imported by
  p620 and p510.
- **NetworkManager** rejects both keys set through
  `networking.networkmanager.connectionConfig`
  (`hosts/p620/nixos/dns-fallback.nix:24–27`) as `unknown key`. The link
  uses `192.168.1.254` from DHCP.

## Design

### D1. One-time conversion of the existing datastore (operational, no repo change)

The datastore is converted in place to `auto_vacuum = FULL`. SQLite then
gives freed pages back to the file system at every commit. The setting is
stored in the database header, so it survives restarts. `VACUUM` only
rewrites pages and keeps every row and every `id` (kine's revision
counter), so no cluster state changes. This is not the p510 recipe's
`DELETE`: compaction already removes the old rows. Tools are the host's
`sqlite3`, `docker` and `k3d`.

Procedure:

1. **Announce** on the agent bus: the cluster is down about 30 minutes
   (the budget is below).
2. **Record the before state:**
   - `kubectl get pods -A -o wide`, `kubectl get pv,pvc -A` and
     `kubectl get applications -A`
   - the Keycloak and `skillai-db` checks the module already uses
3. **Quiesce every writer:**
   - Stop and `mask --runtime` the `k3d-cluster-bootstrap`, `k3d-image-gc`,
     `k3d-backup-freshness` and backup units and their timers. `mask` alone
     would not stop a run already in progress.
   - `k3d cluster stop factory`.
   - **Prove it:** `docker inspect -f '{{.State.Running}}'` is `false` for
     every `k3d-factory-*` container, and `fuser` on `state.db*` finds no
     process. If either fails, abort and run step 9.
4. **Untouched rollback copy, before any SQLite command:**
   `cp -a state.db state.db-wal state.db-shm` into `rollback-20261104/`,
   next to the db, and check sizes.
5. **Checkpoint:** `PRAGMA wal_checkpoint(TRUNCATE);` must return `0|0|0`
   (not busy, and no frames left). `state.db-wal` must then be 0 bytes.
   Anything else: abort and run step 9.
6. **Compact backup and restore test:**
   - `VACUUM INTO 'state.db.compact-20261104'`, then on the copy
     `PRAGMA integrity_check` = `ok`, and `count(*)` and `max(id)` equal to
     the live file.
   - **Real restore test:** copy `server/` (db, TLS, `token`) into a
     scratch directory, and put the compact backup there as `state.db`.
   - Start a throwaway `rancher/k3s:v1.31.5-k3s1` with
     `server --disable-agent`, on that directory, with no published ports
     and on its own network.
   - Check that its API lists the same namespaces and the same number of
     Secrets and PVs as step 2. Then remove the container and the scratch
     directory.
   - **If the throwaway server refuses the data, abort, and do not convert.**
7. **Convert:** `PRAGMA auto_vacuum = FULL; VACUUM;` on `state.db`. Then
   check `integrity_check` = `ok`, `PRAGMA auto_vacuum` = `1`, `count(*)`
   and `max(id)` unchanged, and the size (expected about 25 MB).
8. **Start:**
   - `k3d cluster start factory`, unmask everything from step 3, and start
     `k3d-cluster-bootstrap`.
   - **Verify against step 2:** API reachable, every pod back, PVs Bound,
     Keycloak and `skillai-db` answering, ArgoCD apps Synced and Healthy.
9. **Restore path:** with the cluster stopped, copy `rollback-20261104/*`
   back over `state.db*`, then start as in step 8. It is exercised before
   the change by step 6's throwaway server. It restores the exact bytes,
   WAL included.

**Downtime budget, about 30 minutes:**

- 2–3 min for the stop
- under 1 min for the 11.5 GB copy (SSD, ~400 MB/s)
- seconds for the checkpoint and `VACUUM INTO`, which read live pages only
- 3–5 min for the throwaway server
- seconds to minutes for the conversion: `VACUUM` reads the live pages and
  writes ~25 MB
- 3–5 min for the start and checks

If the stop or the copy runs past twice its budget, the operator stops and
reports.

### D2. New clusters start with `auto_vacuum = FULL` too

D1 fixes only this database; a recreated cluster would start at
`auto_vacuum = 0` again. `k3d.nix` adds to `k3d cluster create`:

```text
--k3s-arg "--datastore-endpoint=sqlite:///var/lib/rancher/k3s/server/db/state.db?_journal=WAL&cache=shared&_busy_timeout=30000&_txlock=immediate&_auto_vacuum=full@server:0"
```

That is k3s's own default path and settings (read from the pinned binary)
plus one option. The SQLite driver applies it before kine creates its
tables. k3d applies server arguments only at create, so the running
cluster is untouched. The plan rereads the defaults whenever `k3sImage`
changes.

### D3. The bootstrap reports the datastore size

After the API answers, `k3d-cluster-bootstrap` logs one line:
`[k3d-bootstrap] datastore <N> MiB, wal <M> MiB, auto_vacuum=<mode>`.

- **Where it reads:** the volume path comes from
  `docker inspect k3d-$CLUSTER-server-0` (as `keycloak-realm-backup` does).
- **How it reads:** the sizes with `stat`, and the mode from the database
  header (bytes 52–55 and 64–67, through `od`), with no SQLite client open
  against the live file.
- **When it warns:** when the db is over 2 GB, the WAL is over 256 MB, or
  `auto_vacuum` is not FULL. The line is printed with the `<4>` syslog
  prefix, so it lands in `journalctl -p warning`.
- **It never fails the bootstrap.**

### D4. The bootstrap's timeout covers its own retries

`TimeoutStartSec` and the `/etc/hosts` pin loop both derive from one value:
`3 × (apiWaitSeconds + 300) + 600` seconds. That's three full attempts,
with their extra polling, stop/start time and the GitOps steps.

The default (1800) makes this about 2 hours, but only a server that keeps
reading for that long uses it. A stall still ends each attempt after about
2 minutes without datastore reads (`:316–356`). With D1 in place the API
answers in seconds. The 15-minute value's purpose, to fail loudly instead
of hanging forever, is kept: the bound is still finite and derived.

### D5. `ollama-model-loader` waits for DNS

`modules/services/ollama.nix` adds `systemd.services.ollama-model-loader.preStart`.
It loops up to 60 s until `${pkgs.getent}/bin/getent hosts registry.ollama.ai`
answers, then exits 0 either way. If DNS never came up, the pulls fail
exactly as they do today, and `Restart=on-failure` applies. The existing
`restartIfChanged = false` stays.

### D6. Remove the ignored DNS pin

Delete `networking.networkmanager.connectionConfig` and its comment from
`hosts/p620/nixos/dns-fallback.nix:19–27`. The rest of the file stays:
systemd-resolved, its fallbacks, `Domains = ~.` and the managed
`performance.conf`. NetworkManager never applied the pin, so removing it
changes no resolver p620 uses. It only removes the `unknown key` warnings
and the misleading comment.

## Alternatives rejected

- **Move to k3s's embedded etcd:** it means recreating or migrating the
  cluster, which puts PVs, Keycloak, `skillai-db` and the rotated
  `factory-cli-creds` at risk (`k3d.nix` records an earlier PVC loss). That
  doesn't fit a problem `auto_vacuum` solves in place.
- **A scheduled `VACUUM` or `incremental_vacuum` timer:** a second writer on
  a live WAL database, from outside the container, plus a new privileged
  unit. `auto_vacuum = FULL` needs no extra process.
- **The p510 recipe's `DELETE` of old revisions:** not needed. Compaction
  already deletes them; only 4,438 rows are live.
- **Only raising `TimeoutStartSec`:** hides the growth (intent). D4 raises
  it only together with D1–D3.
- **Lowering `apiWaitSeconds` to fit 15 minutes:** it would bring back the
  2026-08-19 failure, where a slow but progressing open was killed and the
  work thrown away.
- **A global wait-for-DNS** (changing `network-online.target` semantics):
  it touches every host and every unit. Only one unit is affected, so the
  fix stays with that unit.
- **Fixing the DNS pin with per-connection profiles:** its reason, DHCP
  handing out p620's dead IP, went away with the router change.

## Risks

- **Something writes during D1:** step 3 proves that no container runs and
  no process holds the files before any SQLite command, and step 4's copy
  comes before the checkpoint. Any failed check aborts to step 9.
- **The conversion fails partway:** `VACUUM` is atomic, and step 4's copy
  restores the exact previous bytes.
- **`auto_vacuum = FULL` costs extra writes per commit:** negligible on a
  22 MB database. Checkpoints still grow the WAL between them, so D3 also
  watches the WAL.
- **D2's settings drift from k3s's defaults** after a `k3sImage` bump. A
  plan step makes the plan reread them; D3 catches a regression either way.
- **The longer D4 bound** makes a genuinely stuck but still-reading
  bootstrap visible later, up to about 2 hours instead of 15 minutes. D3
  makes the cause visible.
- **Hosts:** `k3d.nix` and `dns-fallback.nix` are p620-only. `ollama.nix` is
  also imported by p510, so D5 reaches p510 too. **Building p510 needs your
  OK.** Without it, the p510 check is evaluation only.

## Verification

   - `state.db` about 25 MB, `PRAGMA auto_vacuum` = 1
   - `integrity_check` ok, and `count(*)` and `max(id)` unchanged
   - pods, PVs and ArgoCD apps match step 2
   - the throwaway restore test passed before the conversion
2. **Build:**
   - `just check-syntax` and `just test-host p620`
   - p510: `nix eval .#nixosConfigurations.p510.config.system.build.toplevel.drvPath`,
     or `just test-host p510` with your OK
3. **After deploy:**
   - `systemctl show k3d-cluster-bootstrap -p TimeoutStartUSec` matches the
     formula
   - the bootstrap's datastore line appears at info level
   - NetworkManager logs no `unknown key` lines
   - `resolvectl query github.com` and a MagicDNS name both resolve
4. **On the next reboot:**
   - `k3d-cluster-bootstrap` succeeds first try, API reachable within 5 min
   - `ollama-model-loader` has no DNS errors
5. A week later, `state.db` is still under 2 GB (the bootstrap line).
