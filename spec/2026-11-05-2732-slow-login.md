# Spec: Omarchy login takes 20-27 s to settle

## Design

Two small changes in nixarchy-omatheme, delivered here by overriding one flake
input. Neither changes how a real theme change is applied.

### 1. Setting a value it already has does nothing (`bin/hyprchroma`)

At the top of the `--set-enabled` block (line 497), read the recorded value of
the target's key from `settings.json`. Exit 0 before anything is written when all
of these hold:

- the recorded value equals the requested one (a missing key never counts as
  equal)
- `--force` was not passed
- for `true`: `status.json` already has a field for this target, meaning it has
  been synced at least once (`gtk`, `qtKde`, `darkReader`, `pearDesktop`, `flatpak`,
  `browsers`)
- for `false`: the target is neither `dark-reader` nor `qt-kde`

The `status.json` condition is needed for a fresh install. The first `--set-enabled`
writes defaults for all six targets (`:529-533`), and a targeted run also writes the
fingerprint (`:1022`). Comparing the setting alone would then skip Qt, Dark Reader
and Pear, and the daemon's unforced run would see a matching fingerprint and skip
them too. It also means a sync that failed before recording its status is retried
at the next login.

The `false` condition exists because those two targets can defer a revert to a
background waiter that does not survive a logout. Re-running their revert at login
is how that work gets retried, so a host with either switched off keeps today's
behaviour for it.

`hyprchroma framework remove` and `framework restore` (`:243`, `:266`) gain `--force`.
A restored framework must sync even though its recorded value is already `true`.

The login then goes:

- Six `--set-enabled` steps exit in well under a second each.
- `hyprchroma shell`, `editors` and `electron status` run once, as they do today.
  They stay because a changed `starship.toml` relies on them (omatheme issue 60).
- The daemon's own unforced `--target=all` run stays, and it is what applies a
  theme set while the session was down (`bin/hyprchroma:182-185`). It also clears
  per-app colour overrides and resumes pending work, as today (`:709-760`).

The fingerprint already covers `.frameworks` (`:693`), so a changed toggle is
still seen by that run as well as by the forced sync on the changed value.

### 2. The plugin helper skips a plugin already placed (`modules/nixos.nix:127`)

Before `rescanPlugins`, the helper checks `~/.config/omarchy/shell.json` using
`${pkgs.jq}/bin/jq`, because the unit's `PATH` does not promise `jq`. It exits 0 only
when both of these hold:

- the id is a direct entry in a `.bar.layout` section, as a string or as an object
  with that `id`, which is how the shell's own `findBarLocation` looks for it
  (`PluginRegistry.qml:207`)
- the id is not in `disabledPlugins`

Searching the whole file would be wrong: a residual `plugins[]` record can outlive
a removed bar entry (`PluginRegistry.qml:548-553`), and that is exactly the case
that must be repaired.

If the check fails for any reason, including a missing or unreadable file, the
existing rescan and retry path runs unchanged. That covers a fresh install and a
widget the user removed, which is put back as it is today. The other repairs in
`setEnabled` don't apply: the clone restore is first-party only (`:528`), and
Omarchroma is third-party.

### 3. Local delivery (this repo)

After the upstream PR merges, `flake.nix` gains
`nixarchy.inputs.nixarchy-omatheme.url` pinned to the merged commit. This replaces
both the module and the package, so no patch code is carried here. It is the
temporary local override, and it is removed once nixarchy pins that commit or
later. The existing `postFixup` in `omarchy-stylix-theme.nix` still applies,
because upstream `main` equals the pinned revision today, and it will fail the
build loudly if that changes (`--replace-fail`).

### Change from the approved intent

The intent says shell colours sync at most once. **This design syncs them twice.**
The second sync comes from `omarchy-theme-gnome.service`, and it has to stay:

- `omarchy-theme-set-gnome` resets `gtk-theme` to `Adwaita-dark` at every login.
- The forced GTK sync in its `ExecStartPost` restores `adw-gtk3-dark`. Without it,
  GTK apps lose the theme.
- That forced run also does terminals, shell and editors (`bin/hyprchroma:1019-1021`),
  about 1 s of background work. It should wait far less on the lock with the other
  syncs gone, but the two units are not ordered, so some overlap with the daemon's
  run is still possible. The login measurement will show it.

Approving this spec accepts that change to the intent.

## Alternatives rejected

- **Remove the `ExecStartPre` toggles from the module:** nothing would then apply
  a changed Nix setting.
- **A new `--if-changed` flag:** it leaves the test script untouched, but adds a
  flag and a module change for behaviour every caller wants.
- **Remove the forced GTK sync from `omarchy-theme-gnome`:** GTK apps lose the
  theme, as above.
- **Stop `omarchy-theme-set-gnome` resetting `gtk-theme`:** that would also remove
  the login flip between the two themes, but it is Omarchy's script and the change
  reaches GNOME sessions too. Out of scope unless the flip is still visible
  afterwards.
- **Scope the terminals, shell and editors tail to `--target=all`:** this would
  meet "at most once", but targeted runs and the tests rely on the tail, for about
  1 s of background work.
- **`postFixup` plus `mkForce` patches here:** the helper is generated by the
  module, so this means copying it into this repo. The input override carries no
  code.
- **Use `putBarWidget` instead of a `shell.json` check:** it still goes over IPC
  with retries, so it costs time while the shell is loading, and the rescan would
  still need its own guard.
- **Drop the `setdefault` loop instead of checking `status.json`:** it would fix the
  fresh install, but a sync that failed would still not be retried at the next
  login.

## Risks

- **A `--set-enabled=true` that repaired things:** a person who used it to force a
  resync now gets nothing, and must use `--force`. The runtime test at
  `tests/desktop-runtime.sh:180-182` relies on the old behaviour and changes to
  `--force`.
- **A failed revert is not retried:** for `flatpak`, `browsers`, `gtk` and `pear`,
  a revert that fails after `settings.json` is written is no longer retried at
  login. It still logs the failure and exits non-zero the first time.
- **An updated widget may wait for the next login:** the rescan also picked up a
  changed Omarchroma after a rebuild. The shell has a file watcher, which logged 745
  reloads for other plugins in 10 days, but none for this plugin, so it is unproven
  here. If it doesn't fire, an updated widget appears at the next login or shell
  restart. This is checked below and accepted if so.
- **Declared and recorded settings already disagree:** on p620 `settings.json` has
  `browsers: true` while the unit declares `false`, so the next login still reverts
  browsers once.
- **A placed widget stays where it is:** `enablePlugin` moved it back to the right
  section at every login, and now it stays where the user put it. This is a small
  behaviour change.
- **Second `nixarchy_2` lock node:** the lock has a second nixarchy with its own
  omatheme. The override reaches only the `nixarchy` node, which is the one
  `omarchy-stylix-theme.nix` and the hosts use.
- **All three hosts get this.** p510 is not built or deployed without asking.
- **The delay may have other causes.** The first visible frame is still unmeasured,
  and the `gtk-theme` flip remains.

## Verification

Upstream, in nixarchy-omatheme:

- `nix flake check` passes, including `tests/desktop-runtime.sh` and
  `tests/plugin-enable.sh`.
- New runtime cases: on empty state, the sequence `gtk`, `qt-kde`, `dark-reader`,
  `pear` with `--set-enabled=true` syncs all four; repeating it leaves `status.json`
  and the generated files untouched; a changed value still syncs; `--force` still
  syncs; `--set-enabled=false` on `dark-reader` still runs its revert;
  `framework restore` still syncs.
- New helper cases, with `HOME` set to a temporary directory for every case in
  `tests/plugin-enable.sh`: id in `bar.layout` as a string and as an object means no
  `omarchy-shell` calls at all; id only in `plugins[]`, id also in `disabledPlugins`,
  and a missing `shell.json` all take the old path.

Here, before any deploy:

- `just check-syntax`, `just test-host p620` and `just test-host razer`.
- The built `hyprchroma` and helper contain the changes.

On p620, at a real logout and login scheduled by the user, compared with the
intent's table:

- One `shell colors synchronized` line from `hyprchromad`, plus one from
  `omarchy-theme-gnome`.
- The plugin load order appears once in the shell log.
- `hyprchromad` started and plugins loaded by about +8 s.
- `omarchy theme set` to another theme and back still reaches GTK, Qt, kitty and
  editors.
- A rewritten Omarchroma file during a running session shows whether the watcher
  reloads it, which settles the risk above.
- The user judges that the desktop settles sooner.
