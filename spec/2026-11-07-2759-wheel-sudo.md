# Spec: limit passwordless sudo for wheel

## Design

Wheel members on p620 and razer must type their login password for every sudo, and no approval is cached.
p510 keeps today's NOPASSWD, stated in its own host file. Each caller that relied on NOPASSWD is changed to
prompt at a terminal the owner is looking at.

### Facts this design rests on (checked 2026-11-07, read-only)

- Evaluated today on all three hosts: `security.sudo.wheelNeedsPassword = false`, giving the rule
  `%wheel ALL=(ALL:ALL) NOPASSWD:SETENV: ALL`. `sudo-rs` and `doas` are off; classic sudo 1.9.17p2.
  No other `extraRules`. `Defaults passwd_tries=10` comes from outside this repo.
- `passwd -S olafkfreund` status field: `P` (password set) on p620, razer and p510.
- **nixos-rebuild** (nixos-rebuild-ng 26.11), `nixos_rebuild/elevate.py:201-248`: with
  `--ask-elevate-password` it asks once, locally, with `getpass`, and feeds the password to every remote
  `sudo --prompt= --stdin` call it makes. Without it, a remote sudo failure says
  "did you forget to use --ask-elevate-password?". `--sudo` and `--use-remote-sudo` are still accepted.
- **nh** 4.4.2 (strings in the binary): with an elevation strategy that resolves to sudo, nh reads the
  password itself ("Failed to read sudo password", "Password cannot be empty") and runs remote
  `sudo --prompt= --stdin`. It says only sudo supports a password over SSH; run0, doas and pkexec do not.
  It sets `ControlMaster=auto`, `ControlPersist=60` on its SSH. Its help says the strategy "can be a path to
  an elevation program (e.g., /usr/bin/sudo)". That a sudo path selects the remote password flow, and how
  often nh asks per run, are inferred from these strings and are acceptance criteria in Verification step 4,
  not established facts.
- **Agent shells and the sudo cache.** sudo's default `timestamp_type=tty` keys a cached approval on the
  terminal, the session ID and the session leader's start time. Claude Code's own process runs on the
  owner's terminal (`claude` on `pts/14`, session 988536, the same session as the owner's `bash`), while its
  Bash tool children run in a new session with no terminal. An agent process that keeps the owner's
  controlling terminal and session (one started in the same pane, or a child of `claude` that does not
  detach) would match an approval the owner gave there. Such processes are possible and nothing here rules
  them out, so the cache cannot be shown unreachable and it is turned off. This closes reuse of a cached
  approval only; the other routes are closed by removing NOPASSWD.

### Policy

1. `modules/security/default.nix:6-10`: delete `wheelNeedsPassword = false;`. NixOS defaults it to `true`,
   so p510 can state `false` without `mkForce`. Add `security.sudo.extraConfig = "Defaults timestamp_timeout=0";`
   (`extraConfig` lines-merge with the nixpkgs defaults). Keep `execWheelOnly = true`.
2. `hosts/razer/configuration.nix:45-56`: delete the comment block and `security.sudo.wheelNeedsPassword = false;`.
3. `hosts/p510/configuration.nix`, beside the existing `system.autoUpgrade.enable` override (line 547):
   `security.sudo.wheelNeedsPassword = false;`, with one comment line pointing at this issue and saying
   p510 is changed only when the owner schedules it.

### Issue 2758's signing step

The 2758 spec, approved, runs `sudo nix store sign -r --key-file /run/agenix/nix-signing-key <drv>` on the
invoking host before `deploy-via-p620`, `build-on-p620` and the `--build-host` recipes upload. The key is
root-only by design, so under this change that line asks for the password: one more prompt per such deploy,
on the invoking host's terminal. Nothing else changes, and the two land independently in either order. If
2758 lands first the line simply stops being free; if this lands first the line arrives already prompting.

### Unattended jobs

- `nixos-upgrade` (`modules/nix/nix.nix:7-25`): a system unit with no `User=`; `systemctl show nixos-upgrade
  -p User` on p620 prints `User=`, so it runs as root and never calls sudo. Unaffected.
- `nixos-update-checker` timer: runs as `User=nixos-update-checker`, a system user outside wheel, and its
  check script calls no sudo. Unaffected.
- No other systemd unit, system or user, in `modules/`, `home/`, `hosts/` or `pkgs/` calls sudo.
- p510's unattended jobs keep NOPASSWD.

## Alternatives rejected

- **NOPASSWD limited to deploy commands.** Every deploy runs a new
  `/nix/store/<hash>-nixos-system-*/bin/switch-to-configuration`, so the rule needs a store-path wildcard.
  Any user can build a derivation with a script at that path and run it as root through the rule. Same for
  `nix-env -p /nix/var/nix/profiles/system --set <path>` followed by any activation. Root for the user.
- **`security.pam.sshAgentAuth` without a touch-required key.** Every agent runs as the owner with the same
  `SSH_AUTH_SOCK`, so the agent can answer the challenge itself. `ssh-add -c` confirmation moves the
  decision to an askpass dialog on the desktop, which an agent's command can raise and the owner may click
  through, the same weakness as run0 below. With a touch-required FIDO key it would be sound, but no such
  key is set up, and it adds PAM config to every host for no gain over a password.
- **run0 / polkit.** nh and nixos-rebuild both say run0 cannot take a password over SSH; remote deploys
  would need a polkit agent on razer. Locally it would pop desktop dialogs that an agent's command can
  trigger and the owner may click through.
- **A root SSH key for remote activation** (`--target-host root@razer`). The key sits in the same ssh-agent
  the agents use, so it is passwordless root on razer by another name. Only sound with a touch-required key;
  kept as the fallback if the password path fails on razer.
- **Keeping the sudo cache.** See the facts above: agent processes can share the owner's terminal session.

## Risks

- **Lockout on razer over SSH.** If the password is wrong or unknown, or the new sudoers or PAM is broken,
  nobody can get root on razer remotely. The durable remote recovery path is the password itself:
  `ssh -t razer sudo ...`. It is proved before the root shell is closed (Verification step 3). Until then a
  root shell, opened before the install, is the fallback; it does not survive a reboot or a dropped
  connection, so no reboot happens on razer during verification. The known-good pre-change generation is
  recorded and pinned with a GC root so pruning (`check-boot-space.sh` can prune to one generation, line 89)
  cannot remove it. The boot menu (razer `configurationLimit = 2`, `hosts/razer/nixos/boot.nix:28`) needs
  the console and is a last resort only.
- **First deploy order.** The deploy that installs the new policy still elevates under the old one, so it
  goes through unchanged; only the next deploy prompts.
- **Prompt count.** `nhs` with a boot fallback asks twice; with a low-ESP clean it asks for each
  `check-boot-space` sudo line too; signed `deploy-via-p620` asks once more locally. Accepted by the owner.
- **nh caches nothing between runs.** If nh 4.4.2 asks again for each remote sudo call within one run
  (unknown until tested), a deploy asks more than once. Annoying, not unsafe.
- **getpass with no terminal.** If an agent runs a deploy recipe, `--ask-elevate-password` finds no
  terminal and reads stdin, which is the never-closing Bash socket: it hangs. That is the intended outcome
  (agents do not deploy) but it should fail rather than hang; the recipes are already behind the bus guard.
- **p510** is untouched, so its risk is unchanged.
- **Nightly upgrade:** unaffected, confirmed above.

## Verification

1. **Eval** (all hosts): `nix eval .#nixosConfigurations.<host>.config.security.sudo.extraRules` shows no
   NOPASSWD wheel rule on p620 and razer and still shows it on p510; `extraConfig` contains
   `timestamp_timeout=0` on all three. `just check-syntax`, `just test-host p620`, `just test-host razer`.
   p510 is evaluated only, never built.
2. **Before switching any host:** on p620, `su olafkfreund -c true`, and on razer,
   `ssh -t razer su olafkfreund -c true`, each succeed with the owner's password (`su` checks the password
   even under NOPASSWD sudo). On razer, open `ssh -t razer sudo -i` in a spare tmux window and leave it open
   until step 4 passes. In it, record the current system generation `<G0>` and pin it:
   `nix-store --add-root /nix/var/nix/gcroots/2759-known-good -r /nix/var/nix/profiles/system-<G0>-link`.
3. **Install:** deploy razer once with the current recipe (old policy still elevates). Then on razer
   `sudo -n true` fails with "a password is required", and `ssh -t razer sudo true` with the password
   succeeds. This proves the remote recovery path under the new policy; only now may the root shell close
   after step 4. Record this generation as `<G1>`.
4. **Prove the password path on razer**, each with a trivial change (a comment-only rebuild yields the same
   toplevel, so use a harmless real change such as an `environment.etc` marker file):
   - `just deploy-via-p620 razer`: one prompt, activation succeeds;
   - `nhs razer`: activation succeeds;
   - boot fallback: `nh os boot --hostname razer --target-host razer --elevation-strategy /run/wrappers/bin/sudo .`
     succeeds (the same call `nhs` makes after a switch inhibitor);
   - rollback: the remote branch of `update-commit-deploy.sh:593`, run by hand with `<G1>`'s path (a
     generation that already has the new policy, never `<G0>`), asks on the terminal and activates it;
     afterwards `sudo -n true` on razer still fails;
   - record how many times each command asked; this is the count `docs/UPDATE-DEPLOY.md` states.
   If any fails, recover from the open root shell with
   `/nix/var/nix/profiles/system-<G1>-link/bin/switch-to-configuration switch`, or `<G0>` to undo the change.
   When all pass, remove the `2759-known-good` GC root.
5. **Cache not reusable** (p620 after its deploy, owner at the keyboard): in tmux pane A run `sudo true`
   and type the password, then at once in pane A `sudo -n true` must fail, in pane B `sudo -n true` must fail,
   and a Claude Code Bash call of `sudo -n true </dev/null` must fail.
6. **p620 local:** `just p620` and `nhs p620` each prompt and succeed.
7. **Unattended:** after the next 04:00 run, `systemctl status nixos-upgrade` on p620 and razer shows no
   sudo or authentication failure.
8. **Helpers:** `just secrets-status-host razer` asks once and prints; `just p510-clear-sessions` still
   works; `shellcheck` and `just --evaluate` pass on the changed scripts and Justfile.

## Owner decisions, 2026-11-07

The owner accepted both recommendations:

1. The extra password prompts are accepted: one to three per remote recipe, two for `nhs` with the
   boot fallback, and one more for the #2758 signing step.
2. A deploy that an agent starts waits at the password prompt rather than failing. This is accepted,
   because deploys go through the owner.
