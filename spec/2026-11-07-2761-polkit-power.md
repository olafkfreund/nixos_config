# Spec: require auth for power actions by the users group (polkit)

Owner decisions on the intent: option C on p620 and razer if the Omarchy polkit dialog answers login1 actions,
otherwise option A labelled as hygiene; suspend and hibernate unchanged; p510 keeps today's rule through a host
override; remote power actions go through password `sudo` (issue 2759).

## Evidence: the Omarchy session answers polkit requests

All checks were read-only. No power action and no authentication request was triggered.

- **The agent exists.** The running `omarchy-shell` (quickshell 0.3.2, pid 4165849 on p620) loads
  `shell/plugins/polkit/PolkitAgent.qml` from the nixarchy tree. It declares a `PolkitAgent` at the object path
  `/org/omarchy/PolkitAgent` (line 177-179), uses Quickshell's native `Quickshell.Services.Polkit` backend, and
  replaces `polkit-gnome-authentication-agent-1` (plugins `README.md`, "Polkit agent"). That is why `pgrep`
  found no standalone agent process.
- **It is registered with the running polkitd.** The user journal on p620 shows
  `omarchy-shell[4165849]: DEBUG qml: omarchy polkit agent registered` at 10:17:15 on 2026-11-07; the running
  polkitd (pid 3978395) started at 10:08:28. On razer, over SSH, the user journal shows one registration in the
  last 7 days and `loginctl` shows an active display session (`Display=438`).
- **It answers any action.** A polkit authentication agent receives every request polkitd routes to its session;
  it does not filter by action id. The plugin's flow handlers (`onAuthenticationRequestStarted`,
  `onAuthenticationSucceeded`) are not action-specific.
- **The request reaches it.** The menu's `systemctl` call runs in `user@1000.service`, which polkit resolves to
  the display session (measured in the intent with `pkcheck`). That is the session the agent registered for.
  `systemctl` asks for interactive authorisation by default (`--ask-password`), so logind passes
  `AllowUserInteraction` to polkit.
- **It survives a polkitd restart.** `systemd.services.polkit.restartTriggers = [ config.system.path ]` in the
  nixpkgs polkit module restarts polkitd on most deploys (eight restarts on p620 since 2026-11-05).
  `libpolkit-agent-1` from polkit 127, which quickshell links, watches `notify::owner` on the authority and
  carries the message "Attempting to re-register as an authentication agent.". The re-registration is not
  logged at the journal's level, so this rests on the library code, not on a log line. The live check below
  covers it.

Not done: an interactive `pkcheck --allow-user-interaction` probe. It would put a password dialog on the owner's
desktop, and the team rules forbid driving the desktop. The owner's live check replaces it.

Conclusion: option C.

## Design

### Rule (p620 and razer)

In `modules/security/default.nix`, replace the `users`-group rule (lines 27-40) with:

```js
// Power actions need the administrator's password from every caller, the active session included (#2761).
polkit.addRule(function (action, subject) {
  if (action.id == "org.freedesktop.login1.reboot" ||
      action.id == "org.freedesktop.login1.reboot-multiple-sessions" ||
      action.id == "org.freedesktop.login1.power-off" ||
      action.id == "org.freedesktop.login1.power-off-multiple-sessions") {
    return polkit.Result.AUTH_ADMIN;
  }
});
```

- **`AUTH_ADMIN`, not `AUTH_SELF`.** Both ask for `olafkfreund`'s password today: `addAdminRule` names
  `unix-group:wheel` and the owner is its only member. `AUTH_ADMIN` stays correct if a user outside wheel is
  ever added, because that user then cannot authorise with their own password.
- **No `_KEEP`.** The owner asked for a prompt on every reboot and power-off. A kept authorisation lasts
  300 seconds by default, and polkit may let a later process in the same session reuse it, so with `_KEEP` an
  agent could ride on the owner's authorisation inside that window. `AUTH_ADMIN` keeps nothing, so how polkit
  scopes a kept authorisation does not matter.
- **What "authentication" means.** `AUTH_ADMIN` asks the agent to authenticate an administrator through PAM's
  `polkit-1` service. On p620 that stack is `pam_unix` only, so it is the owner's password. The Omarchy dialog
  also supports fingerprint if `polkit-1` is configured for it; razer's stack was not read.
- **No group test and no `subject.local`/`subject.active` test.** The point is to cover the active session.
  Root is unaffected: logind lets a caller with `CAP_SYS_BOOT` through before it asks polkit.
- **`-ignore-inhibit` variants and `halt` are left out.** Their defaults are already `auth_admin_keep` for every
  caller, so they already need the password. Leaving them out keeps p510's override a plain prepend (below).
  Today's inhibitors on p620 are all `delay` mode (`systemd-inhibit --list`), so a menu reboot never needs them.
- **Suspend and hibernate** are not touched (owner decision 2).
- The other rules in the file (`security.sudo` above, and every other module's `extraConfig`) stay as they are.

### p510 override

`security.polkit.extraConfig` has type `lines`, and nixpkgs writes it after the `addAdminRule` in
`/etc/polkit-1/rules.d/10-nixos.rules`. polkit stops at the first rule that returns a result. So
`hosts/p510/configuration.nix` restores today's behaviour by putting today's rule first:

```nix
# Today's power rule, kept on p510 until the owner schedules it (#2761). Runs before the
# AUTH_ADMIN rule from modules/security/default.nix, so it wins.
security.polkit.extraConfig = lib.mkBefore ''
  polkit.addRule(function(action, subject) {
    if (subject.isInGroup("users") && (
        action.id == "org.freedesktop.login1.reboot" ||
        action.id == "org.freedesktop.login1.reboot-multiple-sessions" ||
        action.id == "org.freedesktop.login1.power-off" ||
        action.id == "org.freedesktop.login1.power-off-multiple-sessions")) {
      return polkit.Result.YES;
    }
  });
'';
```

The new rule still follows in p510's file and matches nothing that the first rule has not already answered for a
`users` member. So p510 is unchanged for every member of `users`, which is every login user on it. It is not
byte-for-byte unchanged: a non-root caller outside `users` in p510's active session now needs authentication
where systemd's defaults would have said yes. No such caller is known. Excluding p510 from the module's rule
entirely would need a host option, rejected below. p510 is evaluated, never built, by the team.

### What the Omarchy menu does afterwards

`omarchy-system reboot|shutdown` starts itself with `systemd-run --user … RuntimeMaxSec=30s`, shows the OSD, clears
the `re*-required` state markers (`omarchy-state clear`, line 49), closes every window with a 2-second bound
(`omarchy-hyprland-window-close-all --wait`), then runs `systemctl reboot --no-wall` or
`systemctl poweroff --no-wall` (shutdown inside a `systemd-inhibit --what=sleep:idle:handle-lid-switch` block).
After the change:

1. the markers are cleared and the windows close, as today;
2. the Omarchy polkit dialog asks for authentication;
3. success: the host reboots or powers off, as today;
4. cancel or failed authentication: `systemctl` fails and the script sends the critical notification
   "reboot failed" / "shutdown failed". The windows are closed and the "reboot required" marker is gone;
5. no answer before the 30-second limit: systemd kills the whole unit, the script included, so there is **no**
   notification. The dialog's request is cancelled with it.

An agent that runs `systemctl reboot`, `omarchy-system reboot` or `systemd-run --user systemctl reboot` gets the
same dialog on the owner's screen and cannot answer it. Over SSH with a terminal, `systemctl` starts a text agent
(`pkttyagent`) and the owner can type the password there; without a terminal the request fails.

## Alternatives rejected

- **A, delete the rule.** The fallback only. polkit cannot tell an agent from the owner in the active session,
  and `systemd-run --user` reaches that session from SSH, so A stops only `ssh host systemctl reboot`.
- **B, `subject.local && subject.active`.** Same effect as A, more code.
- **`AUTH_SELF` / `AUTH_SELF_KEEP`.** The same password today, but a future non-wheel user could authorise with
  their own.
- **`AUTH_ADMIN_KEEP`.** The owner asked for a prompt every time; see "No `_KEEP`".
- **Adding suspend and hibernate.** The owner decided against it; razer's idle suspend would prompt.
- **Adding `-ignore-inhibit` and `halt`.** They already need the password by default.
- **A per-host option (`features.…`) to switch the rule.** An option for one host's temporary exception; the
  `mkBefore` prepend does the same with no new option, and is deleted when p510 follows.
- **`lib.mkForce` on `security.polkit.extraConfig` for p510.** It would also drop every other module's rules
  (nh's `pkexec` rule, libvirt, NetworkManager, CUPS, fwupd).
- **A separate agent user (issue 2760).** Closed as not planned.
- **Guard hooks only.** They match command text and do not stop a determined caller.

## Risks

- **No agent answers, so the owner cannot reboot from the menu.** This happens if the shell is crashed or
  restarting, at the SDDM greeter, or if re-registration after a polkitd restart fails. The menu then reports
  "reboot failed" after it has already closed the windows. Ways out, none of which go through this rule:
  `omarchy-restart-shell` and try again; `systemctl reboot` in a terminal, which prompts through `pkttyagent`;
  `sudo systemctl reboot`; or the power button, which logind handles itself (`HandlePowerKey`, default
  `poweroff`). Hosts: p620, razer.
- **The 30-second limit.** `RuntimeMaxSec=30s` on the menu's unit leaves about 28 seconds to authenticate, and
  a timeout ends silently: windows closed, no reboot, no notification. This is upstream nixarchy behaviour;
  report it there if it bites.
- **State is changed before the prompt.** A cancelled or failed prompt leaves the session without its windows
  and without the "reboot required" marker, and no reboot happened. Graceful closing is today's behaviour; only
  the cancel case is new. The marker is set again by the next deploy that needs a reboot, not before.
- **Unattended jobs.** No user-level caller of a power action exists in the repo (intent, "What relies on the
  rule"). Root callers and the p510 watchdog do not go through polkit. Unchanged.
- **razer lid and idle.** The lid is handled by logind itself (`hosts/razer/nixos/laptop.nix:44-47`), and idle
  suspend uses `suspend`, which the rule does not cover. Unchanged.
- **Agents keep other paths** until issue 2759 ships: passwordless `sudo`. They keep `suspend` and `hibernate`
  by the owner's decision. This change is effective against agents only once 2759 has landed on that host.
- **Rule order on p510** depends on `mkBefore` placing the prepend before the module's rule; the eval check
  below proves it.

## Verification

1. **Eval** (no build): `nix eval --raw` of
   `nixosConfigurations.<host>.config.environment.etc."polkit-1/rules.d/10-nixos.rules".text` for p620 and razer
   shows the `AUTH_ADMIN` rule and no `Result.YES` power rule. For p510 the `Result.YES` rule comes before the
   `AUTH_ADMIN` rule.
2. **Build**: `just test-host p620` and `just test-host razer`. p510 is not built by the team.
3. **After deploy, from an agent shell on p620 and razer**, with a script file so the guard does not match the
   command line: one `pkcheck --action-id org.freedesktop.login1.<action> --process $$` per action, without
   `--allow-user-interaction`. `reboot`, `reboot-multiple-sessions`, `power-off` and
   `power-off-multiple-sessions` each exit 2 (authentication needed, no interaction allowed); `suspend` still
   exits 0. This only asks polkit; it powers nothing and shows no dialog.
4. **Re-registration after a polkitd restart.** Before and after the deploy, record polkitd's PID
   (`systemctl show -p MainPID polkit`) and the shell's PID. A rules-only change only reloads polkitd
   (`reloadTriggers`); it restarts only when `system.path` changes. Step 5 counts as a re-registration test only
   if polkitd's PID changed and the shell's did not. Otherwise repeat step 5 after the next deploy that does
   restart polkitd.
5. **Owner's live check on p620 and razer**: menu → Reboot → the Omarchy dialog appears; cancel → "reboot failed"
   notification and no reboot; menu → Reboot → leave the dialog unanswered for 30 seconds → no reboot, no
   notification; menu → Shutdown → cancel → "shutdown failed" (the `systemd-inhibit` path); menu → Reboot →
   authenticate → the host reboots. On razer also: close the lid on battery → it suspends with no prompt.
6. **p510**, when the owner schedules it: unchanged for `users`. A `pkcheck` per action from an agent shell
   there still exits 0, which also proves the prepended rule wins at runtime.

## Owner decision, 2026-11-07

The owner approved option C. A cancelled or timed-out menu reboot leaves the windows closed with no
reboot, and the owner accepts this. Asking nixarchy to prompt before it closes windows is tracked
upstream in nixarchy.
