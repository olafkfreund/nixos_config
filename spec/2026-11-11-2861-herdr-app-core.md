# Spec: the Herdr desktop app and herdr-core (hc) on p620 and razer

Approved intent decisions: packages in `pkgs/`; `hc` starts on demand (no
Nix service); installed as `hc` next to `herdr-core`; telemetry off through
the launch environment; linger declared on for p620 and razer. **Adoption
is gated on verification**: the packages stay in the profile only if every
on-host check below passes on both hosts. Otherwise they come back out (see
Rollback in the plan).

## Design

### 1. `pkgs/herdr-core/default.nix` (new)

- `fetchurl` of
  `https://releases.herdr.dev/core/${version}/herdr-core-linux-x86_64.tar.gz`
  (0.1.20, hash from `core/latest.json`:
  `ac6b8689…14e74`). The binary is static-pie, so there is no patchelf.
- Install `$out/bin/herdr-core` and a symlink `$out/bin/hc -> herdr-core`
  (as the upstream installer does), plus `LICENSE` and
  `THIRD-PARTY-NOTICES` under `share/doc`.
- `passthru.skill`: a `runCommand` that runs `herdr-core --skill` with
  `HOME=$TMPDIR` and writes `SKILL.md` with YAML frontmatter prepended
  (`name: hc`, and a description saying when to use it: the runtime for
  long-lived terminals and agents, not the Herdr TUI). `hc --skill` prints
  no frontmatter, and Claude Code needs it to list the skill.
- `meta.platforms = [ "x86_64-linux" ]`. A bump comment names the manifest
  URL.

### 2. `pkgs/herdr-app/default.nix` (new)

Modelled on `pkgs/okena/default.nix` (another prebuilt GPUI app):

- `fetchurl` of
  `https://releases.herdr.dev/app/${version}/herdr-app-linux-x86_64.tar.gz`
  (0.1.15, hash from `app/latest.json`: `f99e1e04…655dd`).
- `autoPatchelfHook` with `buildInputs = [ libxkbcommon libxcb
  stdenv.cc.cc.lib ]` (its NEEDED entries).
- Install `bin/herdr-app`, the SVG icon to
  `share/icons/hicolor/scalable/apps/herdr-app.svg`, and a
  `makeDesktopItem` desktop entry (`Name=Herdr`, `Exec=herdr-app`,
  `Categories=Development;TerminalEmulator;`).
- `wrapProgram` with:
  - `--prefix LD_LIBRARY_PATH` for what it loads at runtime:
    `vulkan-loader`, `libglvnd` (`libEGL`), `wayland`, `libxkbcommon`
    (as in okena).
  - `--prefix PATH` for `curl` and `pipewire` (`pw-play`, for sounds), and
    `herdr-core`, so the app always finds **our** core first.
  - `--set HERDR_CORE_DIRS ${herdr-core}/bin`: the app's own lookup
    setting, which pins the core.
  - `--set HERDR_TELEMETRY 0` and `--set DO_NOT_TRACK 1`: telemetry off on
    every launch, from the menu or a shell. `settings.json` stays writable
    and untouched.
  - **Self-update off:** `--set HERDR_RELEASES_URL file://${releases}`,
    where `releases` is a small `linkFarm`/`writeTextDir` tree holding
    `app/latest.json` and `core/latest.json`. Each manifest names exactly
    the packaged version (app `core_min` copied from upstream). The app's
    hourly check then reads a local file that always says "you are current",
    so it never downloads, stages or nags. `curl` reads `file://` URLs. The
    app reads this one variable for its release manifests and notes (the
    upstream installer uses the same variable for test servers).
- `passthru.skill`: as for the core, from `herdr-app --skill`, with
  `name: herdr-app` frontmatter (driving the person's Herdr window).

## Alternatives rejected

- **Upstream `curl | sh` installers:** they write into `~/.local`, update
  themselves, and aren't declarative.
- **Our own flake (like `nix-craftapps`):** a two-repo bump cycle for two
  derivations that change often. Rejected at the intent gate.
- **A systemd user service for `hc`:** `hc` starts its own server with
  `systemd-run --user`, and the app starts it on demand. A Nix unit would
  fight that lifecycle. Rejected at the intent gate.
- **Blocking updates with a dead `HERDR_RELEASES_URL`** (for example
  `http://127.0.0.1:9`): it would also stop updates, but every hourly check
  would fail, which risks an error badge. A local manifest that reports
  "current" is quieter. This is the fallback if `file://` turns out not to
  be accepted (Verification 6).
- **Patching the binary's update code:** fragile on every bump.
- **Telemetry through `settings.json`:** the app rewrites that file, so a
  Nix-managed copy would be read-only, and a seeded one could be
  overwritten.

## Risks

- **The update guard rests on one variable.** If a future app version stops
  honouring `HERDR_RELEASES_URL`, it would try to replace itself in
  `/nix/store` and fail (read-only), possibly with a visible error.
  Verification 6 checks it on every bump.
- **GPU on razer.** wgpu picks a Vulkan adapter itself, and on razer's
  hybrid Intel/NVIDIA it could wake the dGPU or pick a device that can't
  present to Wayland. Verification 3 checks this on razer. If it fails, the
  fix (for example a `WGPU_ADAPTER_NAME` / `DRI_PRIME` choice in the
  wrapper) is a plan deviation with its own check, not a fleet-wide offload
  change.
- **A rebuild while an older core server runs.** The running server keeps
  its old store path (Nix GC treats running processes' paths as roots),
  and `hc` documents that older holders "run their terminals to the end".
  The app may show "Herdr needs a newer herdr-core" until `hc server
  restart`, which keeps terminals. Accepted, and noted in the package
  comment.
- **Linger on razer** keeps user units, including `hc` and anything an
  agent left running, alive after logout on a laptop. The owner accepted
  this at the intent gate.
- **0.1.x churn:** frequent bumps, two hashes each. Each bump re-runs
  Verification 2-7 on p620.
- **Binary trust:** prebuilt, unsigned upstream tarballs pinned by
  sha256, the same trust level as okena and the other prebuilt apps.

## Verification

Gate: all of 1-8 pass on both hosts, or the packages come back out.

1. **Build:** `nix-instantiate --parse` on each new or changed file;
   `nix build .#nixosConfigurations.{p620,razer}.config.system.build.toplevel`
   (`just test-host` for each); the skill outputs contain `name: hc` and
   `name: herdr-app` frontmatter.
2. **Cold start** (each host, after the deploy, announced): `hc server stop`
   if one is running, then start Herdr from the launcher (`uwsm-app` /
   desktop entry). A window opens, and `hc ls` lists its terminal.
   `readlink -f /proc/<core pid>/exe` is our store path.
3. **Native Wayland and rendering:** `hyprctl clients -j` shows the Herdr
   window with `xwayland: false`. A command typed in its terminal shows
   output. On razer, it renders without errors in the app log
   (`~/.config/herdr-app` logs). Note which adapter it picked.
4. **Persistence:** close the window and reopen it; the terminal and its
   scrollback are still there. `hc attach` / `hc read` from a shell reach
   the same terminal.
5. **Telemetry off:** the running app's `/proc/<pid>/environ` has
   `HERDR_TELEMETRY=0` and `DO_NOT_TRACK=1`. After a short session, nothing
   has been queued in the app's telemetry `queue`, and no connection to
   `telemetry.herdr.dev` shows in `ss -tp`.
6. **No self-update:** trigger the in-app update check (Settings >
   Updates). It reports current, with no error. No `.download` / `.new`
   staging files appear under `~/.config/herdr-app`, nothing appears in
   `~/.local/bin` or `~/.local/share/herdr-app`, and `which herdr-app hc
   herdr-core` all resolve to the Nix profile.
7. **Coexistence:** `herdr` (the TUI) starts, `herdr --skill` and the
   `herdr` skill are unchanged, and `herdr-team status` still works.
   `claude` started in an `hc` terminal is plain `claude`, not
   `herdr-claude-teams`.
8. **Linger:** `loginctl show-user olafkfreund -p Linger` gives `yes` on
   both hosts.
