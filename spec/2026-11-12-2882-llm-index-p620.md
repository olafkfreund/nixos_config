# Spec: enable llm-index on p620 for Claude Code, Codex and agy

## Design

### 1. Flake input

In `flake.nix`, next to the other nixarchy inputs (for example after
`nixarchy-meetingai`, around line 139):

```nix
# nixarchy-llm-index: local document and code index served to agents over MCP;
# hosts/common/nixos/llm-index.nix (#2882).
nixarchy-llm-index = {
  url = "github:olafkfreund/nixarchy-llm-index/<merge commit of nixarchy-llm-index#8>";
  inputs.nixpkgs.follows = "nixpkgs";
  inputs.home-manager.follows = "home-manager";
};
```

The input is pinned by revision in the URL, as `nixarchy-omatheme` is, so a
flake update cannot move it ahead of a tested build. `flake.lock` gains only
this input: `nix flake lock` adds it without touching the others.

### 2. Host module `hosts/common/nixos/llm-index.nix`

Imported only by `hosts/p620/nixos/nixarchy.nix`, next to
`omarchy-meetingai.nix`. It is a NixOS module that sets
`home-manager.users.olafkfreund`, like meetingai:

```nix
{ inputs, ... }:
{
  home-manager.users.olafkfreund = { config, lib, pkgs, ... }:
    let cfg = config.services.llm-index; in {
      imports = [ inputs.nixarchy-llm-index.homeManagerModules.default ];
      services.llm-index = {
        enable = true;
        roots = {
          source = { path = "/mnt/code/Source-home"; tier = "public"; }; # ~/Source is a symlink
          docs.path = "${config.home.homeDirectory}/Documents";           # private (default)
        };
        limits.memoryMaxMb = 2048; # the trial sat at the 768 MB soft limit of the 1 GB default
      };
      home.packages = [ cfg.package ];
      home.file.".claude/rules/llm-index.md".text = cfg.agentInstructions;
      home.activation.llmIndexMcp = …; # section 3
    };
}
```

- The user service runs under the module's own hardening: Landlock
  workers, `NoNewPrivileges`, `RestrictAddressFamilies = AF_UNIX`, and a
  system-call filter (intent: the user-service exception).
- The state lives in `~/.local/state/llm-index`, which is new, so the
  first start re-indexes, about 15 minutes going by the trial.
- `registerPublic` keeps its default (`programs.mcp.servers`); nothing in
  this repo reads it today.

### 3. MCP registration, converging (`home.activation.llmIndexMcp`)

The entry runs `lib.hm.dag.entryAfter [ "writeBoundary" ]`.

**Desired entry.** `cfg.mcpServers.public` gives the absolute store path of
`llm-index` with `mcp --tier public --config <xdg config path>`. Its store
path changes on every upgrade, which is why registration has to converge
rather than only add.

**For each client** the entry reads the current entry for `llm-index` as
`{command, args}` JSON and compares it with the desired value:
- Claude Code: `jq '.mcpServers["llm-index"] | {command, args}'
  ~/.claude.json`. The file is only read, never written by jq.
- Codex: `codex mcp get llm-index --json | jq '.transport | {command, args}'`.
- agy: `jq '.mcpServers["llm-index"] | {command, args}'
  ~/.gemini/config/mcp_config.json`.

**When they differ or the entry is missing,** it calls the client's own CLI:
`<client> mcp remove llm-index`, ignoring a "not found", then
`<client> mcp add llm-index -- <command> <args…>`. Claude Code uses
`-s user` for both. Because nothing is written when they match, there is
no churn in `~/.gemini` (it syncs across hosts) and no rewrite of
`~/.claude.json` on every switch.

**Rules for the entry:**
- Binaries are absolute: `${config.home.profileDirectory}/bin/<client>`,
  as `codex-cli.nix` does for codex, falling back to
  `/run/current-system/sw/bin/<client>` (where `agy` lives on p620).
- Writes go through `$DRY_RUN_CMD`.
- A missing entry (empty jq result, or `mcp get` failing with "not found")
  is told apart from other CLI errors. Any other error skips that client
  with the warning.
- It prints `llm-index: registered in <client>` only when it changes an
  entry.
- A client that is not installed is skipped.
- Any failure prints `llm-index: could not register in <client>` and goes
  on, since activation entries must never `exit`.
- Only the public server is registered.

This also replaces the trial's entries, because their command differs.

### 4. Instructions for Codex and agy

`home/development/agent-rules.nix` takes `config` and appends one block to
both `protocol` lists:

```nix
llmIndex = lib.optional (lib.attrByPath [ "services" "llm-index" "enable" ] false config)
  config.services.llm-index.agentInstructions;
```

On hosts without the module, `attrByPath` returns `false` and the list is
empty, so their `AGENTS.md` output is byte-identical. Claude Code gets the
same text from `~/.claude/rules/llm-index.md` (section 2), which Claude Code
loads like `~/.claude/rules/craftapps.md`.

### 5. Retire the trial (after the deploy)

Done once by hand, not in Nix:
- `systemctl --user stop llm-index-trial`;
- remove `~/.cache/llm-index-trial`, `~/llm-index-trial-bin` and
  `~/llm-index-trial.toml`.

The registrations were already replaced in section 3.

## Alternatives rejected

- **A `modules/` feature flag.** This is one Home Manager module from an
  external flake for one host, like meetingai; a feature option would
  wrap one `imports`.
- **Writing `~/.claude.json` with jq.** Running Claude sessions rewrite
  it at the same time; the CLI handles that.
- **Remove and add on every switch.** It churns the synced `~/.gemini` and
  `~/.claude.json`.
- **A stable `/etc/profiles/per-user/…/bin/llm-index` path,** so the entry
  never changes. It still needs the convergence code to replace the trial
  entries, and it would hide which package version a client runs.
- **Registering the private tier.** Ruled out by the intent.
- **`programs.mcp` integration.** None of the three clients' modules here
  read it.

## Risks

- **First re-index load:** about 15 minutes of CPU and disk on p620 after
  the switch. That is announced on the bus.
- **Upstream agy synced to other hosts:** it shows `llm-index` as failing
  there. Accepted in the intent.
- **The `agent-rules.nix` change touches every host's evaluation.**
  Verified by comparing `drvPath`s, below.
- **Rollback:** a previous generation removes the unit and the
  `rules/llm-index.md` file. The MCP entries stay, pointing at a store path
  that still exists while that generation exists. Remove them with
  `<client> mcp remove llm-index`.

## Verification

1. `just check-syntax`.
2. Run `just test-host p620` (build only).
3. **Other hosts unchanged.** The whole-system `drvPath` embeds
   `system.configurationRevision` (`flake.nix` around line 396), so compare
   the generated files instead. For razer and p510, run `nix eval --raw` of
   `.#nixosConfigurations.<host>.config.home-manager.users.olafkfreund.home.file`
   `.".codex/AGENTS.md".source` and the same for `.".gemini/AGENTS.md"`. Each
   must give the same store path on `origin/main` and on the branch. Also
   check that neither host has the `llmIndexMcp` activation entry. This is
   evaluation only, no build.
4. Generated `~/.codex/AGENTS.md` and `~/.gemini/AGENTS.md` for p620
   contain the llm-index section once.
5. Bus announcement, then deploy p620 with `just p620` from the shared
   checkout after the merge.
6. After the switch:
   - `systemctl --user is-active llm-index` reports active;
   - `llm-index status` shows both roots `ok` once indexing finishes;
   - the journal has no errors;
   - in a **new** session of each client, a `search` call returns hits;
   - `codex mcp get llm-index --json`, `claude mcp get llm-index` and
     `agy mcp list` show the store path, not the trial path;
   - a public search for `.env`, `id_rsa`, `-----BEGIN` and a known
     document term returns nothing from the denylist or from
     `~/Documents`.
7. Re-running activation prints no `llm-index: registered in` line: the
   entries already match, so nothing is written. Other activation entries,
   such as the agy `mcp_config.json` merge, may rewrite their files as they
   do today; they are out of scope.
8. Retire the trial (section 5), with its own bus announcement before
   stopping the unit.
