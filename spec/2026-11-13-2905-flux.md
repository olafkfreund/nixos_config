# Spec: Flux on p620 and razer

## Decisions carried from the intent's open questions

- The Omarchy shell plugin comes (Flux in the bar). The browser extension does not.
- The Tab S8 Ultra stays as it is. Pairing razer is a manual step on the phone, done once.
- razer opens Flux only on networks marked trusted (owner, 2026-11-13: "trusted networks only"). Home works without
  setup. On any other network Flux's ports are blocked and razer sends no mDNS there.

## Design

### 1. Flake input

In `flake.nix`'s `inputs`, next to the other desktop flakes (pattern at `flake.nix:132-135` and `:147-151`):

```nix
nixarchy-flux = {
  url = "github:olafkfreund/nixarchy-flux";
  inputs.nixpkgs.follows = "nixpkgs";
};
```

`flake.lock` pins it to master after nixarchy-flux#59 merges. Inputs reach modules through `specialArgs`
(`flake.nix:396-406`), and Home Manager through `extraSpecialArgs` (`:451-463`).

### 2. `modules/desktop/flux.nix`: `features.flux`

Imported from `modules/desktop/default.nix`, beside `tfm.nix` (the chain `modules/desktop/default.nix:9-10` →
`modules/desktop.nix:5` → `hosts/templates/desktop.nix:7` reaches both hosts). The shape copies `modules/desktop/tfm.nix:7-20`.

```nix
{ config, lib, inputs, username, ... }:
let cfg = config.features.flux; in
{
  imports = [ inputs.nixarchy-flux.nixosModules.default ];

  options.features.flux = {
    enable = lib.mkEnableOption "Flux, the phone link (fluxd, flux-cli, the shell plugin)";
    trustedConnections = lib.mkOption {
      type = lib.types.nullOr (lib.types.listOf lib.types.str);
      default = null;
      description = "NetworkManager connection UUIDs where Flux may be reached; null = no guard (section 3).";
    };
  };

  config = lib.mkIf cfg.enable { ... };
}
```

When enabled:

- **NixOS side.** `services.flux = { enable = true; users = [ ]; openFirewall = false; approve.services = [ ];
  webcam.enable = false; }`. This installs `flux`, its runtime tools and the udev rule (upstream `nix/nixos.nix:90-91`).
  With `users = [ ]`, it defines no user unit (`:114`).
- **Home Manager side.** `home-manager.users.${username}`:
  - `imports = [ inputs.nixarchy-flux.homeManagerModules.default ]`
  - `services.flux = { enable = true; plugin.enable = true; browser.enable = false; }`

  This is the hybrid Flux documents (`docs/nix.md:89-91`). Home Manager owns the single `fluxd` user unit, wanted by
  `graphical-session.target` (`nix/home-manager.nix:121-139`), and copies the shell plugin to
  `~/.config/omarchy/plugins/flux` as a real folder (`:143-152`). It isn't a symlink, because `fluxd`'s plugin sync
  refuses symlinks (`internal/plugin/plugin.go:174-184`). The plugin is turned on once with `flux-cli setup`; that is
  a manual step, documented.
- **Avahi.** Flux's module sets four Avahi options with `lib.mkDefault` (`nix/nixos.nix:93-100`). This module sets
  nothing further about Avahi:
  - **p620:** `hosts/p620/configuration.nix:635-648` sets Avahi at normal priority, so its `allow-interfaces = [
    "enp1s0" ]` pin (#2293) and publish settings win over Flux's defaults. The pin stays.
  - **razer:** Avahi runs on every interface through `features.gnome-remote-desktop`
    (`modules/desktop/gnome-remote-desktop.nix:79-87`), and Flux announces itself through it (Flux
    `internal/lan/mdns.go:223`, `ifaceUnspec`). Section 3 stops all mDNS leaving an untrusted interface.
- **Service hardening exception.** It is recorded in the module and in `docs/`, with the same argument as
  `modules/programs/claude-swarm-reaper.nix:25-26`:
  - `fluxd` is a user unit that serves the user's own files, clipboard and phone link. `DynamicUser` and `ProtectHome`
    would break that, and `ProtectSystem=strict` needs mount namespacing that a user unit lacks.
  - `NoNewPrivileges` is left off too: `fluxd` runs the user's saved commands from the phone (`commands.run`), and
    with it set, `sudo` and other setuid wrappers in them would fail.
  - No seccomp option such as `LockPersonality`: on a user unit it implies `NoNewPrivileges` (#2909, found after
    merge; this replaces the earlier `LockPersonality = true`).

### 3. The razer network guard: `features.flux.trustedConnections`

`fluxd` binds every address. TCP 12100–12108 and UDP 12100 are listened on through `":<port>"` (Flux
`internal/lan/provider.go:168,179`), and the payload ports are 12070–12099 (`docs/security.md:165`). No option binds
them to an interface (`internal/config/config.go:29-109`). razer has the firewall off (`hosts/razer/configuration.nix:91`),
so no `nixos-fw` chain exists, and the `networking.firewall.interfaces` rules other modules use don't take effect.
Its Wi-Fi is the same `wlan0` at home and on guest networks (`hosts/razer/nixos/power.nix:101-102`).

**Option.** `features.flux.trustedConnections`: a list of NetworkManager connection UUIDs, default `null` (no guard).
UUIDs are opaque, so no SSID lands in the repo. When it is set:

**The table**, loaded by a system oneshot `flux-guard.service`:

```nft
table inet flux_guard {
  set trusted { type ifname; elements = { "lo", "tailscale0" } }
  chain input {
    type filter hook input priority filter - 1; policy accept;
    iifname @trusted accept
    ct state new tcp dport 12070-12108 drop
    ct state new udp dport 12100 drop
  }
  chain output {
    type filter hook output priority filter - 1; policy accept;
    oifname @trusted accept
    udp dport 5353 drop
    udp sport 5353 drop
    udp dport 12100 drop
  }
}
```

**Effect on an untrusted interface.** Everything else passes.

- **Inbound:** a new connection to Flux's ports is refused. Only `ct state new` is matched, so replies to razer's own
  outgoing connections still arrive, even when Linux picked a source port in 12070–12108.
- **Outbound, discovery:** nothing announces razer.
  - All mDNS is dropped: queries and answers to 5353, and answers from 5353 to a legacy querier's own port. That
    covers Flux's Avahi service, GNOME remote desktop's, and Avahi answering anyone who asks.
  - Flux's own identity broadcast to UDP 12100 (Flux `internal/lan/provider.go:219`, sent at start and on network
    changes, `internal/core/daemon.go:608`) is dropped too.

**Two units.** The guard loads early, but NetworkManager starts after `network-pre.target`, so trust is synchronised by
a second unit:

- **`flux-guard.service`** installs the table and nothing else:
  - `wantedBy = [ "multi-user.target" ]`, `before = [ "network-pre.target" ]`, `wants = [ "network-pre.target" ]`.
    That follows NixOS's own firewall unit; `network-pre.target` is passive.
  - `Type = oneshot`, `RemainAfterExit = true`.
  - **Atomic load:** one `nft -f` file holds `table inet flux_guard`, then `delete table inet flux_guard`, then the
    definition. nft applies a file as one transaction, so the table is never missing, and a failed load leaves the
    old table in force. `nft --check` passes on the pinned nftables 1.1.7 (Codex review, in a network namespace).
  - `ExecReload` repeats the atomic load. `ExecStop` deletes the table.
- **`flux-guard-sync.service`** puts the right interfaces in `@trusted`:
  - `after = [ "NetworkManager.service" "flux-guard.service" ]`, `bindsTo = [ "flux-guard.service" ]`,
    `wantedBy = [ "multi-user.target" ]`.
  - `reloadPropagatedFrom = [ "flux-guard.service" ]`, so a guard reload (which resets the set) runs the sync again.
  - `Type = oneshot`, `RemainAfterExit = true`; `ExecStart` and `ExecReload` are the reconcile script.

**The reconcile script** is the only thing that changes `@trusted`. It never trusts an event's own fields, only the
state at the moment it runs:

- It takes an exclusive `flock` on `/run/flux-guard.lock`, so concurrent runs queue.
- It reads `nmcli -t -f UUID,DEVICE connection show --active`, and keeps the devices whose connection UUID is in
  `trustedConnections`.
- In one `nft -f` transaction it flushes `@trusted` and adds `lo`, `tailscale0` and those devices.

**The NetworkManager dispatcher script** (`networking.networkmanager.dispatcherScripts`, type `basic`) runs the
reconcile script on every `up`, `down`, `pre-down`, `dhcp4-change` and `connectivity-change` event. A late or obsolete
`up` handler therefore can't re-add an interface that now carries an untrusted connection: it rebuilds the set from
what is active when it runs. On `pre-down` the interface is still active, so trust ends no later than the following
`down`.

**Executables and hardening.**

- **Executables** are store paths: `${pkgs.nftables}/bin/nft`, `${pkgs.networkmanager}/bin/nmcli` and
  `${pkgs.util-linux}/bin/flock`.
- **Both units** take a reasoned exception to `DynamicUser`, because they need `CAP_NET_ADMIN` in the host network
  namespace. They apply `CapabilityBoundingSet = [ "CAP_NET_ADMIN" ]`, `NoNewPrivileges`, `ProtectSystem = "strict"`,
  `ProtectHome`, `PrivateTmp`, `ReadWritePaths = [ "/run" ]` (for the lock), `RestrictAddressFamilies = [ "AF_NETLINK"
  "AF_UNIX" ]` and `ProtectKernelModules`.
- **The capability set works** (Codex review): nft uses netlink, and nmcli uses D-Bus over a Unix socket.

**What it costs razer:**

- **On trusted networks:** nothing. Home works with no setup, as the intent promises.
- **On other networks:** a phone can't open links to razer or pair from the phone, and razer isn't discoverable.
  razer still dials out to known phones (`docs/security.md:168`). Over Tailscale both directions work, once the phone's
  Tailscale address is added (`docs/tailscale.md`).
- **mDNS on untrusted networks:** razer sends no mDNS there at all. That hides GNOME remote desktop, which is
  intended. It also stops `.local` name resolution and printer and service discovery on those networks, an accepted
  cost for a guest or work network.

**p620:** `trustedConnections = null`, so no guard. It sits on the trusted home LAN, and its Avahi is pinned to
`enp1s0`.

### 4. Hosts

- `hosts/p620/configuration.nix`, next to `features.tfm` (`:518-521`): `features.flux.enable = true;`
- `hosts/razer/configuration.nix`, next to `features.tfm` (`:339`): `features.flux = { enable = true;

  connection show` when the plan runs.

### 5. The handover on p620

The hand-started `fluxd` (pid 2397965, started from agent session `9f0892`'s scratchpad) and the new unit share the
user's state:

- config: `~/.config/flux/config.toml`
- pairings and identity: `~/.local/share/flux/devices.json`, `certificate.pem` and `privateKey.pem`
  (`internal/config/config.go:205,219`, `internal/proto/cert.go:26-27`)
- socket: `$XDG_RUNTIME_DIR/flux/fluxd.sock`

The pairings carry over: the hand-started process uses the default XDG paths (checked 2026-11-13 from
`/proc/2397965/environ`: `XDG_DATA_HOME=~/.local/share`, `XDG_CONFIG_HOME=~/.config`), and `~/.local/share/flux` holds
the certificate, key and `devices.json`. Flux has no single-instance lock, so the old process
stops before the unit starts. The order is:

1. announce on `#agents` and tell session `9f0892`
2. stop the old process
3. switch
4. check

## Alternatives rejected

- **NixOS `users = [ "olafkfreund" ]` only:** no shell plugin. The intent wants it.
- **Both modules owning the unit:** Flux's docs forbid it (two `fluxd.service` definitions).
- **Tailscale only on razer, even at home:** the owner chose trusted networks, so home works without setup.
- **Turning razer's NixOS firewall on:** a host-wide change far beyond this task, and it touches Docker and libvirt.
- **`networking.nftables.enable` on razer:** it switches the firewall backend and conflicts with Docker's iptables use.
- **A bind-address patch in Flux:** a cross-repo change for a single host. It can come later, and then the guard goes.
- **Avahi `allow-interfaces` on razer:** it is static, so it can't follow home versus away on one `wlan0`. The output
  rule does.

## Risks

- **The guard drops something it shouldn't.** It touches only Flux's own ports; everything else is `accept`. A
  mistake shows as "razer can't be reached by the phone". `systemctl stop flux-guard` removes it.
- **The handover loses pairings:** unlikely, since the paths were checked. Re-pairing is the fallback.
- **The Flux input build:** the first build compiles Go and Qt (`flux-gui`). The CI cache doesn't have it, so time is
  spent on p620. Razer builds through p620.
- **Dispatcher timing:** handlers run asynchronously, so an interface may stay trusted for a moment after it switches
  to an untrusted connection, until the `pre-down` or `down` reconcile runs. Every reconcile reads the current state,
  so a stale handler never leaves wrong trust behind. A trusted network that just came up is closed until its `up`
  reconcile, which is the safe side.
- **Shared hosts:** p620 runs CI runners and agents, and razer has a linger session. The deploy is announced, and
  `fluxd` is a user service that disturbs nothing else.

## Verification

- **Eval and build:** `just test-host p620` and `just test-host razer`. Both build with
  `features.flux.enable`, and p510 doesn't change (`nix eval`: `features.flux.enable` is false).
- **p620 after the switch:**
  - `systemctl --user is-active fluxd` is active, and the unit is from Home Manager.
  - `flux-cli status --json` lists the Pixel as paired and online, and the snapshot has `approvals` (#59).
  - Nixi's Phone switch shows "Connected: Pixel 11 Pro XL".
  - The shell plugin folder exists and is not a symlink.
  - Avahi still allows only `enp1s0` (`avahi-daemon` log or `/etc/avahi/avahi-daemon.conf`).
- **razer after the switch** (`fluxd` runs only in the graphical session, so the user checks need a desktop login,
  not the `hc` linger session):
  - `systemctl --user is-active fluxd`, from the desktop session.
  - `sudo nft list table inet flux_guard` shows the table.
  - On the trusted home Wi-Fi: `nft list set inet flux_guard trusted` contains `wlan0`, and from p620 over the LAN
    `nc -vz -w2 <razer-lan-ip> 12100` connects.
  - After switching to an untrusted connection, or deleting `wlan0` from the set by hand to simulate it: the LAN `nc`
    fails, `tcpdump -i wlan0 udp port 5353` shows no outgoing mDNS, and over Tailscale `nc -vz -w2 razer 12100` still
    connects.
  - A failed reload keeps the old table: load a broken file through the same `nft -f` path, and the table is still
    listed.
  - A good reload while home Wi-Fi stays connected: `systemctl reload flux-guard`, and afterwards `@trusted` holds
    `wlan0` again (the propagated reload re-ran the sync).
  - A rapid trusted to untrusted change, simulated by running the dispatcher for a stale trusted `up` after the switch:
    `@trusted` doesn't contain `wlan0`.
  - On an untrusted interface, `tcpdump -i wlan0 'udp port 12100 or udp port 5353'` shows nothing leaving, including
    after `avahi-browse` from another machine and after a `fluxd` restart. An outgoing connection from a port in
    12070–12108 still gets its replies.
  - `systemctl stop flux-guard` removes the table, and starting it adds it back.
