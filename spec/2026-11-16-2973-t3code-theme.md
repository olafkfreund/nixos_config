# Spec: T3 Code follows the Omarchy theme declaratively

## Design

### One activation step, after nixarchy's first-run theme

A new module, `hosts/common/nixos/omarchy-t3code-theme.nix`, adds one Home
Manager activation entry, `home.activation.t3codeOmarchyTheme`:

- ordered `lib.hm.dag.entryAfter [ "writeBoundary" "nixarchySeed" ]`;
- runs `run ${script}`;
- `script` is a `pkgs.writeShellScript` built by a small Nix function,
  `mkScript { binPath }`, so the tests can build it with stub binaries.

This one trigger covers both cases in the intent:

- **Fresh install.** nixarchy's `nixarchySeed` activation stages the
  first-run theme headless (`nixarchy/modules/home.nix:1265-1276`). It runs
  `omarchy-theme-set`, which in turn runs `omarchy-theme-set-t3code`. Ordered
  after it, our step finds a staged `t3code.json` on the very first
  activation, before any login.
- **Running host.** Every rebuild runs the step again.
- **Retry.** `home-manager-olafkfreund.service` runs activation on every boot
  and every switch, so a skipped run is retried at the next boot or rebuild.

Earlier drafts also had a post-boot hook. It was dropped, for three reasons:

- The hook was only there because the draft assumed no theme exists before the
  first login. `nixarchySeed` shows that assumption was wrong.
- Post-boot hooks run in sequence, in name order, inside the session
  (`omarchy-hook`; `default/hypr/autostart.lua:21`), which made ordering
  fragile.
- The hook was the only caller of `omarchy-theme-refresh`.

### Gating: `mkIf` inside the Home Manager module

`lib.hm.dag` only exists on Home Manager's `lib`, so the user module must be a
function (`omarchy-altscape.nix:19-20`). A `mkIf` cannot wrap a module
function. The enable flag is therefore read in the outer NixOS module, and the
`mkIf` goes inside:

```nix
{ config, pkgs, lib, ... }:
let
  enabled = config.programs.nixarchy.apps.t3-code.enable;
  themeId = "omarchy";
  mkScript = { binPath }: pkgs.writeShellScript "t3code-omarchy-theme" ''…'';
in
{
  home-manager.users.olafkfreund = { lib, ... }: {
    home.activation.t3codeOmarchyTheme = lib.mkIf enabled
      (lib.hm.dag.entryAfter [ "writeBoundary" "nixarchySeed" ] ''
        run ${mkScript { binPath = "…"; }}
      '');
  };
}
```

All three hosts import the module from `nixarchy.nix`, next to
`omarchy-altscape.nix`. With the option off (Razer and p510 today) there is no
activation entry and no `~/.t3` folder.

### Binaries

The script sets `PATH` itself:

```text
${lib.makeBinPath [ coreutils jq ]}:/etc/profiles/per-user/olafkfreund/bin:/run/current-system/sw/bin:$PATH
```

- `omarchy-theme-set-t3code` and `t3` are system packages today:
  `/run/current-system/sw/bin/t3` → `t3code-0.1.8`, and the Omarchy tree
  comes from `environment.systemPackages`.
- The per-user profile comes first, so a later move to `home.packages` still
  resolves.
- `$PATH` is kept as the last fallback, as in `omarchy-enable-once.nix:24`.
- Each binary is checked with `command -v` before use. If one is missing, the
  script logs `t3code-theme: <name> not found` and stops.

A test of `t3 theme set` with an empty environment
(`env -i HOME=… PATH=/run/current-system/sw/bin`) succeeded in 0.4 s. So it
runs inside the Home Manager service, with no Wayland, D-Bus or session
variables. The `t3` wrapper is a compiled launcher that sets its own paths.

### The script

It uses `set -u` and ends with an explicit `exit 0`, so it never fails a
switch or a boot. Home Manager's activation runs under `set -e`. Every log
line goes to stderr with the prefix `t3code-theme:`, and lands in the
`home-manager-olafkfreund` journal.

It starts with `export T3CODE_HOME="$HOME/.t3"`, and every `t3` call passes
`--base-dir "$T3CODE_HOME"`. Omarchy's publisher reads the same variable
(`omarchy-theme-set-t3code:9`), so all steps use one folder. Then:

1. **State folder.** `mkdir -p "$T3CODE_HOME/userdata"`.
2. **Palette source.** If `~/.local/state/omarchy/current/theme/t3code.json`
   is missing, log `no Omarchy palette staged yet; next activation retries`
   and stop.
3. **Publish.** Run `omarchy-theme-set-t3code`, which is Omarchy's own script.
   - On a non-zero exit, log the exit code and stop.
   - On exit 0, it may have skipped a placeholder palette while keeping the
     previous file. In that case, log `palette has unresolved colours; kept
     the previous one`. The script detects this with the publisher's own
     `{{` check.
4. **Select.**
   - If `themes/${themeId}.json` does not exist, log and stop.
   - Read the current theme with `jq -r '.defaultTheme // empty'`, and only
     when `settings.json` exists. A missing file means no theme is set.
   - If the current theme equals `themeId`, do nothing: no `t3` call, so
     `defaultThemeSetAt` stays put.
   - Otherwise run
     `timeout -k 5 30 t3 theme set ${themeId} --base-dir "$T3CODE_HOME"`.
   - Its output goes to a temporary file, not a pipe, so a leftover child
     process cannot block the script.
   - On failure or a timeout, log the exit code and the last lines of the
     output.

### Theme id

`themeId = "omarchy"` is one `let` binding. Step 3 always publishes
`omarchy.json`, which is harmless because Omarchy publishes it on every theme
switch anyway. Step 4 selects `themes/${themeId}.json`. #2974 (package T3 Code
Thememaxed) will set it to `omarchy-plus`, which that plugin publishes. The
publish step is not made conditional.

### Owner decisions carried over

- Force `themeId` whenever it differs, on every activation (each boot and each
  switch).
- Open an upstream nixarchy issue. The module header links it and says the
  module can be deleted once upstream ships it.

## Alternatives rejected

- **A post-boot hook.** No longer needed, because `nixarchySeed` stages the
  theme at activation. The hook also had ordering and race problems (agy).
- **`omarchy-theme-refresh` when `t3code.json` is missing.** A staged theme
  always has `t3code.json` on this Omarchy version. Refreshing headless from
  activation is not supported. A missing palette is logged instead.
- **Write `defaultTheme` with jq.** That bypasses T3 Code's CLI and edits
  app-owned state directly.
- **`home.file` for `themes/omarchy.json`.** It breaks Omarchy's atomic replace
  and T3 Code's file watch.
- **`system.activationScripts`.** It runs as root and would create root-owned
  files under `~/.t3`.
- **Upstream nixarchy only.** That would be slower, so it is the follow-up.
- **A `mkIf` around the whole NixOS module.** It cannot wrap a Home Manager
  module function (agy finding 1).

## Risks

- **`nixarchySeed` is renamed upstream.** `entryAfter` naming an entry that
  doesn't exist is allowed in the Home Manager DAG and silently loses the
  order. On a fresh install the first activation would then log "no palette"
  and the next boot would fix it. The eval check below asserts that the entry
  exists.
- **`t3` hangs.** It is bounded by `timeout -k 5 30`, so activation waits at
  most 35 s.
- **The force decision.** A theme picked in the app reverts at the next boot or
  switch. That is accepted, by the owner's decision.
- **Hosts.** The option is only on for p620. Razer and p510 only evaluate the
  module, and p510 is not deployed.

## Verification

- **Eval, all three hosts.**
  - p620 has `home.activation.t3codeOmarchyTheme`, and its `after` list
    contains `nixarchySeed`.
  - `home.activation.nixarchySeed` exists.
  - Razer and p510 have no `t3codeOmarchyTheme`.
- **Build and lint.** `just check-syntax`. Build p620's toplevel. Run
  `shellcheck` on the generated script.
- **Unit test.** A `checks` derivation (or a `tests/` script, if the repo has
  no checks layout) builds `mkScript` with a `binPath` of stub `t3` and
  `omarchy-theme-set-t3code` binaries. It runs them in a temporary `HOME`, and
  covers:
  1. no staged palette: logs and exits 0, without calling `t3`;
  2. publisher exits 1: logs and does not call `t3`;
  3. placeholder palette: logs and still selects, because the previous file is
     kept;
  4. no `settings.json`: calls `t3 theme set`;
  5. theme different: calls `t3 theme set` with `--base-dir`;
  6. theme already `themeId`: does not call `t3`;
  7. `t3` exits 1: logs and exits 0;
  8. `t3` hangs: the stub sleeps and ignores TERM, and the script ends within
     the kill deadline. The test uses a shortened timeout, also a `mkScript`
     parameter;
  9. `t3` missing from `binPath`: logs `not found` and exits 0.
- **Runtime on p620**, after `just p620`, with T3 Code open:
  1. Run `t3 theme set ember`, then switch again. `defaultTheme` is back to
     `omarchy`.
  2. Switch a second time with no changes. `defaultThemeSetAt` is unchanged.
  3. A theme switch updates `omarchy.json`.
  4. `journalctl -u home-manager-olafkfreund` shows only expected
     `t3code-theme:` lines.
- **Dry run.** With `defaultTheme` set to `ember`, run `nixos-rebuild
  dry-activate`. `settings.json` is unchanged.
- **Fresh-install path.** Covered by the eval check (DAG order after
  `nixarchySeed`) and by unit tests 1 and 4. A real reinstall is not done.
