# Spec: T3 Code follows the Omarchy theme declaratively

## Design

### One script, two triggers

A new module `hosts/common/nixos/omarchy-t3code-theme.nix` builds one script,
`t3code-omarchy-theme`, with `pkgs.writeShellScript`. Two triggers run the
same script, so the logic lives in one place:

1. **Home Manager activation**:
   - `home.activation.t3codeOmarchyTheme`, ordered
     `lib.hm.dag.entryAfter [ "writeBoundary" ]`;
   - called as `run ${script}`, so a dry run only prints the command
     (`omarchy-altscape.nix` uses the same pattern);
   - covers a host that is already logged in and is rebuilt.
2. **Omarchy post-boot hook**:
   - `xdg.configFile."omarchy/hooks/post-boot.d/t3code-theme"`, an executable
     that `exec`s the same script with `--session`;
   - covers a fresh install, where there is no current theme until the first
     login;
   - covers any activation that skipped;
   - `omarchy-enable-once.nix` and nixarchy's `default-plugins` hook use this
     same mechanism.

Each run is safe to repeat, and each trigger retries what an earlier one
skipped.

### Gating

The module is `lib.mkIf config.programs.nixarchy.apps.t3-code.enable`. That
NixOS option evaluates on p620 today. All three hosts import the module from
their `nixarchy.nix`, next to `omarchy-altscape.nix` or
`omarchy-stylix-theme.nix`. With the option off, the module adds nothing:

- no activation entry;
- no hook file;
- no `~/.t3` folder.

### The script

It runs as `olafkfreund`. Activation runs under
`home-manager-olafkfreund.service`; the hook runs in the user session. It uses
`set -u` but not `-e`, because each step decides on its own whether to skip.

Its `PATH` is set explicitly:

- `${lib.makeBinPath [ coreutils gnugrep jq ]}`;
- then `/run/current-system/sw/bin`, for `omarchy-theme-set-t3code`,
  `omarchy-theme-refresh` and `t3`. All three come from system packages:
  `t3` resolves to `t3code-0.1.8/bin/t3`, and the Omarchy scripts come from
  the omarchy tree.

The activation never relies on Home Manager's minimal `PATH`. Each step and
what it does:

1. **State directory.** `mkdir -p "$HOME/.t3/userdata"`. The option is on, so
   creating it is intended; it is created as the user.
2. **Palette source.** If `~/.local/state/omarchy/current/theme/t3code.json`
   is missing:
   - with `--session`, run `omarchy-theme-refresh` once. This mirrors
     installer step 2 and only makes sense inside a graphical session;
   - in activation, log `t3code-theme: no Omarchy palette yet (first login
     will retry)` to stderr and exit 0.
3. **Publish.** Run `omarchy-theme-set-t3code`, Omarchy's own script, unchanged.
   It skips placeholder palettes and writes `themes/omarchy.json` atomically.
4. **Select only after a successful publish.**
   - If `themes/omarchy.json` is still missing, log `palette not published`
     and exit 0.
   - Otherwise, if `jq -r '.defaultTheme // empty' settings.json` is not
     `omarchy`, run `t3 theme set omarchy`.
   - If that command fails, log its output on stderr and exit 0, so the next
     trigger retries.
   - When the theme is already `omarchy`, `t3` is not called at all. That keeps
     `defaultThemeSetAt` steady and avoids notifying running clients.

All logs go to stderr with the prefix `t3code-theme:`. In activation they land
in the `home-manager-olafkfreund` journal; in the hook they land in the
session journal. The script always exits 0, so it never fails a switch or a
login.

### Owner decisions carried over

- Force `omarchy` whenever it differs, at every activation and login.
- Open an upstream nixarchy issue. The module header links it and says the
  module can be deleted once upstream ships it.

## Alternatives rejected

- **Only `home.activation`.** It cannot work on a fresh install, because there
  is no palette before the first login (agy's finding).
- **Only the post-boot hook.** A running host would wait for the next login
  before a rebuild took effect.
- **Write `defaultTheme` into `settings.json` with jq.** That bypasses T3 Code's
  own CLI, which also notifies connected clients, and edits app-owned state
  directly.
- **`home.file` for `themes/omarchy.json`.** Omarchy's hook replaces the file
  atomically, and T3 Code watches it. A read-only store symlink would break
  both.
- **`system.activationScripts`.** It runs as root and would create root-owned
  files under `~/.t3`.
- **Upstream nixarchy only.** That is slower, and it is deferred to the
  follow-up issue.
- **`t3 theme set <path>`, publishing and setting in one step.** It would
  duplicate `omarchy-theme-set-t3code`'s placeholder check and atomic write.

## Risks

- **`t3` against a running server.** On p620 `t3 theme set` worked while the
  app was open. Whether that holds in a headless activation, with no session
  environment, is untested. Mitigations: the script calls `t3` only when the
  theme differs, logs failures, and the login hook retries.
- **The `t3` CLI starting slowly or hanging.** Wrap it in `timeout 30`, so
  activation cannot stall.
- **`omarchy-theme-refresh` at login.** It regenerates every theme output, but
  only runs when `t3code.json` is missing, which is rare. It never runs in
  activation.
- **The force decision.** A theme picked in the app is reverted at the next
  rebuild or login. That is accepted, by the owner's decision.
- **Hosts.** Only p620 has the option on. Razer and p510 only evaluate the
  module (`mkIf` false), and p510 is not deployed.

## Verification

- **Eval.** `nix eval` on all three hosts. On razer and p510, check that
  `home-manager.users.olafkfreund.home.activation` has no `t3codeOmarchyTheme`
  entry.
- **Build.** `nix build` p620's toplevel. Run `shellcheck` on the generated
  script.
- **Unit test, against a temporary `HOME`.** The script is run in a temporary
  home with a fake `PATH` that stubs `t3` and `omarchy-theme-set-t3code`, to
  cover:
  1. no palette, in activation mode: logs, exits 0, does not call `t3`;
  2. no palette, with `--session`: calls `omarchy-theme-refresh`;
  3. palette published, theme different: calls `t3 theme set omarchy`;
  4. theme already `omarchy`: does not call `t3`;
  5. `t3` fails: logs and exits 0.

  Where the repo's check layout allows, this is a `checks` derivation;
  otherwise a script under `tests/`.
- **Runtime on p620**, after `just p620`:
  1. set `defaultTheme` to `ember` with `t3 theme set ember`;
  2. switch again: `defaultTheme` is back to `omarchy`;
  3. a theme switch updates `omarchy.json`;
  4. the journal shows no `t3code-theme:` errors.
- **Fresh-install path.** A full reinstall is not tested. Instead:
  1. delete `~/.t3/userdata/themes/omarchy.json` and set
     `"defaultTheme": "ember"`;
  2. run the post-boot hook by hand;
  3. both are restored.
