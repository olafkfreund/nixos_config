# Spec: herdr-app argv launches get their own systemd scope

## Design

One guard in `home/development/herdr.nix`, added as `programs.bash.initExtra = lib.mkOrder 50 …` inside the
existing `programs.herdrSkill.enable` block. `initExtra` sits after Home Manager's `[[ $- == *i* ]] || return`, so it
only runs for interactive bash. Order 50 puts it ahead of every other contributor, including Home Manager's own
completion setup (order 100), bash-preexec (1000), starship (1900) and the tail (2000), so nothing initialises
twice.

```bash
if [ -n "${HC_TERMINAL_ID:-}" ] \
  && [ -S "${XDG_RUNTIME_DIR:-/run/user/$(id -u)}/bus" ] \
  && _hc_cg=$(<"${HC_ARGV_GUARD_CGROUP:-/proc/self/cgroup}") \
  && ! grep -qE '/herdr-pane-[0-9]+\.scope(/|$)' <<<"$_hc_cg" \
  && mapfile -d "" -t _hc_argv 2>/dev/null </proc/$$/cmdline && [ "${#_hc_argv[@]}" -gt 0 ]; then
  exec ${hcShell} "${_hc_argv[@]:1}"
fi
unset _hc_cg _hc_argv
```

Why each condition:

- `HC_TERMINAL_ID`: hc sets it for every app terminal; nothing else does.
- The bus socket: the same test `paneShell` uses. Without it `paneShell` would fall back to plain bash outside a
  scope, and the guard would fire again. With it, the re-exec always lands in a scope.
- The cgroup test is the loop guard and the "already handled" test: a shell in a `herdr-pane-*` scope, or in any
  cgroup below one (`…/herdr-pane-123.scope/child.scope`), is skipped. The cgroup file must be read successfully
  first: if it can't be read, the guard does nothing rather than re-exec without a way to recognise the result.
  `HC_ARGV_GUARD_CGROUP` exists only so the test can supply a fake file.
  That covers plain app shells (already `hcShell`), every Herdr TUI pane (`paneShell`), nested shells and the
  `exec $SHELL -i` that replaces an argv command when it ends (same PID, same scope). It does not depend on
  `HERDR_ENV`, which can leak into app terminals (#2989), and no marker variable is needed, which could leak into a
  core started from an app terminal and switch the guard off everywhere.
- `/proc/$$/cmdline` replays bash's own arguments exactly (NUL-separated), so `-ic "<argv>"` and any quotes,
  spaces, `$` or empty arguments reach the new bash unchanged. `argv[0]` is dropped because `paneShell` supplies the
  bash binary.

The chain `hcShell` → `paneShell` → `systemd-run --scope` → bash execs in place throughout, so the PID hc tracks
does not change, and the command is run once by the new bash (the old one never reaches its `-c` string). `hcShell`
also strips the inherited `HERDR_*`/Claude identities from argv launches.

`herdr-team` members (`hc run … -- bash launch`) are non-interactive and keep their own scope check. SSH commands
and scripts don't run `initExtra`'s guard (non-interactive).

The upstream request (owner's choice: both) is a GitHub issue on the herdr-app repository asking that argv launches
start through the configured `shell`, linked from #2987. Filing it publishes text outside this repo, so the issue
text is shown in the PR first and filed only after the owner merges or says so.

## Alternatives rejected

- `bashrcExtra`: runs for non-interactive `ssh host cmd` too, so it would need its own interactive check; `initExtra`
  already has one.
- A marker variable as the loop guard: inherited by any hc core started from an app terminal, after which every
  argv launch would skip the guard.
- `busctl` `StartTransientUnit` with the shell's PID: moves the shell without an exec but not the environment
  strip, and adds a second scope mechanism next to `paneShell`.
- Wrapping `SHELL` for the app (`SHELL=hcShell` in the app's environment): herdr-app also uses `$SHELL` for its own
  plain shells and other tools read it; a wrapper there leaks beyond the app.

## Risks

- `systemd-run` failing after the bus test passes: the exec'd wrapper exits and the terminal closes. Same exposure
  as every plain app shell today; visible immediately.
- A login argv launch (`argv[0]` starting with `-`) would lose login mode. herdr-app's argv launches use
  `$SHELL -ic`, not login shells; plain app shells never reach the guard.
- Startup cost: one extra exec chain for argv launches only (tens of ms).
- Hosts: p620 and razer; no system services change.

## Verification

- `home/development/herdr-argv-guard-test.sh` (new), run in the same build check as the existing herdr script
  tests (the plan names the derivation after reading `home/development/agent-run.nix`). It runs
  `bash --rcfile <guard> -ic …` with `HC_TERMINAL_ID` set, a fake bus socket and a fake cgroup file; the fake
  `hcShell` logs one line, points `HC_ARGV_GUARD_CGROUP` at a `herdr-pane-$$.scope` file and execs real bash with
  the same rcfile, as the real chain does. It checks:
  - the PID is unchanged, the wrapper ran once and the command ran once;
  - `-ic`, the command, `$0` and positional arguments with quotes, spaces, `$x` and an empty argument arrive intact;
  - a trailing `exec bash -i` after the command does not wrap again;
  - no re-exec for a pane scope, a child cgroup of one, no `HC_TERMINAL_ID`, no bus socket, or an unreadable cgroup
    file.
- The generated `.bashrc` (from the p620 build) has the guard right after the interactive check, before the
  completion block.
- Build p620 and razer (`just test-host`).
- On p620 after deploy: a + menu agent, `herdr-app do tab.new --argv`, a split launch (`ctrl+shift+y`) and the
  shell left after each command exits: `cat /proc/<pid>/cgroup` names its own `herdr-pane-<pid>.scope`; `HERDR_ENV`
  is unset in each; `systemctl --user stop` of one scope leaves the others running. Plain app shells and the TUI
  unchanged.
