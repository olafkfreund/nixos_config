# Spec: the checkout sync also runs after a switch that exits 4 but activated

## Design

All changes are in `scripts/sync-remote-checkout.sh`; no Justfile recipe changes, because every wrapped recipe
(`razer`, `p510`, `deploy-local-build`, the remote branch of `deploy-via-p620`) deploys `--flake .#HOST` from the
checkout the wrapper runs in. `quick-deploy`'s `around HOST -- true` exits 0 and is unaffected.

1. **`around`, after COMMAND:** today `result != 0` skips with `command failed; skipped`. New branch, checked before
   that one: when `result == 4`, the source was eligible (`reason` empty) and the source is still clean, the
   wrapper evaluates the system this deploy built:

   ```bash
   expected=$(nix eval --raw ".#nixosConfigurations.$host.config.system.build.toplevel" 2>/dev/null)
   ```

   - It runs in the deploying checkout, which is clean and on the recorded tree, so it evaluates exactly what was
     deployed. The build is already in the store, so this is evaluation only (the `_sign-drv` recipe already does
     the same evaluation for `drvPath`).
   - Eval failure or an empty result: `say 'exit 4; could not evaluate the deployed system; skipped'`.
   - Otherwise `say 'exit 4; syncing only if HOST runs the deployed system'` and `sync_checkout "$tree" "$expected"`.
   - Every other non-zero exit keeps `command failed; skipped`. The wrapper still exits with `result` (4).

2. **`sync_checkout TREE [EXPECTED]`:** passes `EXPECTED` (empty after exit 0) as a second argument to the existing
   single ssh call: `bash -s -- "$commit" "$expected"`. The `sync` subcommand is unchanged (it never passes one).

3. **Remote script:** after the ancestor check and immediately before `git merge --ff-only`, when `$2` is non-empty:

   ```bash
   running=$(readlink -f /run/current-system 2>/dev/null) || running=
   if [[ $running != "$2" ]]; then
     printf 'target is not running the deployed system; skipped\n'
     exit 0
   fi
   ```

   This is the latest point before the checkout moves, so a rollback or a deploy from another machine after ours is
   caught. A re-deploy of an already running generation (`old == running`) passes, which repairs drift on a retry.
   The `already current` exit stays where it is: nothing to sync there, whatever is running.

4. **Docs:** `docs/UPDATE-DEPLOY.md`, "Remote checkout sync": replace the exit-4 paragraph with the new rule (exit 4
   syncs only when the target runs exactly the system this deploy built; the deploy still reports 4) and keep the
   manual commands for the remaining skip cases.

## Alternatives rejected

- **Before/after comparison of `/run/current-system`:** cannot tell this deploy from a rollback or another
  machine's deploy, and needs an extra ssh call before the deploy (Codex review of the intent).
- **Compare with `/nix/var/nix/profiles/system`:** the profile is set before activation, so it proves the profile,
  not that the system is running.
- **Parse `nixos-rebuild` output for the store path:** depends on output format; evaluation is authoritative.
- **Evaluate before COMMAND on every deploy:** costs an evaluation on the common exit-0 path for nothing.
- **Sync on any non-zero exit with the same proof:** other codes (build failure, ssh failure, activation abort)
  mean the deploy did not finish as intended; the owner chose exit 4 only.

## Risks

- **Evaluation differs from the deployed build:** only if the source changed, which the clean-source check after
  COMMAND rules out, or if evaluation is impure; the flake is pure (`--impure` is not used). A mismatch only skips.
- **Evaluation time:** a few tens of seconds on p620, paid only on exit 4. On a host with a cold eval cache it can
  be longer; it is still bounded by the existing deploy duration.
- **`readlink` on the target fails:** the comparison fails and the sync skips with a reason.
- **Exit 4 does not reach the wrapper** (e.g. `nixos-rebuild` maps it to 1): then nothing syncs and the behaviour is
  unchanged; the p510 test checks this.

## Verification

- `scripts/test-sync-remote-checkout.sh` gains cases, with `nix` stubbed in the test's `bin/` to print a given path
  (or fail) and the fake ssh running the remote script locally, so `/run/current-system` is the test machine's:
  - exit 4, expected = `readlink -f /run/current-system` → fast-forwarded, exit 4;
  - exit 4, expected = another path → `target is not running the deployed system; skipped`, checkout unchanged,
    exit 4;
  - exit 4, `nix` fails → `could not evaluate`, no ssh, exit 4;
  - exit 4, dirty or ineligible source → existing reasons, no `nix` call, exit 4;
  - exit 1 → `command failed; skipped`, no `nix` call, exit 1;
  - exit 0 → unchanged behaviour (no second argument effect, no `nix` call).
- `just test-guards` passes; `shellcheck` and `shfmt` clean.
- **Live, p510** (owner-approved on 2026-11-17): check free space and running jobs on p510, read and post on
  `#agents:freundcloud.org.uk`, then from the merged `main` in `~/.config/nixos` with p510's checkout one or more
  commits behind: `P510_DEPLOY_APPROVED=1 AGENT_BUS_ANNOUNCED=1 just p510`, recording `$?`.
  - Exit chain: `nixos-rebuild` exit code (from the recipe output), the wrapper's, and `just`'s are all 4 (or all 0,
    in which case the exit-4 path is not exercised and is verified by the tests only; reported as such).
  - p510's `~/.config/nixos` HEAD equals the deployed commit, and `readlink -f /run/current-system` on p510 equals
    the evaluated path.
