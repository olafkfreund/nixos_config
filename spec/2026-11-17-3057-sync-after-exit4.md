# Spec: the checkout sync also runs after a switch that exits 4 but activated

## Design

All changes are in `scripts/sync-remote-checkout.sh`; no Justfile recipe changes, because every wrapped recipe
(`razer`, `p510`, `deploy-local-build`, the remote branch of `deploy-via-p620`) deploys `--flake .#HOST` from the
checkout the wrapper runs in. `quick-deploy`'s `around HOST -- true` exits 0 and is unaffected.

The invariant: syncing commit C is correct whenever the target runs exactly the system that C's tree evaluates
to, whoever activated it. So the proof is "the target's running system equals the evaluation of the recorded
tree", and the wrapper must evaluate that tree and nothing else.

1. **`around`, after COMMAND:** today `result != 0` skips with `command failed; skipped`. New branch, checked before
   that one, when `result == 4` and the source was eligible (`reason` empty):
   - Source identity, checked before and again after the evaluation: `git status --porcelain` succeeds with empty
     output and `git rev-parse 'HEAD^{tree}'` equals the recorded `tree`. Otherwise
     `say 'exit 4; source moved during the command; skipped'`. (A clean commit made during COMMAND moves HEAD
     without dirtying the tree; the existing exit-0 path does not need this because it syncs the recorded tree
     without evaluating anything.)
   - Evaluation, in the deploying checkout:

     ```bash
     expected=$(nix eval --raw ".#nixosConfigurations.$host.config.system.build.toplevel" 2>/dev/null)
     ```

     The flake is evaluated purely (no `--impure`), so with a clean checkout at the recorded tree the result is
     determined by that tree and its lock. The build is already in the store, so this is evaluation only
     (`_sign-drv` already evaluates the same attribute's `drvPath`).
   - Eval failure or empty output: `say 'exit 4; could not evaluate the deployed system; skipped'`.
   - Otherwise `sync_checkout "$tree" "$expected"`; its single result line is the only output, as today.
   - Every other non-zero exit keeps `command failed; skipped`. The wrapper still exits with `result` (4).
   - The same post-command checks are not added to the exit-0 path (out of scope; it is correct as is).

2. **`sync_checkout TREE [EXPECTED]`:** passes `EXPECTED` (empty after exit 0) as a second argument to the existing
   single ssh call: `bash -s -- "$commit" "$expected"`. The `sync` subcommand is unchanged (it never passes one).

3. **Remote script:** after the ancestor check and immediately before `git merge --ff-only`, when `$2` is non-empty:

   ```bash
   running=$(readlink -f /run/current-system 2>/dev/null) || running=
   if [[ $running != "$2" ]]; then
     printf 'target is not running the deployed system; skipped\n'
     exit 0
   fi
   ```

   This is the latest point before the checkout moves, so a rollback or a deploy from another machine before it is
   caught. An activation between this `readlink` and the merge (milliseconds) is not; that race stays and is
   documented. A re-deploy of an already running generation (`old == running`) passes, which repairs drift on a retry.
   The `already current` exit stays where it is: nothing to sync there, whatever is running.

4. **Docs:** `docs/UPDATE-DEPLOY.md`, "Remote checkout sync": replace the exit-4 paragraph with the new rule (exit 4
   syncs only when the target runs exactly the system this deploy built; the deploy still reports 4) and keep the
   manual commands for the remaining skip cases.

## Alternatives rejected

- **Before/after comparison of `/run/current-system`:** cannot tell this deploy from a rollback or another
  machine's deploy, and needs an extra ssh call before the deploy (Codex review of the intent).
- **Compare with `/nix/var/nix/profiles/system`:** the profile is set before activation, so it proves the profile,
  not that the system is running.
- **Parse `nixos-rebuild` output for the store path:** depends on output format; evaluation is authoritative.
- **Evaluate before COMMAND on every deploy:** costs an evaluation on the common exit-0 path for nothing.
- **Sync on any non-zero exit with the same proof:** other codes (build failure, ssh failure, activation abort)
  mean the deploy did not finish as intended; the owner chose exit 4 only.

## Risks

- **A deploy of an edit made and undone during COMMAND:** the target then runs the edited system, which differs from
  the recorded tree's evaluation, so the comparison fails and the sync skips. Safe by the invariant.
- **Residual race:** an activation between the remote `readlink` and the fast-forward is not caught. Closing it
  would need a lock shared with every activation path; not worth it for a checkout that the next deploy repairs.
- **Evaluation time:** tens of seconds on p620, paid only on exit 4.
- **`readlink` on the target fails or prints nothing:** not equal, skips with the reason.
- **Exit 4 does not reach the wrapper** (e.g. `nixos-rebuild` maps it to 1): nothing syncs, behaviour unchanged;
  the p510 test checks this.

## Verification

- `scripts/test-sync-remote-checkout.sh`: `nix` and `readlink` are stubbed in the test's `bin/` (the fake ssh runs
  the remote script locally with the same `PATH`), driven by environment variables, so nothing depends on the test
  machine's `/run/current-system`. Cases, each checking exit code, target HEAD and the single output line:
  - exit 4, running = expected → fast-forwarded, exit 4;
  - exit 4, running ≠ expected → `target is not running the deployed system; skipped`, exit 4;
  - exit 4, `readlink` fails → same skip, exit 4;
  - exit 4, running changes during the remote fetch (stubbed `git fetch` side effect) → skip, proving the check runs
    after the fetch;
  - exit 4, `nix` fails, and `nix` succeeds with empty output → `could not evaluate`, no ssh, exit 4;
  - exit 4, COMMAND commits cleanly (HEAD moves) → `source moved during the command`, no `nix`, exit 4;
  - exit 4, source status fails (stubbed) → `source moved`, exit 4;
  - exit 4, dirty or ineligible source before the command → existing reasons, no `nix`, exit 4;
  - exit 1 → `command failed; skipped`, no `nix`, exit 1; exit 0 → unchanged, no `nix`.
- `just test-guards` passes; `shellcheck` and `shfmt` clean.
- **Live, p510** (owner-approved on 2026-11-17): check free space and running jobs on p510, read and post on
  `#agents:freundcloud.org.uk`, then from the merged `main` in `~/.config/nixos`, with p510's checkout behind the
  deployed commit, run the p510 recipe with `P510_DEPLOY_APPROVED=1 AGENT_BUS_ANNOUNCED=1`, recording `$?`.
  - Exit chain, each observed: the activation's failure (`nixos-rebuild`'s "error(s) occurred while switching"
    output and the failed unit in `systemctl --failed` on p510), the wrapper's sync line (only the exit-4 path
    prints a fast-forward after a failed unit), and `just`'s `$?` = 4.
  - p510's `~/.config/nixos` HEAD equals the deployed commit, and `readlink -f /run/current-system` on p510 equals
    the evaluated path.
  - If the deploy exits 0, the live exit-4 requirement is reported as **not verified**, not as passed.
