# Spec: p620 k3d factory cluster on Kubernetes 1.35

## Design

### Code (`modules/containers/k3d.nix`)

- `k3sImage` default (line ~654): `rancher/k3s:v1.31.5-k3s1` → `rancher/k3s:v1.35.10-k3s1`. p620 is the only host
  that enables the module, so the default is the one place to change (intent answer 4).
- `--datastore-endpoint` in the create call (line ~322) becomes the v1.35.10 default DSN plus `_auto_vacuum=full`
  (#2676): `sqlite:///var/lib/rancher/k3s/server/db/state.db?_journal_mode=WAL&_busy_timeout=30000&_synchronous=NORMAL&_txlock=immediate&_stmt_cache_size=20&cache=shared&_auto_vacuum=full`.
  The comment above it names v1.35.10 instead of v1.31.5. The DSN only matters at create; the existing cluster is
  deleted anyway.
- Nothing else in the module changes: privileged nodes (k3d's default; both nodes see `/dev/kvm` today), the
  storage volume, resolver mounts, PV snapshot/restore and the Secret seed stay as they are.

### Docs (`docs/applications/k3d-cluster.md`)

A short "Upgrading k3s" section: k3d does not upgrade in place, so an image change is the recreate runbook below;
the DSN must be reread from the new binary; the bootstrap must be started by hand after the switch. It also warns
that "Full reset" deletes the PV data and is not the upgrade path.

### Recreate runbook (lead, live on p620; owner chose "now")

Before (cluster still up):

1. `just test-host p620` with the meetingai / meeting-mode overrides; the rendered bootstrap script has the new
   image and DSN; bus `read_new` + `post`.
2. Backups: `systemctl start keycloak-realm-backup.service skillai-db-backup.service
   factory-cli-creds-snapshot.service`, all succeed (the last keeps the cluster-rotated Claude credential, which
   the seed prefers over agenix when newer; `k3d.nix:538-551`).
3. Fresh PV snapshot: `systemctl restart k3d-cluster-bootstrap` on the live cluster (the reboot path: no create,
   it ends with `k3d-pv-state snapshot`, `k3d.nix:431`); the snapshot lists the 16 live PVs; dated copy
   `pv-snapshot.pre-recreate-20261118.json`.
4. Every `local.path` in the snapshot has its directory under `/mnt/code/k3d/storage` (checked 2026-11-18: all 15;
   the 16th is the NFS PV). The restore skips a missing directory and carries on (`k3d.nix:165-178`), so this
   check happens before the delete, not after.
5. Baseline: ArgoCD app health counts, the PV → PVC bindings.

Recreate:

1. `systemctl stop k3d-cluster-bootstrap`, then `k3d cluster delete factory`. The storage directory stays.
2. Announced `nixos-rebuild switch` for p620 on the merged main. A stopped oneshot is not started by a switch, and
   the unit has no `wantedBy` (only a boot timer), so:
3. `systemctl start k3d-cluster-bootstrap`. It sees no cluster, marks the restore pending, creates the cluster on
   v1.35.10, restores the 16 PVs pre-bound before any PVC exists, seeds the Secrets (the 21 factory ones and
   both fides ones from agenix) and applies the ArgoCD bootstrap.

After: Verification below.

`factory-gitops` already pins `clusterIP: 10.43.224.175` on the `nfs-provisioner` Service
(`apps/nfs-provisioner/manifests/manifests.yaml:89`, comment citing #1497), so the restored NFS PV for
`tfactory-data-rwx` keeps a working server. No change in that repo (intent answer 3 is already done).

## Alternatives rejected

- **k3s 1.36 or 1.37:** only KubeVirt 1.9 supports 1.36 and none 1.37; 1.35 keeps both 1.8 and 1.9 open.
- **1.34:** supported by KubeVirt 1.7 to 1.9 but the oldest maintained Kubernetes; we would be back here soonest.
- **In-place `k3s` binary swap inside the node containers:** not a k3d-supported path; the next bootstrap or
  recreate would go back to the pinned image.
- **Step through 1.32 → 1.33 → 1.34 → 1.35:** needed only to keep a datastore across minors. A recreate starts a
  fresh datastore and every object comes back from Git, the snapshot or the seed.
- **Upgrade ArgoCD first:** intent answer 2: keep 2.13.1 and check it.

## Risks

- **ArgoCD 2.13.1 on 1.35** (untested upstream). Checked after the recreate: all apps sync. If it fails, the
  rollback below restores 1.31.
- **Restore skips a PV:** prevented by the directory check before the delete; the restore log must still say
  `skipped 0`, and a skip is recovered by hand from its kept directory (scale the app to 0, apply its PV from the
  dated snapshot) before the app writes a fresh volume.
- **Image pulls:** every image is pulled again on a fresh cluster. The k3s image is already pulled. A private
  image needs `ghcr-pull`, which is seeded.
- **Tailscale sidecars:** each re-registers; a stale node with the same name can make the new one take a `-1`
  suffix. Checked after; old nodes removed in the admin console if so.
- **Downtime:** every Factory service, roughly 15 to 30 minutes, announced on the bus.
- **Datastore DSN typo** breaks the create: the plan checks the rendered script before the delete.

## Rollback

1. `systemctl stop k3d-cluster-bootstrap`; `k3d cluster delete factory` (storage stays).
2. Copy `pv-snapshot.pre-recreate-20261118.json` over `pv-snapshot.json`: a non-restore run on the new cluster
   may have replaced the canonical file.
3. Revert the commit on main, announced switch, `systemctl start k3d-cluster-bootstrap`: it recreates on v1.31.5
   through the same restore path.
4. Verify as below with v1.31.5. Data written by apps on 1.35 stays in the same directories; nothing in the
   apps depends on the Kubernetes version.

## Verification

- Before the delete: `just test-host p620` builds; the rendered bootstrap script contains the new image and DSN
  (`bash -n` clean); `just test-guards` unaffected.
- After: both nodes `Ready` at `v1.35.10+k3s1`, privileged, `/dev/kvm` present; restore log `skipped 0`; the 16 PVs
  Bound to the same PVCs; 43 ArgoCD apps Synced/Healthy (as before); the bootstrap log shows the factory and fides
  Secrets applied with no WARN and `factory-cli-creds` seeded unexpired; the datastore line reports
  `auto_vacuum=full` (the bootstrap logs it, `k3d.nix:264-266`); pod DNS resolves (the bootstrap smoke check);
  `tfactory-data-rwx` mounted and readable in a TFactory pod; keycloak realm `factory` present; a Factory UI loads
  through its tailnet name; `systemctl --failed` empty; the bootstrap unit succeeded.
