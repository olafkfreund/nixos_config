# Spec: p620 k3d factory cluster on Kubernetes 1.35

## Design

### Code (`modules/containers/k3d.nix`)

- `k3sImage` default (line ~654): `rancher/k3s:v1.31.5-k3s1` → `rancher/k3s:v1.35.10-k3s1`. p620 is the only host
  that enables the module, so the default is the one place to change (intent answer 4).
- `--datastore-endpoint` in the create call (line ~322) becomes the v1.35.10 default DSN plus `_auto_vacuum=full`
  (#2676): `sqlite:///var/lib/rancher/k3s/server/db/state.db?_journal_mode=WAL&_busy_timeout=30000&_synchronous=NORMAL&_txlock=immediate&_stmt_cache_size=20&cache=shared&_auto_vacuum=full`.
  The comment above it names v1.35.10 instead of v1.31.5. The DSN only matters at create; the existing cluster is
  deleted anyway.
- Nothing else in the module changes: privileged nodes (k3d's default; both nodes see `/dev/kvm` today), the
  storage volume, resolver mounts, PV snapshot/restore and the Secret seed stay as they are.

### Docs (`docs/applications/k3d-cluster.md`)

A short "Upgrading k3s" section: k3d does not upgrade in place, so an image change is the recreate runbook below;
the DSN must be reread from the new binary. It also warns that "Full reset" deletes the PV data and is not the
upgrade path.

### Recreate runbook (lead, live on p620; owner chose "now")

Before (cluster still up):

1. `just test-host p620` with the meetingai / meeting-mode overrides; bus `read_new` + `post`.
2. Backups: `systemctl start keycloak-realm-backup.service skillai-db-backup.service`, both succeed.
3. Fresh snapshot: `k3d-pv-state snapshot` to `/var/lib/k3d-factory/pv-snapshot.json`, then a dated copy
   `pv-snapshot.pre-recreate-20261118.json`; it must list 16 PVs.
4. Export `fides/fides-secrets` and `fides-reporter/fides-reporter-token` with `kubectl get secret -o json`,
   stripped of uid / resourceVersion / creationTimestamp, to a root-only (0600) file under
   `/var/lib/k3d-factory/`. Values are never printed.
5. Record the baseline: app health counts, the PV → PVC bindings.

Recreate:

1. `systemctl stop k3d-cluster-bootstrap`, then `k3d cluster delete factory`. The storage directory stays.
2. Announced `nixos-rebuild switch` for p620 on the merged main. The switch restarts the bootstrap unit (its
   script changed), which sees no cluster, marks the restore pending, creates the cluster on v1.35.10, restores
   the 16 PVs pre-bound, seeds the Secrets and applies the ArgoCD bootstrap.

After:

1. Apply the exported fides Secrets; restart the pods that read them.
2. Verify (see Verification).

`factory-gitops` already pins `clusterIP: 10.43.224.175` on the `nfs-provisioner` Service
(`apps/nfs-provisioner/manifests/manifests.yaml:89`, comment citing #1497), so the restored NFS PV for
`tfactory-data-rwx` keeps a working server. No change in that repo (intent answer 3 is already done).

## Alternatives rejected

- **k3s 1.36 or 1.37:** only KubeVirt 1.9 supports 1.36 and none 1.37; 1.35 keeps both 1.8 and 1.9 open.
- **1.34:** supported by KubeVirt 1.7 to 1.9 but the oldest maintained Kubernetes; we would be back here soonest.
- **In-place `k3s` binary swap inside the node containers:** not a k3d-supported path; the next bootstrap or
  recreate would go back to the pinned image.
- **Step through 1.32 → 1.33 → 1.34 → 1.35:** needed only to keep a datastore across minors. A recreate starts a
  fresh datastore and every object comes back from Git, the snapshot or the seed.
- **Upgrade ArgoCD first:** intent answer 2: keep 2.13.1 and check it.

## Risks

- **ArgoCD 2.13.1 on 1.35** (untested upstream). Checked after the recreate: all apps sync. If it fails, the
  rollback below restores 1.31.
- **Restore skips a PV:** the restore log must say `skipped 0`; a skip stops the runbook before step 8 to recover
  that PV by hand from its kept directory.
- **Image pulls:** every image is pulled again on a fresh cluster. The k3s image is already pulled. A private
  image needs `ghcr-pull`, which is seeded.
- **Tailscale sidecars:** each re-registers; a stale node with the same name can make the new one take a `-1`
  suffix. Checked after; old nodes removed in the admin console if so.
- **Downtime:** every Factory service, roughly 15 to 30 minutes, announced on the bus.
- **Datastore DSN typo** breaks the create: the plan checks the rendered script before the delete.

## Rollback

Delete the cluster again, revert the commit, switch: the bootstrap recreates on v1.31.5 through the same restore
path (the dated snapshot is kept). The PV data is untouched in both directions.

## Verification

- Before the delete: `just test-host p620` builds; the rendered bootstrap script contains the new image and DSN
  (`bash -n` clean); `just test-guards` unaffected.
- After: both nodes `Ready` at `v1.35.10+k3s1`, privileged, `/dev/kvm` present; restore log `skipped 0`; the 16 PVs
  Bound to the same PVCs; 43 ArgoCD apps Synced/Healthy (as before); `tfactory-data-rwx` mounted in a TFactory
  pod; keycloak realm `factory` present; `systemctl --failed` empty; the bootstrap unit succeeded.
