# Spec: login cover lifts through the normal path on p620

Paths are relative to the Omarchy tree `share/omarchy/shell/` (Omarchy
48138d9, which nixarchy edge ships). Upstream `basecamp/omarchy` branch
`quattro` has changed none of these three files in the 73 commits since
48138d9 (checked 2026-11-23 with the GitHub compare API).

## Design

### 1. The reaper's rescan becomes a check that holds nothing when unchanged

Today `PluginRegistry`'s startup chain is: `ensureUserDir()` →
`initProcess.onExited` → `reapOrphanedPluginWatchers()` →
`watcherReaper.onExited`, which starts `localPluginWatcher` and calls
`registry.rescan()` (`services/PluginRegistry.qml:690-706`, `:789-792`,
`:810`). `shell.qml:194` already scanned, so this second scan normally finds
the same 88 manifests. Its cost on 2026-11-23:

- **`scanning` held `desktopReady` false for 4.0 s** (+5.1 to +9.1 s). The
  `find` itself is short, but its exit was handled only after the 15
  `keepLoaded` panels finished loading on the main loop.
- **Then it replaced `installedPlugins` and ran every post-scan sync.**
  `pluginsChanged()` and `scanFinished()` both sync (`shell.qml:1114-1117`,
  `:1432`, `:1491`, `:1636-1638`), followed by a 2.4 s block.

The check stays, because it covers a plugin whose manifest appears or changes
between the first scan and the moment the watcher starts. It changes like this:

- `rescan(onlyIfChanged)` gains an optional argument. The reaper calls
  `registry.rescan(true)`. Every other caller is unchanged.
- **An `onlyIfChanged` scan runs as a check:**
  - it sets a separate `checking` flag, not `scanning`;
  - `rescan()` treats `checking` like `scanning` for its own "already
    running" guard, so two scans never overlap;
  - `desktopReady` (`BackgroundIntro.qml:23`) reads `scanning` only, so the
    check does not hold it;
  - the shell's three scan guards, `rescanPlugins()` (`shell.qml:1588`),
    `reloadPlugins()` (`:1596`) and `finishPluginReload()` (`:1609`), test
    `scanning || checking`. A reload or rescan that arrives during a check is
    therefore marked pending, the same as during a scan today.
    `finishPluginReload` must be included: otherwise its `rescan()` would be
    dropped by the `checking` guard and the reload would never finish.
- **When the check's output equals the last full scan's output** (byte for
  byte, and only once a full scan has completed with exit code 0, tracked by
  `hasScanOutput`), the registry:
  - clears `checking`;
  - emits `scanFinished()` and does not emit `pluginsChanged()`;
  - leaves `installedPlugins` and `registryRevision` untouched;
  - sets `lastScanSkipped = true`.
- **When the output differs, or no full scan has completed yet,** it sets
  `scanning = true` just for the synchronous parse, then parses and publishes
  exactly as today. `lastScanSkipped` is false, and the output is stored.
- **`shell.qml`'s `onScanFinished` (`:1627-1642`)** keeps its reload and
  pending-rescan branches as they are. Its plain branch runs
  `_syncServices`, `syncPanelEntries` and `syncPluginWidgets` unless
  `lastScanSkipped && !shell.pluginReloading`. The `pluginReloading` test
  covers a reload that started while a check was running, so its unloaded
  components are always synced back.
- **Other `pluginsChanged()` listeners do not run for a skipped check:**
  `shell.qml:1114`, `:1432`, `:1491` and `BackgroundIntro.qml:85`
  (`finishStartup`). Nothing changed for them, and `finishStartup` also runs
  from `onBackgroundReadyChanged` and the intro process's exit.
- **The guard is a flag, not `registryRevision`**, because enable and disable
  also move the revision (`PluginRegistry.qml:333`, `:401`, `:597`).

What the comparison covers: everything `parseScanOutput` reads. The scan
script sorts first-party manifest paths (`find … | sort`), bash expands the
third-party glob in sorted order, and each manifest is printed verbatim
(`PluginRegistry.qml:759-781`). `validateManifest` and capability stamping
depend only on that text and the constant `Util.barSections`. A QML-only edit
is not a manifest change. No scan picks it up today either; the watcher's
reload does that.

Existing gaps that this change leaves as they are:

- if the reaper exits while the first scan is still running, `rescan()` drops
  the check, as today;
- the watcher starts without waiting for its recursive watches to be set up,
  as today.

**Decision for the owner (differs from the intent's wording).** The intent
says not to "simply stop the scan from clearing `desktopReady`". Here a check
does not clear it, but only a check that changes nothing ends without
publishing. A check that finds a change publishes under `scanning` exactly as
today. The cause (a second full publish and sync of unchanged state) is
removed, not hidden. The alternative is to keep `scanning` for the check.
That leaves the 4.0 s hold, so the reveal would still depend on the panels'
load time. Recommended: the check design above.

### 2. Measurement (temporary, p620 only)

The #3165 timing patch is applied again for p620 through
`programs.nixarchy.package` (the same `overrideAttrs` + `patch --forward
--fuzz=0` in `postInstall`, `OMARCHY_STARTUP_TIMING=1`). It goes on top of
the fix patch and adds these lines:

- **Who scanned:**
  - `reaper-exit`;
  - `scan-start <caller>`, where caller is `shell`, `reaper`, `rescanPlugins`
    or `reload`;
  - `ipc-rescan` from the IPC `rescanPlugins` (`shell.qml:1908`) before it
    delegates;
  - `check-skip unchanged` or `check-changed`.
- **Handler cost:** `handler <name> <ms>` around `onPluginsChanged` (each of
  the three listeners), `onScanFinished`, `syncPluginApis`, `_syncServices`,
  `syncPanelEntries` and `syncPluginWidgets`, using `Date.now()` before and
  after.
- **Reveal inputs:**
  - `background-ready` with the reason `finishStartup` returns early
    (`BackgroundIntro.qml:51-61`);
  - `fade-end` when `startupPending` clears, so the reveal is measured to its
    end.

This takes one owner login with the fix, plus one in-session baseline. After
the login, an IPC `rescanPlugins` call runs a full, unchanged scan, with all
the syncs the reaper's scan used to run. It is the same sync path, measured
per handler without a second login:

```bash
omarchy-shell plugins rescanPlugins
```

The exact IPC target name is read from `shell.qml:1907` when the patch is
written. Then the timing patch is reverted the same way as PR 3180.

### 3. Where the fix lives

- **Phase 1 (proof):** the fix patch is applied for p620 only, in this repo,
  in the same way: `hosts/p620/nixos/omarchy-3181-reaper-check.patch`,
  applied before the timing patch. Both apply in `postInstall` of the host
  override. That is after nixarchy's own patches and substitutions, so they
  are made against the built tree (`share/omarchy` of the current pin), not
  the raw upstream tree.
- **Phase 2 (keep):** the gate is a login log that shows
  `check-skip unchanged`, no sync after it, and no plugin, panel or widget
  missing. Phase 2 does not need `fade-start normal`: the change removes a
  real 4 s hold and a 2.4 s block either way. If the timer still wins, the
  intent's outcome stays open and the follow-up issue is opened.

  The fix then moves to nixarchy as a carried patch under a new nixarchy
  issue N:
  - the file is `pkgs/omarchy/N-reaper-check.patch`;
  - it is applied in `pkgs/omarchy/default.nix` with `# CARRIED (#N)` and
    `--forward --fuzz=0`, the same as `1192-panel-loader-errorstring.patch`;
  - its header says what it fixes, which nixos_config issue it came from,
    and when to drop it.

  This repo then drops its copy and bumps the nixarchy pin, so razer and p510
  get it. p510 is built and deployed only with the owner's OK.
- **Upstream (decision for the owner):** the intent said the fix goes to
  upstream Omarchy and nixarchy carries it until upstream releases it.
  nixarchy's own convention is "the owner carries fixes here" (header of
  `1192-panel-loader-errorstring.patch`). Recommended: carry it in nixarchy
  and leave an upstream PR to `basecamp/omarchy` as the owner's separate
  call.

## Alternatives rejected

- **Keep `scanning` for the reaper's check.** It is simpler, but the check's
  exit waits behind the `keepLoaded` panel loads (4.0 s on 2026-11-23), and
  `desktopReady` is held all that time.
- **Drop the startup scan in `shell.qml:194` and keep only the reaper's.**
  The first scan would then wait for `mkdir`, a `pgrep` over every process,
  and a `/proc` read per orphaned watcher (63 on one machine, per the code
  comment). That cost is unmeasured, and every login would pay it before the
  bars get widgets.
- **Skip the reaper's rescan when a scan has already run.** It is smaller,
  but a plugin added before the watcher starts would be missed until its
  next change.
- **Make every unchanged scan skip its syncs.** IPC `rescanPlugins` callers
  may rely on the syncs re-reading shell config when no manifest changed.
  That is unchecked, so it is out of scope.
- **Shorten the safety timer, or stop real scans from clearing
  `desktopReady`.** The intent rules both out.
- **Defer `keepLoaded` panels, or compile services asynchronously.** These are
  separate costs. They go in the follow-up issue if the login shows them as
  the last input.

## Risks

- **Two scans overlapping:** `checking` joins `rescan()`'s guard, so they
  cannot overlap.
- **A reload during a check:** reload and rescan requests go pending while
  a check runs. `onScanFinished` drains them on a skip, and a reload that
  started anyway is still synced because of the `!pluginReloading` test.
  Codex and agy disagreed on whether that window can be reached at all
  (`finishPluginReload` is a `Qt.callLater`). The test costs one condition, so
  it stays.
- **A missed manifest change between the first scan and the check:** the
  byte comparison catches it, so the check publishes it. This holds only
  after a successful full scan (`hasScanOutput`).
- **Patch drift:** `--fuzz=0` makes an upstream change to these lines fail
  the build instead of misapplying. The carried patch needs a refresh when
  nixarchy bumps edge.
- **Hosts:**
  - Phase 1 touches p620 only.
  - Phase 2 changes the shell on razer and p510 as well. Their logins are not
    measured, and a bug there would show as a missing plugin or bar widget.
- **The reveal may still miss** if:
  - the wallpaper (+7.8 s) is the last input;
  - the panels' 2.0 s stall is;
  - the later stalls with no scan running (1.9 s at +14.3 s, 0.45 s at
    +14.7 s) start earlier.

  The log shows which. The follow-up issue covers it.

## Verification

- **Build:**
  - both patches apply with `--forward --fuzz=0` to the current pin's built
    `share/omarchy`;
  - `just test-host p620` builds;
  - the built tree has `rescan(true)` in the reaper, the `checking` flag in
    `rescan()` and all three shell guards, and the
    `lastScanSkipped && !shell.pluginReloading` test in `onScanFinished`;
  - for razer, `nix-diff` against `origin/main` shows nothing related to
    Omarchy in Phase 1.
- **Offline:** the full shell cannot load offscreen (no PanelWindow
  backend), as in #3165. The patched QML is checked with the same offscreen
  harness, for the same error classes as the untouched tree.
- **Login (p620, owner):**
  - `scan-start reaper` is followed by `check-skip unchanged`;
  - no `handler` sync line follows it;
  - `desktop-ready` stays true across the check;
  - `fade-start normal` and `fade-end` appear, with no `fade-start timeout`;
  - the reveal is reported against `media-ready` and `background-ready`;
  - 54 `widget-registered` lines and the 15 startup `panel-loaded` lines are
    present, as in #3165 (herdr loads later, when it becomes active).
- **Baseline:** the in-session IPC `rescanPlugins` gives `handler` costs for
  a full unchanged scan. They are reported next to the login's numbers.
- **Behaviour, in the same session:**
  - **add:** create `~/.config/omarchy/plugins/zz-3181-test/` with a minimal
    valid `manifest.json`. It is listed by the registry, then removed and
    unlisted.
  - **manifest change:** edit that manifest's `name`, and the registry shows
    the new name.
  - **code change:** edit a visible string in an existing local plugin's QML.
    `reloading true`, then `reloading false`, and the new string shows. The
    edit is reverted after.
  - **queued IPC:** call IPC `rescanPlugins` right after login. With the
    timing lines, it is either run or recorded as pending, never lost.
- **Phase 2:**
  - nixarchy's `tests/patched-files.nix` and its build pass with the carried
    patch;
  - after the pin bump, `just test-host` passes for p620 and razer;
  - p510 is built only with the owner's OK.
