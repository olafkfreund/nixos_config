# Spec: login cover lifts through the normal path on p620

Paths are relative to the Omarchy tree `share/omarchy/shell/` (Omarchy
48138d9, which nixarchy edge ships). Upstream `basecamp/omarchy` branch
`quattro` has changed none of these three files in the 73 commits since
48138d9 (checked 2026-11-23).

## Design

### 1. The reaper's rescan runs only when the plugin tree changed

Today `PluginRegistry`'s startup chain is: `ensureUserDir()` →
`initProcess.onExited` → `reapOrphanedPluginWatchers()` →
`watcherReaper.onExited`, which starts `localPluginWatcher` and calls
`registry.rescan()` (`services/PluginRegistry.qml:690-706`, `:789-792`,
`:810`). `shell.qml:194` already scanned, so this second scan normally finds
the same 88 manifests. It still replaces `installedPlugins`, and then runs
every post-scan sync.

The rescan stays, because it covers a plugin added between the first scan
and the moment the watcher starts. It becomes conditional:

- `PluginRegistry` keeps the raw output of the last scan it parsed
  (`property string lastScanOutput`).
- `rescan()` takes an optional `onlyIfChanged` argument and stores it for the
  running scan. The reaper calls `registry.rescan(true)`. Every other caller
  is unchanged.
- In `scanProcess.onExited`, when the running scan is `onlyIfChanged` and its
  output is byte-identical to `lastScanOutput`, the registry:
  - sets `scanning = false`;
  - emits `scanFinished()` but not `pluginsChanged()`;
  - leaves `installedPlugins` and `registryRevision` untouched.

  Otherwise it parses as today and stores the output.
- That skipped scan also sets `lastScanSkipped = true`. A full parse sets it
  to `false`.
- `shell.qml`'s `onScanFinished` (`:1627-1642`) keeps its reload and
  pending-rescan branches exactly as they are. Its plain branch skips
  `_syncServices`, `syncPanelEntries` and `syncPluginWidgets` when
  `lastScanSkipped` is true. A full reload never takes the skip path, because
  its scan is not `onlyIfChanged`.
- With no `pluginsChanged()`, the other listeners do not run for a skipped
  scan: `shell.qml:1114`, `:1432`, `:1491` and `BackgroundIntro.qml:85`
  (`finishStartup`). Nothing changed for them to act on, and
  `finishStartup` still runs from `onBackgroundReadyChanged`.
  `registryRevision` is not used as the guard, because enable and disable
  also move it (`PluginRegistry.qml:333`, `:401`, `:597`).

Raw output is a safe test of "nothing changed". The scan script sorts
first-party paths (`find … | sort`), bash expands the third-party glob in
sorted order, and every manifest is printed verbatim
(`PluginRegistry.qml:759-781`). A change to any manifest, or an added or
removed plugin, changes the output. Enable and disable live in the shell
config, not in manifests. They do not go through the reaper's call, so they
are not affected.

Because `scanning` still flips, `desktopReady` drops for the duration of the
`find`. Unlike today, it is no longer held by the 2.4 s block. With the loop
free this is about 0.2 s, the length of the first scan.

### 2. Measurement login (temporary, p620 only)

The #3165 timing patch is applied again for p620 through
`programs.nixarchy.package` (the same `overrideAttrs` + `patch --forward
--fuzz=0` in `postInstall`, `OMARCHY_STARTUP_TIMING=1`). It goes on top of
the fix patch and adds these lines:

- `reaper-exit` and `scan-start <caller>`, where caller is one of `shell`,
  `reaper`, `rescanPlugins`, `reload` or `ipc`, so a second scan names itself.
  `scan-skip unchanged` when the reaper's scan changes nothing.
- `handler <name> <ms>` around `onPluginsChanged`, `onScanFinished`,
  `syncPluginApis`, `_syncServices`, `syncPanelEntries` and
  `syncPluginWidgets`, using `Date.now()` before and after. This splits the
  post-scan block per handler.
- `background-ready` with the reason that `finishStartup` returns early
  (`BackgroundIntro.qml:47-61`), so the wallpaper's +7.8 s can be compared
  against the reveal.

One owner login gives the result. Then the timing patch is reverted, as in
# 3180.

### 3. Where the fix lives

- **Phase 1 (proof):** the fix patch is applied for p620 only, in this repo,
  the same way as the timing patch. It is a file
  `hosts/p620/nixos/omarchy-3181-reaper-rescan.patch` that applies before the
  timing patch. This needs no nixarchy release to test.
- **Phase 2 (keep):** once the login shows `fade-start normal`, the fix moves
  to nixarchy as a carried patch: `pkgs/omarchy/3181-reaper-rescan.patch`,
  applied in `pkgs/omarchy/default.nix` with a `# CARRIED (#3181)` line and
  `--forward --fuzz=0`, the same as `1192-panel-loader-errorstring.patch`.
  The patch header says what it fixes and when to drop it. This repo then
  drops its copy and bumps the nixarchy pin, so razer and p510 get it. p510
  is deployed only with the owner's OK.
- **Upstream:** nixarchy's convention is "the owner carries fixes here". An
  upstream PR to `basecamp/omarchy` is optional and is the owner's call. It
  is not part of this task.

## Alternatives rejected

- **Drop the startup scan in `shell.qml:194` and keep only the reaper's.**
  The first scan would then wait for `mkdir` plus a `pgrep` over every
  process, plus a `/proc` read per orphaned watcher (63 of them on one
  machine, per the code comment). Its length is not measured, and every
  login would pay it before the bars get widgets.
- **Skip the reaper's rescan when a scan has already run.** This is smaller,
  but a plugin added in the seconds before the watcher starts would then be
  missed until its next change. The constraints keep in-session adds working.
- **Make every unchanged scan skip its syncs**, not just the reaper's. IPC
  `rescanPlugins` callers, such as `omarchy plugin` commands, may depend on
  the syncs re-reading shell config even when no manifest changed. That is
  not checked, so this is out of scope.
- **Shorten the safety timer, or stop scans from clearing `desktopReady`.**
  The intent's constraints rule this out: it hides the cause.
- **Defer `keepLoaded` panels or compile services asynchronously.** These are
  allowed by the intent, but are separate costs. They go in the follow-up
  issue if the measurement login shows them as the last input.

## Risks

- **A missed plugin change:** the gap between the first scan and the reaper's
  exit is covered by the byte comparison, so a plugin added or edited in it
  still causes a full parse. Risk: low.
- **A lost reload request:** `onScanFinished` still runs its reload and
  pending-rescan branches on a skipped scan, so a reload or rescan requested
  meanwhile still happens. Only the three syncs are guarded.
- **Patch drift:** `--fuzz=0` makes an upstream change to these lines fail
  the build rather than misapply. On nixarchy edge bumps the carried patch
  needs a refresh.
- **Hosts:**
  - Phase 1 touches p620 only.
  - Phase 2 changes the shell on razer and p510 too. Their logins are not
    measured, and a bug there would show as a missing plugin or bar widget.
- **The reveal may still miss.** If the wallpaper (+7.8 s) or the
  `keepLoaded` panels' 2.0 s stall is the last input, the cover may still
  lift by the timer. The measurement login shows this. In that case Phase 2
  still lands, because it removes a real 4 s scan and its block, and the
  follow-up issue is opened.
