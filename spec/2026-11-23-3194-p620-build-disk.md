# Spec: a dedicated NVMe for builds and the GitHub runners on p620

## Decisions on the intent's open questions

The owner approved the intent and took the suggested answers:

1. **Missing disk:** the nix daemon falls back to `/`, so p620 can still rebuild itself. The four GitHub runners
   require the mount and do not start without it.
2. **VM workspace:** moves to the new disk.
3. **Naming:** a general build mount, `/mnt/build`, labelled `build`.
4. **Old `scratch` SSD:** left unmounted, for a later task.
5. **Runners:** four, unchanged.

## Design

### Disk layout

- **Partition table:** GPT on `/dev/disk/by-id/nvme-Lexar_SSD_EQ790_1TB_QJC054R004014P221Q`, with one partition
  over the whole disk, named `build` (GPT partition label).
- **Filesystem:** ext4 with label `build`, `-m 0` (no root-reserved blocks; nothing on it needs them), and
  default inode density. This matches the other p620 data disks, the tools the repo already uses, and the
  existing recovery habits.
- **Mount:** `/mnt/build` by `/dev/disk/by-label/build`, as `/mnt/code` is mounted, with
  `noatime nofail x-systemd.device-timeout=10s`. TRIM stays periodic: `common-pc-ssd` already enables
  `fstrim.timer`, and the disk reports discard support. No `discard` mount option, which would add latency to every
  delete during build churn.
- **Directories,** made by tmpfiles after the mount:
  - `/mnt/build/nix`, `0755 root root`: the nix build-dir;
  - `/mnt/build/vmtest`, `0755 olafkfreund users`: the agents' VM workspace, matching today's
    `/mnt/data/vmtest` ownership, which the plan reads and copies exactly.

### The build-dir

`services.nixarchy-runner.buildDir = "/mnt/build/nix"` in `hosts/p620/configuration.nix`. The module already sets
`nix.settings.build-dir`, the daemon's `TMPDIR`, and a tmpfiles rule from it.

**Fallback:** when the disk is missing, the `nofail` mount is skipped and tmpfiles creates `/mnt/build/nix` on `/`.
Builds then run on the root NVMe, as they did before #2182. The runners cannot add 16 GB VM jobs to that, because
they don't start (below).

### Runners require the disk

Each `github-runner-nixarchy*` service gets `unitConfig.RequiresMountsFor = [ "/mnt/build" ]`, so a missing
`/mnt/build` fails the runner instead of running CI on `/`. This is the pattern Docker and containerd already use on
p620 for `/mnt/img_pool`. It goes in `modules/services/nixarchy-runner.nix` as `RequiresMountsFor = [ cfg.buildDir ]`,
so it follows whatever `buildDir` a host sets. For a host whose `buildDir` is on `/`, that is a no-op.

### The VM workspace keeps its path

nixarchy hardcodes `/mnt/data/vmtest` in `AGENTS.md`:

- line 448: agents keep their worktrees there;
- line 788: `flock /mnt/data/vmtest/codex-build.lock`.

It is also in docs and plans. Renaming the path would break every agent's instructions, and any agent working there
at the time.

So the path stays, and the data moves under it:

- **Bind mount:** `fileSystems."/mnt/data/vmtest"` mounts `/mnt/build/vmtest` there, with
  `bind nofail x-systemd.requires-mounts-for=/mnt/build`.
- **What doesn't change:** `services.nixarchy-runner.vmImageDir` stays `/mnt/data/vmtest`. The prune timer then
  works on the new disk. Its `find -xdev` starts at the mount, so it stays on that disk.
- **Old data:** the contents of `/mnt/data/vmtest` (4.4 GB, plus any worktrees) are copied once, with
  `rsync -a -H -A -X`, before the bind mount first goes live. The originals stay underneath the mount, hidden and not
  deleted. Removing them is a later task, with the owner's OK.
- **Missing disk:** the bind mount fails (`nofail`), and `/mnt/data/vmtest` shows the old copy. That is stale but
  intact, and agents can still work there.

### What doesn't change

- `/nix/store` and its `min-free` and `max-free` limits stay on the root NVMe.
- Build outputs are still copied into the store across filesystems, as they are from `scratch` today.
- The BFQ udev rule (`nvme[0-9]n1`) already covers the new disk, and the daemon's best-effort priority 7 still
  applies. Only the rule's comment, which says "both NVMe disks", is updated.
- The old `scratch` SSD's `fileSystems."/var/lib/nix-build"` entry is removed, so it is no longer mounted. Its
  data stays on the disk.

## Cutover

The switch changes the build-dir for every build on p620, so it runs in a quiet window:

1. Announce on the agent bus.
2. Wait until no nixarchy runner is busy, no `omarchy-edge` verify is running, and no other build is in flight:
   no `nix-daemon` build children, and no `nixbld` processes.
3. Check that nothing has files open under `/mnt/data/vmtest` (`fuser -vm`). If an agent does, ask on the bus and
   wait.
4. Partition, format, then mount `/mnt/build` by hand, create `vmtest` with the owner and mode the plan reads from
   `/mnt/data/vmtest`, and rsync.
5. Unmount, then `just p620`. The switch mounts `/mnt/build`, adds the bind mount, and restarts the daemon and the
   runners with the new settings.

## Alternatives rejected

- **Mount at `/var/lib/nix-build`:** that keeps one path, but it gives the agents' workspace no tidy home on the
  same disk.
- **Rename the workspace to `/mnt/build/vmtest` and edit nixarchy's docs:** this touches another repo, breaks
  agents mid-task, and leaves old paths in history and plans. The bind mount gives the same result with no change
  outside this repo.
- **A symlink from `/mnt/data/vmtest`:** `find -xdev`, `flock` and git worktree paths resolve differently through a
  symlink. A bind mount is the same directory as far as every tool can tell.
- **XFS or btrfs:** these add no benefit for build scratch here, and differ from the rest of p620.
- **`discard` mount option:** it adds latency to every delete during build churn. Weekly `fstrim` is already in
  place.
- **Moving runner state:** 300 MB, and it would reopen the DynamicUser trap the module records.
- **No fallback (required mount):** a dead build disk would then also stop the host from rebuilding itself.
- **More runners:** they are limited by CPU and RAM during VM tests, not by disk.

## Risks

- **Formatting the wrong disk:** the plan uses the by-id path only, and checks again just before `mkfs` that it
  has no partitions and no signatures.
- **A build or agent active during the cutover:** a running build loses its temporary tree, and an agent loses its
  open files under the workspace. Mitigation: the quiet-window checks and the bus.
- **A fallback build on `/` fills the root disk:** only p620's own and agents' builds run there. CI is gated, and
  `min-free` still protects the store.
- **A missing disk at boot delays it** by the 10 s device timeout, as `scratch` does today.
- **Hidden old data under the bind mount** stays out of sight and keeps using space on `/mnt/data`, until a later
  cleanup.

## Verification

- **Before the switch:**
  - `just check-syntax` and `just test-host p620`;
  - `nix eval` shows `nix.settings.build-dir = "/mnt/build/nix"`, `RequiresMountsFor` on all four runners, and the
    two new `fileSystems` entries.
- **After the switch:**
  - `findmnt /mnt/build` and `findmnt /mnt/data/vmtest` show the new disk, and `nix config show build-dir` shows
    `/mnt/build/nix`;
  - a small `nix build --rebuild` of a test derivation creates its tree under `/mnt/build/nix`, seen with `ls`
    during the build;
  - the next nixarchy runner job writes its VM install there, seen with `df` growth on `/mnt/build`;
  - the four runners are active, and `systemctl show -p RequiresMountsFor` lists `/mnt/build`;
  - `lsblk` shows `scratch` unmounted, and its data is still there;
  - no failed units.
- **Fallback:** with `/mnt/build` unmounted by hand, at an approved quiet moment, `systemctl start` of a runner
  fails on the mount dependency, and a small `nix build` still works on `/`. Then remount.
