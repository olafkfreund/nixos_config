# Spec: p620 switches itself after a green edge, without killing CI jobs

Revision 2. The Codex and agy reviews of revision 1's plan (2026-11-27) found
two holes. A deferred drain restarted units, which cancels the job a runner is
still running. A crash after closing admission left four runners offline with
nothing to recover them. Their other findings are folded in below.

## Design

Option 1 of the design pass on nixarchy#1967: a drain operation in the
listener.

### 1. The listener protocol (patch to github-runner 2.338.2)

The patch is appended to nixpkgs' existing `patches` with
`pkgs.github-runner.overrideAttrs`. The files live in the runner's
`StateDirectory`, `$RUNNER_ROOT/drain/` (`/var/lib/github-runner/<name>/drain/`).
That directory survives a unit exit. The work directory is a `RuntimeDirectory`
that systemd wipes when the unit stops, so the files cannot go there.

- **Request.** `drain/request`, written by root, mode 0644, atomically
  (write a temporary file, then rename). Contents: `{"id": "<uuid>"}`.
- **Acknowledgement.** `drain/ack`, written by the listener atomically.
  Contents: `{"id": "<request id>", "invocation": "$INVOCATION_ID",
  "state": "draining" | "exited-idle" | "exited-after-job" | "cancelled"}`.
- **Admission boundary.** Before the listener acknowledges a new broker offer,
  it checks for `drain/request`.
  - If the request is present, the offer is left unaccepted, and the broker
    requeues it after 60 seconds.
  - An offer that was already acknowledged or acquired goes on to run.
  - The worker, its lease renewal and job-cancellation messages keep running
    until the job completes.
- **Exit.** Once no job is running and the request is still present, the
  listener deletes its session, writes `exited-idle` or `exited-after-job`, and
  exits 0. It exits only after writing the acknowledgement.
- **Cancel.** If `drain/request` is removed before the listener exits, the
  listener writes `cancelled` and goes back to accepting offers. Its process
  never stops.
- **A deterministic L0 test.** Under `src/Test/L0/Listener/`, a synchronisation
  barrier at the point between offer and acquisition shows three things: an
  offer that arrives after the request is not accepted, an acquired job runs
  once, and cancel resumes the listener. nixpkgs runs the L0 tests at build time
  (`doCheck`).

### 2. Admission closed by systemd (module)

`modules/services/nixarchy-runner.nix` adds
`systemd.services."github-runner-nixarchy${suffix}".unitConfig.ConditionPathExists
= "!/var/lib/guarded-upgrade/runners-closed"`. It goes in `unitConfig`, the
`[Unit]` section; `serviceOverrides` writes `[Service]`. While the marker
exists, systemd skips the start: the unit stays inactive and the job result is
`done`. switch-to-configuration then neither fails nor starts the runner (agy
checked this in the pinned `switch-to-configuration-ng`). The condition stops
no running unit, so the upgrade still waits for each unit to exit. The module
also wires the patched `package`, and gives the starts a bound,
`TimeoutStartSec` instead of `0`, for the starts the upgrade itself makes.

### 3. The orchestration (`scripts/guarded_upgrade.py`, p620)

The p620 branch runs these steps in order, under `STATE/lock` and the deploy
lock:

1. **Journal first.** Write `STATE/drain` with
   `{"phase": "draining", "sha", "request", "deadline"}` before the marker.
   Delete `STATE/verified`: the canary must not outlive the drain.
2. Write the marker, then each runner's `drain/request`.
3. **Wait** up to 30 minutes, polling every 15 seconds. Every runner needs an
   `exited-*` acknowledgement whose id matches the request, an `invocation`
   equal to the unit's `InvocationID` before the drain, and an inactive unit
   with an empty cgroup.
4. **Defer.** A missing or ambiguous acknowledgement, or the deadline, defers
   without killing anything:
   - remove every request (draining listeners cancel and keep running);
   - remove the marker;
   - `systemctl start` only the units that are inactive, within a bounded
     timeout;
   - clear the journal;
   - exit 0 with "deferred: drain incomplete".
   No unit is ever stopped or restarted.
5. **Recheck the gates** after the drain: the window, pause, sessions,
   `deploy_conflict`, and that `resolve_main()` is still the SHA. The drain
   can take minutes, and idle reports go stale after 120 seconds. If a gate
   fails, defer as in step 4.
6. **Activate.** Set the journal's phase to `switching` and run the existing
   transaction.
7. **Verify the host while the runners are still closed.** This is
   `verify_local` without the runner part.
8. **Commit or roll back.** If verification passes, set the phase to
   `settled-commit`. Otherwise roll back, and once the old generation is
   confirmed, set the phase to `settled-rollback`.
9. **Reopen.**
   - Remove the marker, start the four units with a bounded timeout, and wait
     with a bound for four new invocations that GitHub reports online. Busy is
     fine; "online" is the bar.
   - A readiness failure publishes nothing and exits 1. The phase becomes
     `reopen-failed`, and the next run's recovery retries the reopen.
   - After `settled-commit` and a successful reopen, publish `verified`. A
     rollback never publishes the rejected SHA.
10. Clear the journal.

**Recovery** runs at the start of `main()`, under both locks, before the pause
and runner gates:

- A journal in `draining` gets the defer path.
- `switching` gets today's interrupted-transaction rollback, then reopens.
- `settled-*` or `reopen-failed` goes straight to the reopen.
- A marker with no journal is an orphan. Recovery logs it loudly and runs the
  reopen.

A rollback inside a recovery reopens on p620. `scripts/deploy-hold.sh` refuses
a manual deploy while `STATE/drain` exists, and names the journal.

**Razer** re-reads p620's canary after taking its own deploy lock, immediately
before it activates. The manual p620 canary path (`verify_local`, then save)
moves under p620's deploy lock, and keeps its runner check.

**For the disposable test**, `guarded_upgrade.py` reads these from environment
variables:

- the repositories;
- the runner unit and name prefix;
- the CI workflows it checks;
- the window;
- the bus room.

The defaults stay as they are today.

### 4. Test, roll out, turn on

- **An isolated NixOS VM on p620** with outbound network access, the patched
  runner and the module, and four runners under a unique label against a
  disposable repository. It has two generations: a baseline, and a candidate
  that can be forced to fail verification. It runs the real
  `guarded_upgrade.py` with the overrides, and these scenarios:
  - (a) a job acquired at the boundary completes exactly once, before the
    switch;
  - (b) a job dispatched after admission closes queues, and runs exactly once
    after the reopen;
  - (c) the same as (b), with a forced verification failure and a real
    rollback;
  - (d) one runner withholds its acknowledgement, and the switch defers
    without stopping it;
  - (e) the upgrade is interrupted right after the marker is written, then
    again after the rollback, and recovery reopens both times;
  - (f) one runner stays busy past the deadline, the drain defers, and the
    job completes.
  Each job writes to an execution counter. The run records invocation IDs,
  condition skips, the running and boot generations, and the canary's
  contents.
- **Rollout.** Deploy steps 1–3 to p620 with `autoActivate = false`, so the
  running generation and the rollback target both carry the patch and the
  condition. Then run one manual drain on p620 with the runners idle. Only
  after that, set `autoActivate = true`.

## Alternatives rejected

- `--once` listeners under a supervisor: an idle listener still races.
- Routing on GitHub: there is no drain endpoint and no acknowledgement.
- A longer stop timeout or systemd ordering: SIGINT cancels the active job.
- Restarting units on defer, which revision 1 did: it kills the job in flight.

## Risks

- A wrong serialisation in the patch loses or duplicates a job. The L0 test
  and scenarios (a) and (b) are there to catch it.
- Each runner bump re-applies the patch, and a failed apply fails the build.
- A drain that never completes defers every night, and each deferral logs
  "drain incomplete". The nightly review should see repeated deferrals.
- A 30-minute deadline means an install that needs its full hour defers the
  upgrade to the next night, which is the intended behaviour.
