# Spec: p620 switches itself after a green edge, without killing CI jobs

## Design

Option 1 of the Codex design pass recorded on nixarchy#1967
(https://github.com/olafkfreund/nixarchy/issues/1967#issuecomment-7218397792).

1. **A drain operation in the listener.** A patch to the pinned
   `github-runner` (2.338.2), applied through the runner module's `package`
   (`modules/services/nixarchy-runner.nix`). On a drain request the listener
   stops accepting new job offers, lets an acquisition in flight settle, keeps
   any acquired job's worker and lease alive until it completes, then closes
   its session and exits 0. The request is a file the listener polls in its
   work directory, or a signal, whichever the patch can serialise with job
   acceptance most simply; the patch says which. It writes an acknowledgement
   (state file: `draining`, `idle-exited`, `job-finished-exited`) the upgrade
   reads.
2. **Admission closed by systemd.** A root-owned marker
   `/var/lib/guarded-upgrade/runners-closed` and a
   `ConditionPathExists=!/var/lib/guarded-upgrade/runners-closed` on the four
   `github-runner-nixarchy{,-2,-3,-4}` units, so nothing (activation, a
   restart, recovery) can start a listener while maintenance is open. It is in
   the running, candidate and rollback generations before `autoActivate` is on.
3. **The upgrade orchestrates.** In `guarded_upgrade.py`'s p620 branch, after
   staging and under the deploy lock: recheck the gates, announce, write the
   marker, request all four drains, wait (bounded) for four fresh
   acknowledgements tied to this request and each unit's invocation, and an
   exited unit with an empty cgroup. A missing or ambiguous acknowledgement, or
   the deadline, defers: remove the marker, restart the units, no switch. Then
   activate. On verify, check the system with the runners closed (today's
   `verify_local` expects four active runners, so it moves to after reopening).
   On commit or confirmed rollback: remove the marker, start the four units,
   check they reconnect, then publish `verified` for razer. The marker survives
   an interrupted transaction, so recovery keeps admission closed until it
   settles.
4. **Test, then turn on.** A disposable repository with four equivalent
   runners under a unique label on an isolated NixOS host: (a) a job held after
   acquisition at the boundary completes once, before the switch; (b) a job
   dispatched after admission closes stays queued and runs once after reopening;
   (c) the same with a forced verification failure and rollback; (d) withholding
   one acknowledgement prevents the switch. Job IDs, attempts, status
   transitions, acknowledgements and unit start times are recorded. Then
   `autoActivate = true` on p620.

Unit-level tests for the orchestration go into
`scripts/test_guarded_upgrade.py` with the existing fixture style.

## Alternatives rejected

- **`--once` listeners under a supervisor**: an idle listener can still take its
  first job after a busy snapshot; the race stays.
- **Routing on GitHub (labels, deletion)**: no drain endpoint and no
  acknowledgement that outstanding offers settled.
- **Longer stop timeout or systemd ordering**: SIGINT cancels the active job.

## Risks

- The patch touches the broker acquisition path; a wrong serialisation loses
  or duplicates a job. The disposable test exists for exactly this.
- Each runner bump re-applies the patch; a failed apply must fail the build.
- A stuck acknowledgement defers every night; the deferral is logged and the
  nightly review should see repeated deferrals.

## Verification

The four disposable-repository scenarios above, recorded in the PR; unit
tests; p620 and razer toplevels build; the runner package builds with the
patch; one manual end-to-end drain on p620 with runners idle before
`autoActivate` is turned on.
